# Git 分支与提交规范

## 工作区保护

- 开始前执行 `git status --short`，确认当前分支、已修改文件和未跟踪文件来源。
- 发现非本任务修改时保留并绕开；同文件存在修改时必须逐块阅读后协同编辑。
- 禁止使用 `git reset --hard`、`git checkout --`、`git clean` 覆盖未确认修改。
- 禁止把 `target/`、`dist/`、日志、密钥、IDE 临时文件和本地环境文件纳入提交。
- Git 操作只在用户明确要求时执行；查看 status、diff、log 不视为提交授权。

## 分支

- 正式开发使用短生命周期分支，命名为 `feat/<topic>`、`fix/<topic>`、`refactor/<topic>`、`docs/<topic>`。
- Codex 创建的分支遵守运行环境要求使用 `codex/` 前缀。
- topic 使用简短英文 `kebab-case`，表达业务目的，禁止 `test1`、`new-branch`、日期堆砌。
- 一个分支围绕一个可交付目标；无关修复另建任务或分支。
- 未经确认禁止切换分支、删除分支、rebase、merge 或推送远端。

## 提交拆分

- 一个提交只表达一个可独立理解、验证和必要时回退的目的。
- 实现与直接保护该实现的测试放在同一提交；纯测试基础设施可单独提交。
- 后端契约与必须同步的前端调用可放同一提交，前提是拆开后任一提交都会破坏构建或行为。
- 机械格式化、依赖升级、Schema 迁移、业务代码和文档治理不得无理由混在一个提交。
- 同一目的涉及多个文件不是拆分理由；多个目的碰巧修改同一文件也不能强行合并。
- 提交前使用 `git diff` 按块检查，确保没有调试代码、临时注释和顺手修改。

## 提交信息

格式：

```text
type(scope): 中文摘要
```

- type 仅使用 `feat`、`fix`、`refactor`、`test`、`docs`、`chore`、`build`。
- scope 使用稳定模块名，如 `auth`、`tran`、`customer`、`web`、`rules`；无明确范围时可省略。
- 摘要使用祈使含义，说明完成了什么，禁止“修改代码”“fix bug”“更新文件”。
- 需要正文时说明原因、关键约束和兼容影响，不复述文件列表。
- 禁止添加无意义 AI 署名、共同作者、生成工具宣传和虚构 issue 编号。

示例：

```text
fix(auth): 统一登录失败错误码
refactor(cache): 按职责拆分 Redis Key 常量
docs(rules): 细化前端代码规范
```

## 暂存与提交前检查

1. `git diff --check` 检查空白错误。
2. `git diff -- <files>` 检查未暂存修改。
3. 按文件或补丁显式暂存，复杂工作区禁止直接 `git add .`。
4. `git diff --cached` 确认提交内容和删除文件。
5. `git status --short` 确认未遗漏直接相关文件，也未混入无关文件。
6. 确认相应测试和文档已经完成，再创建提交。

## 回退与历史

- 已共享提交使用 `git revert`，保留原提交和回退原因；禁止擅自改写已发布历史。
- 本地未共享提交需要重写时也必须先确认不会覆盖用户修改。
- 禁止 force push，除非用户明确要求且已说明影响范围。
- 回退代码不回退仍然正确的文档或迁移时，提交信息必须明确保留原因。
- 冲突解决必须理解双方改动，禁止一律选择 ours/theirs。
