# 开发流程与架构边界

## 任务类型

- 审查：只报告可验证的问题、风险和缺失测试，未经要求禁止修改文件。
- 修复：保持原有正确行为，先复现问题，再修实现并增加回归测试。
- 功能：先确认业务输入、输出、权限、状态和失败规则，再实现完整前后端流程。
- 重构：不得改变外部行为；必须有测试或对比证据保护现有契约。
- 数据变更：必须同时处理 `CarDealerCRM.sql`、初始化数据、测试数据和代码映射。
- 文档任务：只修改约定范围内文档，不借机改代码或生成无关文件。

## 实施顺序

1. 读取 `AGENTS.md`、业务 Spec、相关规则、实现、调用方和现有测试。
2. 写清本次允许改变和必须保持不变的行为。
3. 识别输入、输出、权限、状态变化、事务、并发、缓存、错误和前后端影响。
4. 确定主要实现文件、直接调用方、测试文件和必须同步的文档。
5. 先修改主要实现，再同步调用方和测试；禁止先改测试迎合错误实现。
6. 运行最小有效验证，再按影响面扩大验证范围。
7. 检查完整差异、未跟踪文件和未验证风险，满足验收后才可提交。

## 后端分层

- `web` Controller：HTTP 参数、Bean Validation、权限入口、调用 Service、返回 `R`。
- `service`：公开业务用例契约；`service.impl`：业务规则、状态迁移、事务和并发控制。
- `manager`：跨领域编排或基础设施封装，不建立无意义的透传层。
- `mapper` 与 Mapper XML：持久化读写，不读取当前用户，不决定业务状态。
- `model`：数据库持久化对象；`dto/query/result`：跨层输入、查询和输出契约。
- `config/security/filter/handler`：框架装配和认证边界，不承载普通业务流程。

禁止 Controller 依赖 Mapper/RedisManager、Mapper 依赖 Service、Model 依赖 Spring Bean。
Service 之间出现循环依赖时必须重新划分业务边界。

## 前端分层

- `pages`：路由页面和页面流程，不直接访问 Axios 或浏览器存储。
- `modules/<domain>`：领域 API、类型、组件和 composable，不跨领域读取内部实现。
- `stores`：认证、权限和全局 UI 等跨页面状态，不充当所有接口数据缓存。
- `shared`：跨领域基础能力，不包含汽车销售领域规则。
- `components/ui`：基础 UI，不访问 API、Store、权限码和业务状态。

前端校验、按钮隐藏和路由守卫只改善体验，不能替代后端校验和授权。

## 影响面检查

- Java public 方法变化：检查接口、实现、Controller、Manager、测试和反射/框架调用。
- API 变化：检查模块 API、TypeScript 类型、页面、Store、错误码、`docs/api/openapi.yaml` 和 `docs/api/api-conventions.md`。
- 状态或枚举变化：检查数据库值、Java 枚举、SQL 条件、前端映射、筛选项和测试数据。
- Schema 变化：检查 `CarDealerCRM.sql`、测试 Schema、Mapper XML、Model、查询对象和初始化数据。
- 认证权限变化：检查 SecurityConfig、Filter、Handler、`@PreAuthorize`、数据范围和前端权限展示。
- Redis Key 或缓存变化：检查所有生产者、消费者、失效逻辑、TTL 和旧 Key 兼容。
- 共享前端组件或 http-client 变化：扩大到全部调用模块并运行完整前端检查。

## 修改边界

- 只修改完成任务所必需的文件；发现旁支问题先记录，不得静默并入当前任务。
- 不得覆盖、回退或重新格式化来源不明的现有修改。
- 删除 public 方法、兼容入口或旧字段前必须证明无调用并说明迁移方式。
- 依赖升级、框架替换、全项目格式化和目录迁移必须作为独立任务。
- 用户限制测试、服务启动或文件范围时必须遵守，并在交付中说明未验证部分。

## 完成条件

- 实现、直接调用方、测试和契约文档保持一致。
- 新失败路径不会返回成功、泄露内部信息或留下部分写入。
- 已执行与风险匹配的测试、编译、类型检查或静态检查。
- 工作区没有本任务产生的临时文件、后台进程和意外格式差异。
