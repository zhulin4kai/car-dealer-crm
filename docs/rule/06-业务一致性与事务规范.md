# 业务一致性与事务规范

## 业务状态机

- 交易、支付、退款、发票、库存和客户转换必须定义允许状态、允许动作和迁移结果。
- 状态只能通过命名明确的业务动作修改，禁止通用 `updateStatus/updateStage` 接口任意赋值。
- 每次迁移必须校验当前状态、操作者权限、必备数据和关联对象状态。
- 非法迁移必须返回稳定错误码，不得静默忽略、自动跳级或依赖前端阻止。
- 状态 code 在数据库、Java 枚举、前端映射和测试数据中保持一致，禁止依赖枚举 ordinal。
- 关键迁移记录操作者、发生时间、前后状态和业务原因。

## 事务边界

- 一个用户可感知的业务动作对应一个事务入口，放在 public Service 或跨领域 Manager 方法。
- 多表写入、“校验后写入”、库存变化、支付退款、审批和发票操作必须在事务内完成。
- 事务方法使用 `@Transactional(rollbackFor = Exception.class)`；禁止 private 方法或类内自调用假装建立事务。
- 事务内禁止执行不可控长耗时网络调用；确需外部调用时必须定义超时、重试和补偿策略。
- 禁止捕获异常后返回 `false` 或成功导致事务提交；转换异常时必须保留 cause。
- 事务完成前不得发布“已成功”事件或写成功审计；缓存失效和外部通知必须考虑提交时序。

## 并发控制

- 库存、支付状态、退款额度、审批状态和唯一转换必须使用 CAS、行锁或唯一约束。
- CAS SQL 必须包含旧状态或版本条件，并检查影响行数是否为 `1`。
- 悲观锁必须在事务中使用；多个对象加锁时按稳定顺序排序，降低死锁风险。
- 禁止只通过“先查询再判断再更新”保证并发正确性。
- 冲突必须返回明确 `409`/业务 code，禁止自动覆盖另一个用户的成功修改。

## 幂等与重复请求

- 创建支付、退款、审批、库存流水和客户转换必须定义幂等键或唯一业务约束。
- 重复请求不得重复扣减库存、重复记账、重复退款或生成第二条成功流水。
- 幂等命中时必须返回第一次操作的确定结果，不能根据当前偶然状态重新执行副作用。
- 前端禁用按钮不能作为幂等保障；重试、网络超时和用户双击都必须由后端处理。

## 库存、支付与发票

- 库存扣减和恢复必须绑定明确业务动作、数量和业务对象，并写入不可删除流水。
- 库存更新必须防止结果小于零；恢复库存必须证明对应扣减已发生且未恢复。
- 支付记录只能追加或状态迁移，禁止删除原支付事实；退款使用反向流水关联原支付。
- 累计收款、可退款金额和交易应付金额必须由服务端计算，禁止信任客户端汇总值。
- 发票金额不得超过可开票金额；作废、红冲和重新开票必须保留历史关联。
- 交易阶段、付款状态、退款状态、发票状态和库存状态必须在同一业务动作后保持一致。

## 客户、线索与删除

- 线索转客户必须防止重复转换，保留原线索、来源、负责人和转换记录。
- 客户归属变更必须检查操作者数据权限，并记录原负责人和新负责人。
- 删除前检查业务状态、关联记录和审计保留要求；已产生交易、支付或流水的数据不得物理删除。
- 可删除数据也必须明确级联范围，禁止依赖数据库默认级联造成未知删除。
- 批量操作必须选择“全成功”或“逐项结果”，接口和事务实现必须与选择一致。

## 缓存一致性

- 数据库是业务事实来源，缓存不得决定核心状态迁移、权限、金额和库存。
- 写操作先完成数据库事务，再失效相关详情、列表和派生缓存。
- 缓存 Key 统一由 `RedisKeys` 构造；模式删除使用 SCAN，禁止生产环境使用 KEYS。
- 缓存读取失败必须回源或明确失败，禁止返回伪造空数据；缓存写入失败不得重复业务写入。
- TTL、空值缓存和列表缓存必须有明确策略；禁止无期限缓存可变业务数据。
- 新旧缓存结构不兼容时必须更换版本化 Key 或提供迁移，禁止用旧数据反序列化碰运气。

## 验证场景

- 状态迁移测试覆盖合法迁移、非法旧状态、无权限、记录不存在和重复请求。
- 并发写入测试至少覆盖 CAS 失败或唯一约束冲突，不得只测试顺序执行。
- 事务测试验证中途失败时所有数据库写入回滚，且不会留下成功缓存或成功审计。
- 库存和财务测试同时核对主记录、流水、汇总金额及关联状态。
