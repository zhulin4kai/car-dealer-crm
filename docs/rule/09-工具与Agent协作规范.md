# 工具与 Agent 协作规范

## 代码发现

- 禁止使用 graphify。
- 代码定义、调用关系和影响面优先使用 `codebase-memory-mcp` 的 `search_graph`、`trace_path`、`get_code_snippet`。
- 知识图谱未索引时先运行 `index_repository`；索引结果不足时再使用 `rg`、`rg --files`。
- 字符串、错误文案、配置值、Markdown 和脚本搜索直接使用 `rg`。
- 查找调用方必须覆盖主代码和测试；禁止只读一个文件后猜测全项目行为。
- 架构说明、代码注释和历史记录只能作为线索，最终结论必须与当前代码相互核对。

## 修改前

- 明确任务是审查、讨论、教学还是执行；审查和“只说不写”禁止修改文件。
- 修改前向用户说明将涉及的文件类型和目的，不得先改后解释。
- 读取目标实现、直接调用方、相关测试、适用规则和工作区现有差异。
- 写出必须保持的行为和允许改变的行为，避免把修复扩大为未授权重构。
- 发现用户已有修改时默认保留；只有无法兼容时才请求确认。

## 文件编辑

- 手工修改使用 `apply_patch`，禁止用覆盖整文件的 shell 技巧隐藏实际差异。
- 批量机械替换和格式化必须限定路径，并在执行后检查完整 diff。
- 新文件遵守现有目录职责；禁止因找不到位置就创建 `common`、`utils`、`Constants` 杂物文件。
- 不自动安装依赖、访问网络、启动前后端或修改本机配置，除非任务明确需要。
- 禁止破坏性 Git 命令，不得覆盖、回退或删除来源不明的修改。

## 实施与验证

- 执行任务必须完成主要实现、直接调用方、对应测试和必要文档，不停在方案阶段。
- 前后端契约变化必须双向检查；Schema 变化必须同步测试 Schema 和 Mapper。
- 测试失败先判断根因，禁止降低断言、跳过测试、关闭安全组件或恢复不安全行为。
- 命令长时间运行时持续报告当前阶段；需要的进程结束前不得提前宣称完成。
- 未经用户明确要求不得创建分支、commit、push、PR 或修改远端状态。

## 事实与沟通

- 禁止虚构类、字段、调用关系、业务规则、命令输出、测试结果和提交状态。
- 结论区分：已从代码或命令验证、根据证据推断、尚未验证。
- 用户要求教学时，说明原行为、问题、修复原则、具体修改和取舍，不能只交付代码。
- 用户限制文件、阶段、测试或服务启动范围时严格遵守，不以“最佳实践”为由越界。
- 新消息与旧任务冲突时以最新要求为准；停止或收拢指令必须立即执行。

## 交付输出

- 说明修改了什么、为什么、验证命令和结果，不逐文件复述机械替换。
- 明确列出未执行的测试、遗留风险和需要用户决定的事项。
- 不宣称未运行测试通过，不隐藏失败、警告、权限限制和环境依赖。
- 未实际完成的 Git 操作不得报告为已提交或已推送。
