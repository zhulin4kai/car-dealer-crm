# 文档与 Spec 治理规范

## 文档职责

- `docs/specs/`：项目愿景、目标用户、业务问题、范围、能力、非目标和成功标准。
- `docs/rules/`：长期有效且可执行的开发约束，不记录一次任务过程。
- `docs/todo/`：阶段计划和临时执行清单，必须有负责人范围、顺序、验收和结束条件。
- `docs/api.md`：请求、响应、HTTP 状态、业务错误码和兼容变化。
- `docs/backend.md`：后端模块、分层、基础设施和关键运行机制。
- `docs/frontend.md`：前端目录、模块、状态、路由和共享能力。
- `docs/integration.md`：前后端联调、认证、环境变量和本地协作流程。

## Spec

- Spec 只写业务事实和方向，不写实现类、数据库字段、API 路径、测试命令或生成过程。
- 必须区分业务范围与非目标，禁止用模糊“支持管理”代替可理解的业务能力。
- 成功标准必须能从用户结果、业务数据或流程完成度判断，禁止只写“代码质量提升”。
- 技术实现不得反向篡改 Spec 以证明现有代码正确；业务变化必须先明确决策来源。

## Rule

- Rule 使用“必须、禁止、应当、可以”表达强度，并给出适用对象、触发条件和验证方式。
- 每份 Rule 必须包含 `description` 和 `globs` Front Matter，匹配真实目录。
- Rule 应针对当前技术栈和目录，禁止复制 JPA、React 等项目未使用框架的规则。
- 同一约束只在职责最匹配的文件定义，其他文件通过引用衔接，禁止多份相互冲突。
- 新规则不能仅因一次事故产生；必须能预防一类重复问题且不妨碍正常实现。

## Todo

- Todo 必须说明目标、当前事实、明确范围、实施顺序、依赖、风险和验收命令。
- 每项状态只能依据代码、测试或文档证据更新，禁止凭感觉标记完成。
- 计划改变时更新原 Todo，不新建多个内容重叠的“最终版”。
- 完成后应归档或删除临时 Todo，长期结论迁移到对应 Spec、Rule 或技术文档。

## 更新触发

- API 字段、状态码、错误码变化：更新 `docs/api.md` 和必要联调说明。
- 后端目录、分层、认证、缓存和基础设施变化：更新 `docs/backend.md`。
- 前端模块、路由、Store、共享 API 和构建命令变化：更新 `docs/frontend.md`。
- 环境变量、代理、端口和认证联调流程变化：更新 `docs/integration.md`。
- 业务范围、用户或成功标准变化：更新对应 Spec，并明确这是业务决策。
- 长期工程约束变化：更新对应 Rule、Front Matter 和总览索引。

## 写作与维护

- 标题和正文使用中文，代码标识符、命令、路径和协议字段保持原样。
- 文档描述当前有效事实；历史原因仅在理解当前决策确有必要时保留。
- 路径、命令和配置必须可在仓库中验证，禁止记录不存在的脚本和未来设想为已完成。
- 完成状态必须附代码、测试或命令证据；未验证内容明确标记为待确认。
- 文件重命名时同步 `AGENTS.md`、规则索引和所有引用。
- 行为与文档冲突时不能长期保留两套标准：确认正确来源后同步另一方。
