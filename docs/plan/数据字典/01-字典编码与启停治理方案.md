# 字典编码与启停治理方案

## 关联 Spec

- docs/spec/数据字典/00-业务范围与边界.md
- docs/spec/数据字典/01-流程规则与验收规格.md

## 背景

数据字典用于统一来源、状态、原因、类型等业务口径。字典不是规则引擎，不能替代领域状态机和权限系统。

## 目标

- 字典类型和字典项具备稳定业务编码、展示名称、适用模块、启停状态和排序。
- 字典项启停不破坏历史数据展示。
- 删除或修改字典受到业务关系约束。
- 核心状态和原因不在各模块重复硬编码为不同含义。
- 字典变更可审计。

## 当前现状

- 后端已有 `DicController`、`DicServiceImpl`、`TDicType`、`TDicValue`、`DicMapper`。
- 后端已有 `DicEnum` 表达部分字典类型。
- 前端已有 `dealer-web/src/modules/dict/` 和字典类型、字典值页面。
- 当前字典适用范围、启停影响、删除限制和缓存一致性需要治理。

## 设计方案

### 字典模型

字典类型表达业务域和可维护范围，字典项表达稳定 code、展示名称、排序、启停状态和适用范围。

状态机核心 code 不应完全依赖可随意维护的字典项。

### 后端方案

- 在 `DicServiceImpl` 中补齐类型和值的唯一约束、启停、删除限制和缓存失效。
- 删除字典前检查业务引用，存在引用时禁止删除或仅允许停用。
- 字典读取提供按类型查询和缓存，但数据库仍是事实来源。
- 字典变更写操作审计。

### 前端方案

- 字典类型和值页面展示编码、名称、状态、排序和适用模块。
- 删除、停用和修改 code 前展示影响提示。
- 业务页面使用后端字典接口或稳定前端映射，不临时写中文值。

### 数据方案

- 字典类型 code 唯一，字典项在同类型下 code 唯一。
- 历史数据保存稳定 code，展示时可读取已停用字典名称。
- 缓存 key 使用 `RedisKeys` 或统一缓存管理。

## 风险与约束

- 字典不能替代商机、交易、支付、库存等状态机校验。
- 启停不能造成历史记录无法展示。
- 删除不能破坏已有业务引用。
- 多语言翻译、流程编排和用户自定义资料项不是第一阶段范围。

## 实施阶段

1. 梳理当前字典类型、值、缓存和业务引用。
2. 补齐字典唯一约束、启停状态和删除限制。
3. 补齐业务引用检查和缓存失效。
4. 调整前端字典页面和业务页面字典使用。
5. 补充唯一约束、引用限制、缓存和权限测试。
6. 更新 API、后端、前端和集成文档。

## 验收标准

- 同一字典类型下不能创建重复 code。
- 停用字典项不再用于新增业务，但历史记录仍可展示名称。
- 被业务引用的字典项不能普通删除。
- 字典变更后业务页面读取到最新有效口径。
- 字典维护操作产生审计记录。

## 核心闭环补充

- 被任何业务记录引用的字典值不得物理删除。
- 字典删除不得删除交易备注、线索备注、客户备注或活动备注。
- 系统内置字典类型编码和业务判断编码不得普通修改。
- 字典类型删除必须检查其下所有字典值引用。

## 业务协同关系

- 依赖业务口径、展示需求、分类规则和状态治理要求。
- 影响线索、客户、商机、活动、原因、分类、展示名称和部分可配置枚举。
- 权限控制覆盖字典类型和值的新增、编辑、启停、删除和导入导出。
- 审计记录覆盖核心编码、展示名称、启停和删除拒绝。
- 统计口径依赖稳定编码，不能依赖可变展示名称。

## 状态与事件方案

- 状态列表：启用、停用、内置、删除受限和草稿。
- 触发事件：字典创建、改名、启停、引用、删除申请和缓存失效。
- 非法迁移：核心状态机编码不得普通修改，被引用字典值不得物理删除。
- 异常策略：存在引用时拒绝删除，建议停用；编码冲突时拒绝保存。

## 数据与历史方案

- 必须保留稳定 code、展示名称、启停状态、内置标识和引用关系。
- 被业务引用的字典值不能物理删除，更不能删除业务备注。
- 编码、启停、删除和批量导入必须审计。
- 字典 code 进入业务判断和统计口径。
