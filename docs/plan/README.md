# Plan 目录说明与归档目录

`docs/plan/` 保存的是整改、排查、执行和迁移过程中的计划文件。这里的内容用于解释某个阶段为什么要做、怎么分批做、当时发现了什么问题；它不是长期事实源，也不应被后续 agent 直接当作当前实现、接口或业务规则的权威依据。

## 使用原则

- 当前事实以代码、测试、`docs/specs/`、`docs/api.md`、`docs/backend.md`、`docs/frontend.md` 和 `docs/integration.md` 为准。
- `docs/plan/` 只作为过程上下文使用。执行任务前必须重新核对当前代码和测试，不得只按旧 plan 机械执行。
- plan 文件完成、废止或被新决策覆盖后，不要求持续同步其中所有细节；应在本文件的归档目录中登记状态。
- 新的短期执行事项优先写入 `docs/todo/`；长期业务方向写入 `docs/specs/`；长期规则写入 `docs/rules/`。
- 若旧 plan 与当前代码、spec、API 文档或用户最新决策冲突，以当前代码、长期文档和用户最新决策为准，并在提交中说明原因。

## 状态定义

- `active`：仍可作为当前整改入口，但执行前必须核对现状。
- `archived`：阶段目标已结束，仅保留历史上下文。
- `superseded`：已被新方案、新模块或新决策覆盖，不再执行原计划。
- `reference`：只作为背景材料，不作为执行清单。

## 维护要求

1. 完成或废止某个 plan 文件后，只更新本文件的归档目录，不要求回写旧 plan 的所有细节。
2. 如果旧 plan 仍有未完成事项，但已不适合作为当前入口，应把剩余事项重新拆到 `docs/todo/`。
3. 提交前用 `git diff --check` 检查格式，避免过程文档产生尾随空白。
