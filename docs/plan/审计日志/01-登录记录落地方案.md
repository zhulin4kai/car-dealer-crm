# 登录记录落地方案

## 关联 Spec

- docs/spec/审计日志/00-业务范围与边界.md
- docs/spec/审计日志/01-登录记录功能规格.md
- docs/spec/审计日志/03-权限安全与数据治理规格.md

## 背景

账号访问事实是审计日志的基础能力。登录成功、登录失败和失败原因必须由服务端认证结果产生，不能依赖前端提示、普通应用日志或临时控制台日志。

## 目标

- 持久化登录成功和登录失败记录。
- 对失败原因使用稳定编码，同时保持前台登录提示不暴露账号枚举信息。
- 支持管理员按账号、用户、结果、IP、时间范围查询。
- 支持详情查看和受控导出。
- 登录记录不保存认证凭证和完整请求体。

## 当前现状

- 登录成功处理在 `dealer-server/src/main/java/com/autodealer/crm/config/handler/MyAuthenticationSuccessHandler.java` 的 `onAuthenticationSuccess`。
- 登录失败处理在 `dealer-server/src/main/java/com/autodealer/crm/config/handler/MyAuthenticationFailureHandler.java` 的 `onAuthenticationFailure`。
- 认证入口由 `dealer-server/src/main/java/com/autodealer/crm/config/SecurityConfig.java` 配置。
- 当前登录成功会签发 JWT 并写入 Redis，登录失败会返回统一认证失败响应。
- 当前没有登录记录模型、Mapper、Service、Controller 和数据库表。

## 设计方案

### 数据模型

登录记录应独立于操作记录保存，建议字段包括：

- `id`：唯一标识。
- `login_act`：用户提交的登录账号。
- `user_id`：识别成功时的用户 ID，无法识别时为空。
- `user_name`：识别成功时的用户姓名，无法识别时为空。
- `result`：`SUCCESS` 或 `FAILURE`。
- `reason_code`：稳定失败原因编码，成功记录可为 `SUCCESS`。
- `reason_message`：面向管理员的简短原因说明。
- `ip`：客户端 IP。
- `browser`：浏览器名称和主要版本。
- `os`：操作系统名称。
- `request_id`：跨日志关联标识。
- `create_time`：登录发生时间。

### 失败原因模型

失败原因至少保留以下稳定编码：

- `BAD_CREDENTIALS`：账号不存在或凭证不正确。
- `DISABLED`：账号禁用。
- `LOCKED`：账号锁定。
- `ACCOUNT_EXPIRED`：账号过期。
- `CREDENTIALS_EXPIRED`：凭证过期。
- `INVALID_REQUEST`：请求参数不合法。
- `AUTH_SERVICE_ERROR`：认证服务异常。

前台响应可以继续返回统一登录失败文案，后台审计记录保存受控原因。

### 写入策略

- 登录成功：认证已通过但 JWT 尚未返回前写入成功记录。
- 登录成功记录写入失败：不签发 Token，返回系统异常，避免“成功登录但无审计事实”。
- 登录失败：认证失败处理器写入失败记录。
- 登录失败记录写入失败：仍返回认证失败响应，同时记录应用错误日志，避免把认证失败变成登录成功。
- 客户端信息解析失败：保留账号、结果、IP 和时间，浏览器或操作系统记为未知。

### 查询与详情

- 列表支持账号、用户姓名、结果、IP、时间范围组合筛选。
- 默认查询最近时间范围内第一页数据，禁止空条件无上限返回全部历史。
- 排序使用 `create_time desc, id desc`。
- 详情展示请求标识、完整结果类别和客户端信息，不展示认证凭证或异常堆栈。

### 导出

- 导出使用独立权限。
- 导出使用与列表一致的筛选条件和排序。
- 导出限制时间范围和最大数量。
- 导出动作写入操作记录，动作语义为“导出登录记录”。

## 风险与约束

- 登录失败无法识别用户时，不能伪造用户 ID 或用户姓名。
- 反向代理头必须受信任代理配置约束。
- 失败原因不能泄露给前台登录用户用于账号枚举。
- 登录审计写入不能记录密码、验证码、Token、Cookie、Authorization 或完整请求体。

## 实施阶段

1. 新增登录记录数据结构和枚举。
2. 新增登录记录写入服务。
3. 在登录成功和失败处理器接入写入服务。
4. 新增登录记录分页查询、详情和导出接口。
5. 新增权限控制、测试数据和 API 文档。
6. 执行认证、权限、脱敏、分页、排序和导出验证。

## 验收标准

- 正确账号密码登录后产生一条成功记录。
- 密码错误、未知账号、禁用账号、锁定账号均产生失败记录。
- 未知账号记录中用户 ID 为空，但账号、结果、原因、IP 和时间存在。
- 前台登录失败提示不暴露账号是否存在。
- 管理员可按账号、结果和时间范围查询。
- 无导出权限用户不能导出。
- 记录、详情和导出均不包含密码、Token、Cookie、Authorization 或验证码。

## 业务协同关系

- 依赖登录认证、权限变化、业务事件和敏感操作。
- 影响责任追溯、安全分析、异常排查和经营复盘。
- 权限控制覆盖审计查询、详情、导出和保留策略。
- 审计本身记录业务动作结果，不替业务模块做业务校验。
- 统计口径可读取审计异常，但不得用审计记录改写业务状态。

## 状态与事件方案

- 状态列表：记录成功、记录失败、待归档、已归档和保留期内。
- 触发事件：登录成功/失败、业务新增、编辑、审批、取消、作废、红冲、导出、删除和权限变更。
- 非法迁移：审计记录不得被业务接口物理删除。
- 异常策略：审计写入失败必须记录风险，不能悄悄吞掉关键业务操作。

## 数据与历史方案

- 必须保留操作者、业务对象、业务动作、结果、时间、IP、摘要和关联 ID。
- 审计日志在保留期内不可变更和删除。
- 审计查询和导出本身也应受权限和审计控制。
- 审计数据服务责任追溯和安全分析。
