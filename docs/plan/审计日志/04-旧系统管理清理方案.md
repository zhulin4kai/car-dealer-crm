# 旧系统管理清理方案

## 关联 Spec

- docs/spec/审计日志/00-业务范围与边界.md

## 背景

审计日志的产品边界不包含服务器监控、JVM 监控、系统参数维护、站点配置或开发调试页面。旧系统管理能力如果保留在菜单、接口、权限或文档中，会让管理员误以为 CRM 需要承担运维平台职责。

## 目标

- 清理旧系统管理、系统配置和服务器监控能力。
- 保留与审计日志相关的用户访问和业务操作追溯能力。
- 避免前端菜单、后端接口、权限数据、数据库结构和文档继续暴露旧能力。

## 当前现状

- 当前计划来源中已确认旧系统管理能力不属于 CRM 产品范围。
- 需要在当前代码和文档中检查是否仍存在系统配置、服务器监控、运行时指标、无业务价值系统信息等残留。
- 如果残留能力已经不存在，只保留验证记录，不制造空改动。

## 清理范围

需要检查并清理：

- 前端系统管理菜单、路由和页面。
- 后端系统配置、系统监控、运行时指标接口。
- 与旧系统管理相关的权限编码和种子数据。
- `t_system_info` 或等价系统配置、监控类数据表。
- API、后端、前端和业务文档中的旧能力描述。

不得清理：

- 用户权限管理。
- 数据字典管理。
- 审计日志相关权限。
- 应用日志和后端错误日志基础设施。

## 风险与约束

- 不能把用户权限、数据字典误删为旧系统管理。
- 如果旧接口仍被前端引用，必须先移除前端入口再删除接口。
- 如果数据库中存在历史表，删除前必须确认没有业务依赖和迁移风险。
- 文档清理必须保持 spec、plan、task 的职责边界。

## 实施阶段

1. 检索前端菜单、路由和页面中的旧系统管理引用。
2. 检索后端 Controller、Service、Mapper、模型和 SQL 中的旧系统管理引用。
3. 检索权限种子和权限常量中的旧系统管理引用。
4. 检索文档中的旧能力描述。
5. 删除或修正确认无业务价值的旧能力。
6. 执行编译、类型检查和文档引用检查。

## 验收标准

- 前端不再出现系统配置、服务器监控、JVM/CPU/内存/磁盘/网络监控页面。
- 后端不再暴露旧系统配置或服务器监控业务接口。
- 权限数据中不再出现旧系统管理菜单权限。
- 数据库结构中不再包含无业务价值的旧系统管理表。
- 文档不再将服务器监控、系统配置描述为 CRM 审计日志范围。

## 业务协同关系

- 依赖登录认证、权限变化、业务事件和敏感操作。
- 影响责任追溯、安全分析、异常排查和经营复盘。
- 权限控制覆盖审计查询、详情、导出和保留策略。
- 审计本身记录业务动作结果，不替业务模块做业务校验。
- 统计口径可读取审计异常，但不得用审计记录改写业务状态。

## 状态与事件方案

- 状态列表：记录成功、记录失败、待归档、已归档和保留期内。
- 触发事件：登录成功/失败、业务新增、编辑、审批、取消、作废、红冲、导出、删除和权限变更。
- 非法迁移：审计记录不得被业务接口物理删除。
- 异常策略：审计写入失败必须记录风险，不能悄悄吞掉关键业务操作。

## 数据与历史方案

- 必须保留操作者、业务对象、业务动作、结果、时间、IP、摘要和关联 ID。
- 审计日志在保留期内不可变更和删除。
- 审计查询和导出本身也应受权限和审计控制。
- 审计数据服务责任追溯和安全分析。
