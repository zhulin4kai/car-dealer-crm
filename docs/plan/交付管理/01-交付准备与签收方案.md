# 交付准备与签收方案

## 关联 Spec

- docs/spec/交付管理/00-业务范围与边界.md
- docs/spec/交付管理/01-流程规则与验收规格.md

## 背景

交付管理用于表达客户车辆交付前准备、资金条件确认、资料检查、客户签收和交付异常。交付不是库存出库的简单别名，也不是交易完成的唯一条件。

## 目标

- 建立独立交付记录，关联订单、客户、车辆、销售、库存和财务状态。
- 支持交付准备、资料检查、交付预约、客户签收和交付异常。
- 交付完成后驱动车辆出库和交易履约完成条件判断。
- 交付异常保留原因、责任人和处理结果。
- 交付后回访可触发跟进任务。

## 当前现状

- 当前没有独立 `DeliveryController`、`DeliveryService`、`TDelivery` 和前端 `modules/delivery`。
- 当前交易详情可观察交易、收款、发票等信息，但没有交付清单和签收记录。
- 当前库存车辆实例尚未独立落地，交付需要与库存管理计划协作。

## 设计方案

### 状态模型

交付状态建议覆盖待准备、准备中、待客户确认、待交付、交付中、已签收、已完成、交付异常、已取消。

状态迁移必须校验订单状态、资金条件、车辆准备状态、资料清单和操作者权限。

### 后端方案

- 新增交付模型、Mapper、Service、Controller 和 DTO。
- 交付准备检查车辆、资料、收款和发票必要条件。
- 客户签收记录签收时间、签收人、交付人、车辆和资料确认结果。
- 交付完成后调用库存出库或车辆状态变更，并通知交易履约判断完成条件。
- 异常处理必须记录原因和责任人。

### 前端方案

- 新增交付列表、详情、准备清单、预约和签收操作。
- 在交易详情展示交付状态和阻塞项。
- 交付异常需要醒目展示给销售主管和相关责任角色。

### 数据方案

- 新增交付记录表、交付清单或交付检查项表。
- 交付记录保存订单、客户、车辆、状态、负责人、计划时间、实际时间和签收信息。
- 交付完成记录不得物理删除。

## 风险与约束

- 资金未满足交付条件时不能普通完成交付。
- 交付完成必须与库存出库、交易履约保持一致。
- 交付资料不完整不能被前端绕过。
- 第一阶段不包含物流运输全流程和售后维修服务。

## 实施阶段

1. 定义交付数据结构、状态和检查项。
2. 实现交付创建、准备、预约、签收、完成、异常和取消。
3. 接入交易履约、库存车辆、收款退款和发票状态。
4. 新增前端交付列表、详情和操作入口。
5. 补充条件校验、状态迁移、异常、权限和前端测试。
6. 更新 API、后端、前端和集成文档。

## 验收标准

- 订单进入待交付后可以创建交付记录。
- 资金或资料条件不满足时不能完成交付。
- 客户签收后交付记录保留签收事实。
- 交付完成后车辆不再是可售库存。
- 交付异常能被主管识别并处理。

## 业务协同关系

- 依赖订单、交易履约、库存占用、资金条件、票据规则和权限数据范围。
- 影响交易完成、库存出库、客户回访、经营分析和审计日志。
- 权限控制覆盖交付创建、准备、预约、签收、异常、完成和导出。
- 审计记录覆盖资料确认、车辆确认、客户签收、异常和完成。
- 统计口径依赖待交付、交付完成、交付超期、异常和回访。

## 状态与事件方案

- 状态列表：待准备、准备中、待客户确认、待交付、交付中、已签收、已完成、交付异常和已取消。
- 触发事件：订单成立、库存占用、资料准备、客户预约、签收、交付完成和交付异常。
- 非法迁移：交付完成不能绕过资金和票据条件直接完成交易。
- 异常策略：资料不完整、车辆异常和客户拒签进入交付异常并保留原因。

## 数据与历史方案

- 必须保留准备清单、车辆确认、资料确认、签收人、交付人、签收时间和异常原因。
- 交付完成记录不能普通物理删除。
- 签收、异常和完成必须审计。
- 交付状态进入交易完成条件和交付效率指标。
