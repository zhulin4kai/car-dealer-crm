# 审计日志模块落地计划

## 目标

用“审计日志”替代已经下线的“系统管理”模块，为管理员提供登录记录和关键业务操作记录的查询、详情与导出能力。

本计划只描述实施顺序和验收边界。长期业务要求以 `docs/specs/审计日志/` 为准。

## 已确认决策

- 一级菜单名称为“审计日志”。
- 下设“登录记录”和“操作记录”两个页面。
- 登录记录第一版不做 IP 归属地解析，不调用外部 IP 定位服务。
- 操作记录不提供删除和清空功能。
- 审计数据禁止物理删除；后续如需控制数据规模，采用保留期限和归档策略。
- 当前系统配置、服务器硬件监控、JVM/CPU/内存/磁盘/网络监控不属于 CRM 产品范围，相关页面、接口、模型、权限和数据结构直接删除。
- 操作审计继续采用业务 Service 显式记录，不引入自动拦截全部请求的通用日志切面。

## 当前基础

- 项目已有 `t_operation_log`、审计动作枚举和统一审计记录入口。
- 用户、客户、线索、交易、字典、商品等部分关键写操作已经接入操作审计。
- 当前没有管理员可用的操作日志查询接口和页面。
- 当前没有独立、完整的登录记录持久化能力。

## 实施范围

### 登录记录

- 记录登录成功和登录失败。
- 支持按登录账号、用户姓名、登录结果、IP、时间范围查询。
- 展示账号、用户、结果、失败原因、IP、浏览器、操作系统和登录时间。
- 支持分页、稳定倒序和按当前筛选条件导出。
- 不记录密码、验证码、Token、Authorization、Cookie 或完整请求体。

### 操作记录

- 复用并补强现有业务操作审计链路。
- 支持按模块、动作、操作人、结果、业务对象和时间范围查询。
- 列表展示关键摘要，详情展示受控、脱敏的结构化审计内容。
- 支持分页、稳定倒序和按当前筛选条件导出。
- 不提供删除、批量删除和清空接口。

### 权限

- 新增审计日志菜单权限。
- 登录记录与操作记录分别拥有列表、详情和导出权限。
- 默认仅系统管理员拥有审计日志权限。
- 普通业务角色不得通过前端隐藏以外的方式绕过后端授权。

## 粗略实施顺序

1. 完成旧系统管理模块清理，确保路由、权限、接口、表和文档不再暴露旧能力。
2. 确定登录记录的业务数据结构、状态编码、失败原因分类和保留期限。
3. 在认证成功、认证失败和登出边界接入登录记录。
4. 为登录记录提供分页查询、详情和导出能力。
5. 为现有操作日志补齐查询条件、稳定排序、详情响应和导出能力。
6. 审查所有关键业务写操作，补齐缺失的操作审计动作。
7. 新增前端“审计日志”菜单、登录记录页面和操作记录页面。
8. 完成权限种子、测试数据、接口文档、前端文档和后端文档同步。
9. 完成单元、集成、权限、脱敏、分页、导出和前端交互验证。

## 主要风险

- 登录失败时可能无法取得有效用户 ID，必须允许账号文本和匿名操作者语义。
- 反向代理环境下客户端 IP 可能来自代理头，必须由可信代理配置决定，不能直接信任任意客户端头。
- 浏览器和操作系统来自 User-Agent，只能作为辅助信息，不能作为安全身份依据。
- 操作摘要如果由调用方自由拼接，容易泄露手机号、客户备注、支付信息或认证凭证。
- 导出可能造成敏感数据扩散，必须独立授权、限制时间范围并审计导出动作。
- 审计写入与业务事务语义不清会产生“业务回滚但日志显示成功”的错误事实。

## 验收

- 仓库不再包含系统管理页面、系统配置接口、系统监控接口、`t_system_info` 或对应权限。
- 管理员能够查询登录成功和失败记录，并按条件分页和导出。
- 管理员能够查询关键业务操作记录并查看详情。
- 普通业务用户访问审计能力时返回无权限。
- 审计数据没有删除或清空入口。
- 请求参数、返回摘要和导出内容不包含密码、Token、Authorization、Cookie、验证码和未脱敏敏感信息。
- 登录和操作记录均按发生时间倒序，并以主键作为同时间稳定排序补充条件。
- 业务事务回滚时不得保留成功操作记录。

## 结束条件

- `docs/specs/审计日志/` 中的必需项全部实现并通过验收。
- API、前端、后端和数据库文档与实际实现一致。
- 完整前后端检查通过，且没有遗留旧系统管理引用。
