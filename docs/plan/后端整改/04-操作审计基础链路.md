# 操作审计基础链路

## 目标

把现有操作日志表、Model 和 Mapper 补成可由业务 Service 显式调用的审计基础能力，不使用自动业务切面隐藏状态变化。

## 当前问题

位置：

- `dealer-server/src/main/java/com/autodealer/crm/model/TOperationLog.java`
- `dealer-server/src/main/java/com/autodealer/crm/mapper/TOperationLogMapper.java`
- `dealer-server/src/main/resources/mapper/TOperationLogMapper.xml`

当前只有表映射和 insert SQL，没有 Service/Recorder 调用链。用户、字典、交易、支付、退款、库存和导入导出等关键动作无法形成持久化审计。

## 文件所有权

允许修改：

- `TOperationLog.java`
- `TOperationLogMapper.java`
- `TOperationLogMapper.xml`
- 新增 `audit` 或等价明确目录下的审计事件、Recorder、Service 和实现
- 审计基础能力的单元与 Mapper 集成测试

禁止修改其他模块的 Controller、Service、Mapper、Schema、日志配置和 `CurrentUserProvider`。

## 修改方案

1. 定义稳定审计动作枚举或 code，至少覆盖：
   - 用户创建、编辑、状态变化
   - 线索导入、线索转客户、客户归属变化
   - 交易创建、结算、审批、重提、删除
   - 支付、退款、发票状态
   - 商品入库、库存调整、商品下架
   - 字典修改
   - 导出
2. 提供显式 `OperationAuditRecorder`，由模块 Service 在业务动作成功路径调用。
3. Recorder 从 `CurrentUserProvider` 获取操作者；业务模块只提交动作、对象类型、对象 ID、结果和必要摘要。
4. 审计字段使用结构化列或受控 JSON 摘要，不序列化完整请求、Model、密码、Token 和客户敏感信息。
5. 明确事务语义：
   - 成功审计与业务事务一致，业务回滚时不能留下成功记录。
   - 失败审计如需保留，使用独立明确入口和事务，不伪装为成功。
6. Mapper 写操作检查影响行数；审计插入失败按动作重要性抛出异常，不静默吞掉。
7. 查询接口只在确有后台需求时提供，并限制权限、时间范围和分页；本 Plan 不新增无需求 Controller。

## 提供给模块 Agent 的接口

模块 Agent 只能调用稳定 Recorder，不得直接依赖 `TOperationLogMapper`。接口应能表达：

- action code
- resource type
- resource ID
- result
- before/after 的受控摘要
- 可选 requestId/IP

## 测试

- 成功动作写入操作者、动作、资源、时间和结果。
- 业务事务回滚时成功审计同时回滚。
- 未登录系统动作能够使用明确 system actor，不伪造普通用户。
- 审计摘要不包含密码、JWT、Authorization、手机号全值和完整请求体。
- Mapper 分页和时间范围查询有稳定排序。

## 验收

- 操作日志不再是孤立 Model/Mapper。
- 业务模块有单一显式审计入口，基础层不依赖具体业务 Service。
- 不引入自动拦截所有方法的通用切面。
- 后续模块可以在不修改审计基础文件的情况下接入审计。
