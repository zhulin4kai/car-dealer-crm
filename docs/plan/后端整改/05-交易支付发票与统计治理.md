# 交易、支付、发票与统计治理

## 目标

补全交易请求契约，确保金额由服务端计算，并完成交易、审批、支付、退款、发票、库存联动的事务、并发、幂等和统计口径治理。

## 当前问题

### 创建请求缺少校验

位置：

- `dto/TranCreateRequest.java`
- `web/TranController.create`

`products`、customerId、productId、quantity、price 没有字段级约束。Controller 直接调用 `request.getProducts().stream()`，空列表会触发异常；创建和更新共用同一 DTO，日期仍由 Controller 手工解析字符串。

### 结算金额由客户端覆盖

位置：`web/TranController.settle`

接口接收 `Map<String,Object>` 中的 amount，只校验大于零后直接提交。客户端可以绕过产品合计和价格规则修改交易金额。

### 交易产品契约重复且无效

`query/TranProductQuery.java` 没有调用方，实际产品项藏在 `TranCreateRequest.ProductDetail`。审批、发票状态、批量删除等接口也仍使用无类型 Map。

### 统计口径错误

`StatisticManager` 把 distinct customer 数称为交易数。一个客户多笔交易时漏斗统计偏低，方法名、SQL 和前端文案不一致。

### 横向审计尚未闭环

需要对交易相关 Mapper XML 全量检查状态条件、锁、影响行数、N+1、分页和删除；对审批、重提、支付、退款、发票、库存恢复和批量删除验证事务与幂等。

## 修改方案

### 请求 DTO

1. 拆分 `CreateTranRequest`、`UpdateTranRequest`、`SettleTranRequest`、`ApproveTranRequest`、`UpdateInvoiceStatusRequest`、`BatchDeleteTranRequest`。
2. 产品项使用独立 `TranProductItemRequest`，至少校验 productId 必填、quantity 大于零。
3. 日期使用明确 Java 时间类型和 JSON 格式，不在 Controller 使用 `SimpleDateFormat`。
4. 删除未使用 `TranProductQuery`，禁止 Query 承担写命令。
5. Controller 使用 `@Valid`，只负责绑定、权限和调用 Service，不构造持久化 Model。

### 金额与产品快照

1. 创建和结算时从数据库锁定并读取商品，确认存在、在售和库存充足。
2. 产品单价和交易合计由服务端计算；客户端不得提交最终可信 amount。
3. 交易产品保存成交时价格快照，后续商品调价不得改写历史交易。
4. 如保留人工改价，必须使用独立字段、改价原因、操作者和审批规则，保留原始金额与调整后金额。
5. 所有金额使用 `BigDecimal`，明确 scale 和舍入规则。

### 状态、事务与幂等

1. 每个命令明确允许旧状态和目标状态，SQL 使用旧状态条件进行 CAS。
2. 创建、更新产品、结算、审批、重提、开票、收款、退款、删除分别建立 public 事务入口。
3. 支付流水号、发票号和退款请求使用数据库唯一约束或业务幂等键。
4. 重复审批、重复开票、重复收款、重复退款返回稳定冲突结果，不重复写历史和库存。
5. 退款恢复库存前验证原扣减和未恢复状态；退款写反向流水，不删除原支付。
6. 批量删除锁定稳定顺序，逐条检查状态和引用，保持全成功语义。
7. Mapper 写操作检查影响行数；`0` 行区分不存在、无权限和并发冲突。

### SQL 与性能

1. 审查全部交易 Mapper XML，禁止不受控 `${}`、无条件 update/delete 和空集合 foreach。
2. 列表使用一种分页方式和稳定排序，详情避免 N+1。
3. 交易、支付、审批、发票、历史的 join/resultMap 列别名唯一。
4. 移除未接入业务的 productionStatus 查询字段或补齐正式业务设计；不得保留半套状态模型。

### 统计口径

1. 明确漏斗显示“交易单数”还是“产生交易的客户数”。本次默认改为交易单数和成交交易单数。
2. Mapper 直接 count 交易记录；方法名、返回 DTO 和前端文案统一。
3. 时间范围、状态范围和数据权限使用同一统计口径。

### 权限与审计

- 每个交易读写接口核对 `@PreAuthorize` 和数据权限，详情、支付、发票、导出不得绕过。
- 在 Service 成功路径调用 04 提供的 Recorder，记录创建、结算、审批、重提、支付、退款、开票和删除。

## 测试

- 创建空产品、非法数量、商品不存在、商品下架、库存不足均失败且无写入。
- 客户端伪造金额不能改变服务端计算结果。
- 合法和非法状态迁移、CAS 失败、重复审批/支付/退款/开票测试。
- 任一步失败时交易、产品明细、库存、支付、发票、历史和审计全部保持一致。
- 批量删除包含不可删除交易时全部回滚。
- 同一客户多笔交易时统计按交易单数计算。
- 前端 DTO、状态映射、错误码、loading 和重复提交测试。

## 验收

- Controller 不再使用 Map 或共用 DTO 表达不同交易命令。
- 交易金额和库存完全由服务端事实决定。
- 支付、退款、审批和发票具备并发及重复请求保护。
- 交易相关 Mapper XML 全部有明确审计结论并有测试覆盖。
- 交易与统计前后端契约一致。
