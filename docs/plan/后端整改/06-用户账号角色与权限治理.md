# 用户账号、角色与权限治理

## 目标

拆分用户请求契约，补齐账号唯一性、密码策略、角色分配、账号保护和业务引用检查，并完成用户权限接口审计。

## 当前问题

位置：

- `query/UserQuery.java`
- `web/UserController.java`
- `service/impl/UserServiceImpl.java`
- `mapper/TUserMapper.java` 及 XML

新增和编辑共用 `UserQuery`，没有系统性 Bean Validation，客户端可提交账号启用、锁定等状态字段。Service 没有统一检查登录名、手机号、邮箱唯一性；删除仍是物理删除，只做数据范围判断，没有保护当前用户、内置管理员、最后一个管理员和仍负责业务数据的用户。

## 文件所有权

允许修改：

- 用户、角色、权限相关 Controller、Service、Model、Query、DTO、Mapper 和 XML
- 用户角色、角色权限关联逻辑
- 用户、角色和权限的直接测试
- `dealer-web/src/modules/user/`、用户页面和对应测试
- 用户前端页面消费现有 Permission Store；`stores/permission.store.ts` 归属 03，本任务只读

禁止修改公共错误码、Schema、SecurityConfig、CurrentUserProvider、审计基础文件和其他业务模块。

## 修改方案

### 请求契约

1. 拆分 `CreateUserRequest`、`UpdateUserRequest`、`ChangeUserStatusRequest`、`AssignUserRolesRequest` 和 `UserListQuery`。
2. 创建要求登录名、密码、姓名等必填，手机号和邮箱格式明确；编辑不默认覆盖密码。
3. 启用、禁用、锁定、解锁和角色分配使用独立命令及权限，不允许普通编辑接口修改安全状态。
4. Controller 使用 `@Valid`，Service 不接收无关查询字段。

### 唯一性与密码

1. 创建和编辑检查登录名、手机号、邮箱唯一性，编辑时排除当前用户。
2. 数据库唯一约束冲突转换为稳定业务错误，不能只依赖先查再写。
3. 定义最低密码策略，密码只存 BCrypt 哈希；响应、日志和审计不得包含密码字段。
4. 更新密码时清理现有 Redis 会话或明确要求重新登录，通过 03 的稳定认证接口完成。

### 用户生命周期

1. 默认使用禁用代替物理删除；历史业务操作者和负责人必须保留可解释身份。
2. 禁止当前登录用户删除/禁用自己，除非存在专门的自助注销业务。
3. 保护内置管理员和最后一个有效管理员，避免系统失去管理入口。
4. 禁用前检查该用户是否仍为活动、线索、客户、交易负责人；要求先转移归属或使用明确批量转移流程。
5. 批量操作先校验全部用户，任何一项失败则全部不修改。
6. 用户角色变更检查角色存在、权限边界和影响行数。

### 权限矩阵

- 列出用户、角色、权限的全部接口及 HTTP method、权限码、数据权限和敏感字段。
- 用户列表、详情、创建、编辑、状态、角色分配和导出必须有后端权限。
- 普通用户只能访问允许的数据范围，不能通过请求参数查看或修改其他账号。
- 前端按钮权限与后端权限码一致，但不作为安全边界。

### 审计

在 Service 成功路径记录用户创建、资料修改、密码重置、状态变化、角色分配和归属转移；摘要禁止包含密码和完整个人信息。

## 测试

- 创建空密码、弱密码、非法邮箱和重复登录名/手机号/邮箱失败。
- 编辑用户不提交密码时原哈希不变，提交合法密码时重新编码并使旧会话失效。
- 当前用户、内置管理员、最后一个管理员和仍有业务引用的用户不能被错误禁用。
- 状态变更和角色分配权限不足时返回 403。
- 批量操作出现受保护账号时全部不修改。
- 前端表单不暴露服务端审计字段，状态命令和错误码行为有测试。

## 验收

- `UserQuery` 不再同时承担列表、创建、编辑和状态命令。
- 用户生命周期不再依赖不受保护的物理删除。
- 唯一性同时有友好业务错误和数据库兜底。
- 所有用户权限接口都有明确权限和数据范围结论。
