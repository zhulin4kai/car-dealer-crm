## 优先级与执行边界

- 本方案是用户管理功能完成后的 **P2 内部解耦重构**，不作为 Task 21 宣告现有用户管理功能完成的阻塞条件。
- Task 25 开始前，Task 21 必须已经取得完整自动化、真实数据库、启动和手工验收证据，且用户管理范围内不得仍有未关闭的 P0/P1 正确性或安全问题。
- 若特征测试或重构过程发现新的 P0/P1，必须暂停本方案并回到对应功能 Task 修复；禁止借重构改变业务规则、放宽权限或吞掉并发冲突。
- 本方案只处理用户管理后端命令解耦及其直接测试、架构文档，不修改客户、交易、财务、库存等其他业务模块，也不建设 ERP、财务、人事、SSO 或 MFA 对接。

## 背景与当前证据

用户管理已经形成账号、凭证、会话、组织、汇报、角色、个人权限、生命周期、审计和恢复门禁等完整安全闭环，但写命令逐步集中在少数大型 Service 中。业务校验、Mapper 写入、图锁、CAS、历史、审计、会话失效、缓存失效和提交后回调混在同一方法或同一类中，使后续修改容易遗漏安全副作用，也使单元测试需要构造大量无关依赖。

本轮开始时的权威基线冻结在 HEAD `d0d91f7f7f9d96389df909d22798ce8cceff3237`。基线必须覆盖原有用户域全部 12 个实现文件，不能只统计准备拆分的十个文件，也不能把已经新增的切面或协调器倒算为“改造前代码”：

| 基线项 | 冻结快照 |
| --- | --- |
| 12 个既有实现 | 原十文件，加 `UserServiceImpl`、`AdminAccessRecoveryService` |
| 既有生产代码总行数 | 5,025 行 |
| 新架构生产代码 | 0 行；命令、AOP、协调器必须全部计入改造后当前总量 |
| 统计口径 | 物理行数，包含空行和注释；逐文件快照见 Task 25 |

当前共享工作区已经完成薄切面试点和轻量安全副作用协调，12 个既有实现为 4,546 行，新增架构为 162 行，合计 4,708 行，相对冻结基线真实净减少 317 行。构造依赖、字段注入、锁文本和高密度行继续报告，但不作为逼迫隐藏最后管理员、汇报环、状态机、锁序、CAS 或权威历史的硬门禁。

## 目标

- 用薄切面统一识别用户管理根命令并输出一次脱敏完成观测，不让切面决定业务授权、状态或并发结果。
- 不为当前单一试点保留无生产观察器的注册表和空拦截管线；只有出现两个以上真实独立观察器且抽取后仍净减少时才扩展观察协议。
- 只在能够减少重复且保持总代码净减少时，把禁止自改、授权委派、最后管理员、恢复账号用途、账号与员工状态、汇报环和负责人资格提取为显式领域策略。
- 用事务内轻量 `UserSecurityMutationCoordinator` 收敛访问或认证变化后的会话撤销与负责人候选缓存失效，不接管业务状态机、锁和历史。
- 复用现有提交后边界处理 Redis 与缓存派生状态；只有能证明必要且保持总量净减少时才增加新的事件抽象。
- 保持所有 HTTP、稳定错误码、数据库状态、锁序、CAS 冲突、审计内容和历史解释与重构前一致。

## 非目标

- 不把现有 Service 机械改名后继续保留同样的巨型构造器。
- 不用一个“万能切面”代替显式业务策略、事务或 Mapper 影响行数检查。
- 不把数据库权威历史、授权事实、生命周期事件或安全版本改为提交后异步写入。
- 不借机改变账号、员工、角色、权限、组织、会话或凭证业务规则。
- 不引入事件溯源、微服务拆分、消息中间件或新的框架依赖。
- 不为了减少行数压缩格式、合并语句、删除断言或降低可读性。

## 目标架构

### 薄切面

- `@UserManagementCommand` 只声明稳定命令编码，不声明角色名、权限码、锁名、状态迁移、审计内容或历史内容。
- `UserManagementCommandAspect` 只识别一次根调用，取得请求 ID、可信操作者、开始时间和根调用标识，在完成或失败时输出一条脱敏结构化日志，并执行原方法。
- 切面不得开启或提交业务事务，不得查询 Mapper，不得调用权限策略，不得获取图锁，不得执行 CAS，不得写审计或历史。
- 公开命令必须从 Spring 代理入口进入；禁止依赖类内自调用触发切面。嵌套命令不得重复记录第二个根命令。

### 根命令观测

- 每个外部根命令只输出一条完成观测，内容限于命令 code、请求 ID、可信操作者 ID、随机根调用标识、结果、耗时和失败类型；不记录异常消息、参数、返回值或授权明细。
- 观测不得把 `BusinessException` 改成成功，不得改写稳定 HTTP/code；嵌套标注方法直接执行原调用，不重复输出。
- 已删除没有生产观察器的 `Registry`、`Pipeline`、`Interceptor` 和上下文模型，避免启动期反射扫描与空管线；未来新增观察协议必须有真实消费者和净减量证据。

### 显式领域策略

- 自改和上下级边界由授权管理策略显式判断。
- 可委派权限、受保护角色、数据范围上限和安全管理员资格由授权委派策略显式判断。
- 最后一个可恢复普通管理员和固定恢复账号保护由管理员可用性策略显式判断。
- DIRECT/ACTING 时间区间环、负责人候选和组织范围由汇报图策略显式判断。
- 账号、员工、凭证和生命周期允许迁移由各自状态策略显式判断。
- 每个策略必须可以脱离 AOP 直接单测，并返回确定结果或抛出既有稳定业务错误码。

### 显式锁序与 CAS

- 每个写命令在进入领域写入前明确声明并获取所需锁序，例如 `AUTHORIZATION_MEMBERSHIP_GUARD → ORGANIZATION_HIERARCHY → REPORTING_GRAPH → AVAILABLE_ADMIN_GUARD → 账号行`。
- 可以由统一锁执行器按命令提交的有序锁计划执行，但锁计划必须在命令代码和测试中可见；禁止由切面按方法名猜锁。
- 状态迁移和版本更新继续使用命名明确的 Mapper CAS，并检查影响行数；CAS 预期版本、冲突错误码和写入结果不得由切面隐式推断。
- 最后管理员、汇报环和状态机校验必须在正确锁内重验，不能只在管线前置阶段查询一次。

### 事务内 UserSecurityMutationCoordinator

- 公开写命令继续拥有明确 `@Transactional(rollbackFor = Exception.class)` 边界。
- 协调器使用 `Propagation.MANDATORY`，只接受已经由命令完成业务校验、锁、CAS、版本与权威历史写入后的访问变化或认证变化通知。
- 协调器只统一调用 `UserSessionServiceImpl` 撤销会话，并调用 `OwnerCandidateCacheInvalidator` 安排负责人候选缓存失效；不得查询业务对象重新决定规则。
- 禁止为了形式完整增加通用 `SecurityMutationPlan`、反射分发或自由 Map；只有出现两个以上真实且稳定的额外维度，并且抽取后生产代码仍净减少时才允许引入强类型计划。
- 权威授权历史、组织任职历史、生命周期事件和操作审计继续由原命令在事务内同步保存，不能隐藏在切面或协调器，也不能降级为提交后事件。

### 提交后派生边界

- `OwnerCandidateCacheInvalidator` 继续作为负责人候选缓存的统一提交后边界。
- `UserSessionServiceImpl` 可以保留其内部专用 `TransactionSynchronization`，集中处理会话 Redis Key 的提交后清理和事务回滚补偿；脚本报告该调用但不为清零而强制引入事件框架。
- 数据库 `authVersion`、会话撤销事实、凭证状态和权威历史必须先在业务事务内生效，Redis 与缓存失败不能恢复旧权限或旧会话。
- Task 29 只有在现有集中边界无法满足真实故障恢复需求，且新增事件代码后当前生产总量仍严格小于 5,025 行时才实施；否则保留轻量混合方案。

## 拆分阶段

1. Task 25 固化结构基线、命令目录和行为特征测试。
2. Task 26 建立薄切面和一次根命令脱敏观测。
3. Task 27—32 作为候选优化逐项评估；每项开始前和完成后都必须运行 `--current`。
4. 只有删除的既有生产代码大于新增策略、计划、事件或处理器代码，且总量继续严格小于 5,025 行时，才实施对应 Task。
5. 若现有显式业务代码已经清楚，或抽取只会搬文件、增加构造层级、迫使隐藏锁序和状态机，则记录“不实施”依据并保留现状。
6. Task 33 删除旧重复编排并执行结构、行为和全链路收口验收。

执行顺序固定为 `Task 21 已完成 → Task 25 → Task 26 → 按净减少门禁评估 Task 27—32 → Task 33`。Task 27—32 不是必须制造代码的打勾任务，不满足净减少或显式性条件时不得实施；Task 25—33 不反向成为 Task 21 的完成前置。

## 量化验收

Task 25 冻结本轮开始 HEAD 的 12 个既有实现文件，Task 33 使用同一脚本把当前 12 文件与全部新增架构生产代码相加。`--baseline` 只输出冻结快照，不要求重构后的当前文件恢复成旧值；`--current` 和 `--compare-baseline` 执行净减少与调用边界门禁。

### 代码量

- 当前 12 个既有用户域实现与全部新增 command、AOP、policy、coordinator、event 生产代码合计必须严格小于冻结基线 5,025 行。
- 统计必须包含从 `UserServiceImpl` 实际删除的代码及新增架构代码，不能通过把代码搬到新目录或漏掉旧大类制造下降。
- 每个 Task 27—32 完成后必须继续满足严格小于 5,025；不能保持净减少的候选重构不得合入。
- 不为了减少行数压缩格式、合并语句、删除必要注释或降低可读性；长行、分号密度作为审查报告项。

### 构造依赖

- 脚本逐文件报告构造参数、协作者、配置参数和字段注入，用于识别新的巨型依赖对象。
- 构造依赖不是硬门禁；不能为了数字好看把 Mapper、策略和当前用户藏入 `ApplicationContext`、Service Locator 或无边界依赖包。
- 是否继续拆策略以业务边界清晰和生产代码净减少共同决定，不以固定依赖数量驱动拆分。

### 重复调用

- `.revokeAllForSecurityChange(` 的直接调用只允许 `UserSecurityMutationCoordinator → UserSessionServiceImpl`。
- `.invalidateAfterCommit(` 的直接调用只允许 `UserSecurityMutationCoordinator → OwnerCandidateCacheInvalidator`；协调器可以为访问变化和负责人资格变化保留多个明确入口。
- `UserSessionServiceImpl` 内部专用 `registerSynchronization` 作为集中会话缓存边界报告，不要求为了清零再增加事件层。
- `lockGraph(`/`lockMembership(` 数量只报告不设阈值；锁序必须继续在业务命令中可见，不得为了减少文本把锁序藏入切面或按方法名推断。
- 同一命令不得同时调用旧清理路径和协调器，测试必须验证每类安全副作用恰好一次。

### 行为等价

- Task 21 的全部自动化、真实数据库、启动和手工场景保持通过。
- 禁止自改、越级授权、最后管理员、四态门禁、DIRECT/ACTING 混合环、状态机、锁序、CAS、权威历史、Outbox 和会话失效的结果不变。
- 所有原 HTTP 状态、稳定业务 code、响应结构、OpenAPI 和前端调用保持不变；若发现必须改变契约的功能缺陷，必须退出本 P2 任务并另立功能修复。
- 对每个迁移命令提供重构前后数据库事实、审计、历史、派生副作用和异常的特征对照测试。

## 风险与约束

- AOP 顺序与事务代理顺序不明确时，宁可让切面只包根命令观测，也不得让切面控制事务提交。
- 提交后派生边界不能承担 fail-close 所需的权威写入；Redis 和缓存只是派生状态。
- 协调器不能演变成新的巨型 Service；它只处理命令显式通知的访问或认证变化，不查询业务对象来重新决定规则。
- 策略拆分不能产生循环依赖；策略只依赖必要查询端口或只读 Mapper，不调用命令 Service。
- 迁移按命令族分批完成，每批删除旧路径并运行特征测试，禁止长期双写或双清理。
- 本重构默认无 Schema 和 API 变化；若确需迁移或契约调整，必须暂停并拆成独立任务。

## 完成标准

- Task 25、26 和 Task 33 完成；Task 27—32 已逐项实施或记录因不能保持净减少/显式性而不实施的依据。
- 当前 12 个既有实现与全部新增架构生产代码总量严格小于 5,025 行。
- 代码图谱证明 revoke/invalidate 只经过允许的协调器边界，未形成新旧双清理。
- 切面源码不包含权限码、角色名、锁名、状态枚举、Mapper、审计动作或历史写入。
- 最后管理员、汇报环、状态机、锁序、CAS 和权威历史在命令、策略、协调器调用点及测试中均可直接定位。
- 完整回归证明外部行为等价，工作区无临时脚本、后台进程和无关修改。
