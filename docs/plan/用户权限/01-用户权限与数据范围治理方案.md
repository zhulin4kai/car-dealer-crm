# 用户权限与数据范围治理方案

## 关联 Spec

- docs/spec/用户权限/00-业务范围与边界.md
- docs/spec/用户权限/01-流程规则与验收规格.md

## 背景

用户权限决定谁可以访问账号、线索、客户、商机、订单、收款、退款、发票、交付和审计等能力。前端隐藏只改善体验，后端权限和数据范围才是安全边界。

## 目标

- 建立账号、个人资料、员工档案相互关联但职责独立的人员模型。
- 建立公司、门店、部门、团队、岗位和直属管理者组成的最小组织模型。
- 用户账号状态清楚，禁用或锁定账号不能继续操作业务。
- 角色权限矩阵、用户直接授权和拒绝、权限来源及数据范围稳定可追溯。
- 任何用户不能修改自己的授权，管理者只能在管理关系和可委派上限内调整下属授权。
- 登录用户可以维护个人资料、密码和本人会话，但不能借个人中心改变授权信息。
- 导入、导出、审批、收款、退款、开票、交付和审计查看具备独立权限。
- 人员调岗或离职时业务数据可以交接。
- 账号、组织、任职、角色、权限和会话安全变化能够被审计追溯。

## 改造前基线

以下内容保留为本轮用户管理改造启动前的事实基线，用于解释方案动机，不代表当前工作树仍缺少这些能力。

- 后端已有 `UserController`、`UserServiceImpl`、`TUser`、`TRole`、`TPermission`、`PermissionCodes`。
- 后端已有 `DataScopeAspect` 和 `CurrentUserProvider`。
- 前端已有 `dealer-web/src/modules/user/`、用户管理页和权限存储。
- 当前账号与员工信息混合在扁平用户对象中，没有组织、岗位和直属管理者模型。
- 当前角色和权限来自固定初始化数据，只能整体替换用户角色，没有角色管理、角色权限矩阵和用户直接授权能力。
- 当前角色分配允许管理员修改本人，非管理员访问规则主要允许本人，无法表达“管理者只能管理下属”。
- 当前数据范围主要表达管理员全局和普通用户本人，岗位团队、离职交接和跨模块权限粒度需要继续治理。
- 当前用户页未使用已有锁定、解锁、角色分配和密码重置接口，也没有个人中心、组织、角色和权限管理页面。
- 当前 Redis 会话按用户保存单个 Token，不能提供会话列表和选择性撤销；部分登录、OpenAPI 和技术文档契约存在漂移。

## 设计方案

### 账号模型

账号、登录标识、个人资料和员工档案分开表达：账号保存认证与安全状态，登录标识事实永久保存标识归属和当前/退休状态，个人资料保存用户可自行维护的信息，员工档案保存员工编号、任职状态、主要组织、主要岗位和直属管理者。账号管理状态只使用待激活、启用、禁用；锁定原因与期限、账号到期时间、凭证到期时间和首次改密要求作为独立安全属性。任职状态使用待入职、在职、待交接、已离职，返聘作为重新建立任职的业务动作。业务人员离职或调岗不通过删除账号表达。

现有用户标识保持兼容，新增员工档案与原用户一对一关联。现有用户通过兼容迁移生成员工档案，无法推断的组织、岗位和管理者进入待补录状态，不伪造组织事实。

### 组织与任职模型

- 组织单元使用层级结构表达公司、门店、部门和团队，维护稳定编码、名称、类型、上级、负责人、排序和启停状态。
- 岗位目录独立于权限角色，维护岗位编码、名称、层级、说明和启停状态。
- 员工档案维护主要组织、主要岗位、直属管理者和任职状态；兼岗或代理关系作为有明确有效期的补充任职记录。
- 最高级管理者使用唯一根公司的 `leader_employee_id` 识别；普通人员四条写路径共用以目标主要组织为锚点的管理者候选校验器。首次初始化用显式引导命令在同一事务创建首个普通管理员、员工、主任职、根公司负责人、初始角色和邀请。
- DIRECT 继续由任职命令维护唯一直属管理者；ACTING 使用独立的有限期多关系替换命令和页面，不复用单值字段。两类关系共用按时间区间交集遍历的汇报图环校验，账号禁用、人工锁定、安全到期和自动锁按 `REPORTING_GRAPH → AVAILABLE_ADMIN_GUARD → 账号行` 顺序串行，关系写在图锁内重验候选资格。
- 组织树固定合法父子类型矩阵并保护唯一根公司；岗位或组织存在当前、未来任职或待交接责任时拒绝停用。
- 管理关系校验禁止本人管理、循环汇报和无效管理者，组织停用前检查下级节点和在职员工。
- 调岗、离职、返聘通过命名明确的业务动作产生不可覆盖的任职历史。

### 权限模型

权限编码使用稳定英文 code，区分菜单、查看、新增、编辑、删除或关闭、导入、导出、分配、转派、审批、收款、退款、开票、交付、审计查看。

- 权限目录补充业务模块、说明、敏感级别、是否可委派和启停状态；权限编码由代码与初始化数据共同约束，普通管理员不能创建无实现支撑的权限码。
- 角色补充说明、受保护标记、授权级别、默认数据范围、启停状态和并发版本。
- 角色权限矩阵维护角色与权限关系，保存前展示影响用户数量和权限差异；受保护角色仅允许符合条件的安全管理员维护。
- 角色区分全局共享和组织级适用范围；全局共享角色仅由安全管理员维护，组织级角色的维护者必须覆盖全部适用组织和受影响用户。
- 普通管理者不能通过修改已分配给同级、上级或范围外人员的共享角色矩阵间接改变其权限。
- 用户直接权限使用 `GRANT` 和 `DENY` 表达个人增加与明确拒绝，并允许设置有效期；有效权限按照角色权限和个人增加取并集后应用个人拒绝。
- 运行时授权事实来自每项角色权限或个人增加及其对应范围；角色默认范围只作为新配置的默认值或上限，不作为第二套运行时范围。
- `GRANT` 必须携带范围，`DENY` 关闭整个权限且不携带可合并范围；多个来源只合并同一权限动作各自合法的范围。
- 权限明细返回角色来源、个人来源、有效状态、可编辑性和不可编辑原因，前端不自行推断。
- 数据范围至少表达本人、直属下属、完整汇报树、主要组织、组织及下级组织、指定组织和全局；功能权限和数据范围同时满足才允许访问。
- 稳定范围 code 统一为 `SELF`、`DIRECT_REPORTS`、`REPORTING_TREE`、`PRIMARY_ORG`、`ORG_TREE`、`CUSTOM_ORGS`、`GLOBAL`。

### 安全委派模型

- 授权命令首先拒绝操作者和目标用户相同的请求，管理员也不例外。
- 非受保护管理者必须是目标用户的直接或间接管理者，并处于允许管理的组织范围内。
- 可分配角色不得高于操作者授权级别；可增加权限必须是操作者当前拥有、允许委派且不超过目标数据范围的权限。
- 普通管理者不得修改同级、上级、范围外人员、受保护系统账号和受保护管理员角色。
- 最高级管理员由另一名符合条件的安全管理员处理；系统始终保留至少一个可用的受保护管理入口。
- 受保护恢复管理员权限固定且不进入常规授权入口；普通最高级管理员可以由另一名符合条件的安全管理员维护，但同样禁止本人修改。
- 安全管理员资格按账号、任职、受保护治理权限和全局范围事实实时计算，不以 `admin` 角色名直接放行。常规治理要求操作者授权级别严格高于目标；两个最高级管理员之间只允许独立增加或撤销受保护管理员角色，禁止在同一命令夹带其他角色或个人权限变化。
- 角色、权限和数据范围修改使用版本校验防止并发覆盖，成功后撤销目标用户旧会话并记录修改前后值。
- 最后管理员保护使用行锁、CAS 或等价数据库并发控制，两个并发降级或禁用请求最多一个成功；受保护恢复管理员与普通可变管理员分别计数。
- 初始部署不自动生成带默认密码的普通管理员；受保护恢复管理员只用于引导创建首个具备真实任职的普通管理员。门禁按 `UNINITIALIZED → PENDING_FIRST_CHANGE → READY` 推进，普通管理员完成激活后仍须完成首次改密并验证至少一个当前员工联系方式，才开放日常业务。
- 认证过滤层实时判断四态：`UNINITIALIZED` 只放行引导白名单；`PENDING_FIRST_CHANGE` 只放行普通管理员完成激活、首次改密、本人资料与当前员工联系方式验证所需入口；`READY` 至少保留一个具备当前已验证员工恢复渠道的普通管理员，并对恢复账号永久关闭常规治理和日常业务；已初始化但普通管理员全部失效时进入 `DEGRADED`，只允许固定恢复账号调用无目标选择的窄恢复命令，不重新执行根负责人 bootstrap。固定恢复账号在四态中始终保留本人非授权资料与独立专用联系方式入口，但该专用渠道不参与普通管理员就绪计数。
- `DEGRADED` 恢复在授权成员、组织、汇报和可用管理员固定锁序内运行；服务端只选择仍保留受保护管理员角色与有效任职的 HUMAN 账号，清理安全失效、撤销旧会话并排队恢复凭证，不允许借机新增角色、权限或任职。
- 增加默认关闭的独立 break-glass 恢复命令，以部署环境外部密钥换取一次性恢复凭证；命令只面向固定受保护账号执行密码轮换、清锁和清除到期，提升安全版本、撤销会话并写高危审计，不复用常规用户管理授权。
- 新建库与 Task 22 升级统一把固定恢复账号的仓库密码替换为不可登录的随机占位摘要并置为人工锁定、强制改密；系统不提供默认恢复密码，部署方必须配置外部恢复密钥和安全投递通道后走首次 break-glass。

### 个人中心与凭证模型

- 个人中心只允许当前用户维护姓名、联系方式、头像等白名单资料，并查看只读的账号、组织、岗位、管理者和有效权限来源；固定恢复账号使用独立资料来源维护本人专用联系方式，但不得由此获得常规治理、日常业务或授权修改能力。
- 本人改密校验当前密码；管理员重置下属密码使用独立命令，要求目标用户下次登录改密，任何接口都不返回明文密码。
- 邀请、激活和重置凭证使用单次且有时限的凭据；连续登录失败达到阈值后自动锁定。
- 首次激活原子推进账号与员工状态；普通密码重置保持账号启禁用和任职状态不变。禁用、离职、登录账号变化、安全到期和密码成功变化统一撤销尚未消费的凭证，凭证消费与安全命令通过行锁及 CAS 串行。
- 手机和邮箱验证使用独立单次凭证与验证状态；联系方式变化清除对应验证并撤销旧凭证，找回密码只向当前已验证联系方式投递。
- HUMAN 账号的通知联系方式只以 `t_employee` 当前值为权威，签发和 Worker 均不得回退到 `t_user` 兼容投影；固定 SYSTEM 恢复账号才使用其专用账号联系方式。
- 凭证交付使用事务 Outbox：业务事务原子写由 `messageId`、用途和随机 nonce 计算的 64 字符不可逆预交付承诺与待投递事实并返回 HTTP 202/`QUEUED`，不生成原始凭证，绝不在事务或全局图锁内调用 Webhook。Worker 提交后使用独立 `CREDENTIAL_DERIVATION_KEY` 确定性派生原始凭证，再使用消费端共用的凭证 HMAC 摘要器，以 CAS 把预交付承诺绑定为实际 `token_digest` 后投递；Webhook 使用 `Idempotency-Key=messageId`。
- 凭证摘要绑定允许“预交付承诺首次绑定”与“已绑定同一摘要重试”两种状态；其他摘要、凭证失效或绑定竞争失败均 fail-close。Worker 崩溃或租约恢复后必须重新派生同一原始凭证和摘要，不得覆盖不匹配的持久化事实。
- Outbox 以 CAS 认领、租约超时、指数退避和最大次数控制重试；成功或永久失败清除 nonce，永久失败同时撤销未消费凭证。投递审计只记录 messageId、用途、次数和结果代码，不记录原始凭证、nonce 或完整联系方式。
- 普通账号自动锁定同步提升安全版本并撤销全部会话；恢复账号和唯一普通管理员不执行会关闭最后管理入口的普通自动锁，而记录高危阻断审计并进入独立恢复策略。
- 登录标识通过永久归属表和共享数据库锁串行创建或切换，退休标识不能转给其他员工；登录成功更新最后登录时间。登录账号、密码、状态、安全到期时间或授权变化后撤销受影响会话。

### 会话模型

- JWT 增加不可猜测的会话标识，Redis 按用户和会话标识保存有效会话，数据库或等价持久记录保存会话元数据和撤销事实。
- 每次受保护请求继续校验 JWT、Redis、数据库账号状态和实时有效权限，不把权限全集放入 JWT。
- 数据库账号安全版本或授权版本是旧 Token 立即失效的权威事实；权限、密码和状态变化在数据库事务内原子提升版本。
- Redis 删除是会话清理和加速手段，失败必须告警和重试，但不能使旧 Token 重新有效，也不能伪造数据库与 Redis 原子回滚。
- 用户可以查询和撤销自己的会话；授权管理者可以查询和撤销管理范围内下属的会话。
- 当前会话、其他会话和全部其他会话使用明确命令区分；撤销失败不得返回成功。
- 会话同时具有绝对有效期和空闲有效期，`rememberMe` 只影响明确配置的绝对期限；系统限制最大并发会话数量并采用确定的超限策略。
- 最近活动时间按受控间隔更新，避免每次请求写数据库；过期和撤销记录按安全保留期限清理，设备、IP 和客户端信息只保存脱敏摘要。

### 后端方案

- 账号邀请、受管账号资料与状态、个人中心、授权、组织任职和人员生命周期分别由受控的新 Service 承担写操作；`UserServiceImpl` 中缺少版本、原因、管理边界或完整事务契约的旧写入口一律 fail-close。
- 在认证过滤层增加管理员初始化就绪与受保护账号用途门禁，使用稳定错误码返回未完成初始化或恢复账号越界，不依赖前端菜单隐藏。
- 新增组织、岗位、角色权限和授权服务，避免继续把全部人员与权限逻辑堆入 `UserServiceImpl`。
- 新增统一的目标用户管理边界与授权上限判断组件，供账号状态、组织任职、角色、权限、数据范围和会话管理复用。
- `PermissionCodes` 与前端 `dealer-web/src/shared/constants/permissions.ts` 保持一致。
- 有效权限查询合并启用角色、启用权限、有效个人增加和个人拒绝，并返回可追溯来源。
- 数据范围在 Mapper 查询条件中体现，不允许查全部后过滤；本次先提供统一组织范围上下文，其他业务模块按各自主关闭 Task 接入。
- 离职或调岗交接只直接转移市场活动、线索、客户、商机、跟进任务和试驾六域当前责任；报价和交易随客户归属做派生核验，待审批队列和沟通历史不改写。

### 前端方案

- 保留 `/dashboard/user` 作为用户管理入口，拆分列表筛选、员工表单、状态、密码、角色权限和交接组件。
- 新增个人中心，左下角用户区域提供个人资料、修改密码和退出入口；折叠头像不再直接触发退出。
- 新增组织与岗位页面、角色权限页面，并为用户详情提供组织任职、角色权限来源、会话和变更历史视图。
- 用户管理页展示员工编号、组织、岗位、直属管理者、任职状态、账号状态、角色、数据范围和业务引用风险。
- 列表和详情同时展示账号/凭证到期、首次改密、自动/人工锁定原因与期限、有效数据范围摘要和六个直接责任域引用风险；敏感字段继续按管理关系脱敏。
- 后端为目标用户返回可执行动作和不可执行原因，前端不根据角色名推断能否管理目标用户。
- 用户权限采用继承、允许、拒绝三态表达，清楚区分角色来源与个人调整，不能用一个无来源二态开关误导管理员。
- 权限按钮只做展示控制，接口错误按稳定 code 处理。
- 离职交接需要明确原负责人、新负责人和交接范围。

### 数据方案

- 增加组织单元、岗位、员工档案、补充任职、任职历史、用户直接权限、授权历史和会话记录。
- 扩展角色的受保护属性、授权级别、默认数据范围和版本；扩展权限的模块、敏感级别和可委派属性。
- 现有账号、角色、权限及关联 ID 保持兼容，通过新增、回填、切换方式迁移，不直接删除旧字段或历史关系。
- 本项目当前不引入新的迁移框架，使用 `dealer-server/src/main/resources/migration/manifest.tsv` 声明顺序、依赖、checksum、恢复策略和对象探针，并且只允许通过 `scripts/database/user-management-migrate.sh` 显式执行；升级步骤、备份、失败恢复和 baseline 策略记录到 `docs/integration.md`。
- 统一迁移执行器必须持有数据库命名锁，在账本中记录 `RUNNING/SUCCEEDED/FAILED`、执行次数和最后完成步骤；每个业务 DDL 或回填过程必须在过程内部再次校验执行器上下文，直接运行 SQL 即使使用 `mysql --force` 也不得改变业务 Schema。
- 完整初始化库通过逐项对象探针建立 baseline，旧库按 manifest 执行并支持从步骤账本恢复；Task 21 必须分别在受支持的 MySQL 和 MariaDB 上验证旧库升级、故障恢复、重复执行、baseline 和不可变触发器。
- 永久登录标识和恢复账号不可变触发器必须由统一迁移执行器在有效上下文内安装；`mysql --force` 直接执行任一迁移不得绕过上下文留下部分对象。若数据库对过程内触发器 DDL 有差异，迁移实现必须使用经过两种数据库实测的受控替代方案，不能靠契约测试删除整段触发器后放行。
- 迁移脚本只执行新增、兼容回填和可重复核验，不在旧代码仍写入期间直接收紧非空；Task 21 必须在现有数据库快照上实际验证升级，而不只验证新库初始化。
- 现有用户无法推断真实组织时可使用明确标记的迁移占位组织或待补录状态；占位组织不参与管理范围、负责人资格和业务数据范围计算。
- 关系表新增字段先允许兼容默认值或可空，旧接口保持单写兼容；新服务切换并完成回填核验后才能收紧约束。
- 账号、角色、组织、岗位和授权写入使用版本或状态条件，影响行数不符合预期时返回并发冲突。
- 权限种子使用权限 code 建立关系，不依赖漂移数字 ID。
- 角色权限、个人授权、组织任职和账号状态变更必须保存不可变历史并写业务审计。
- 生命周期事件与授权历史同为不可覆盖事实，生产数据库必须用拒绝 `UPDATE/DELETE` 的触发器保护，应用层不得提供物理删除入口。
- 禁用或锁定用户时清理 Redis 会话。

### API 与契约方案

- 现有用户列表和详情路径在兼容期保留，新增接口统一使用复数资源路径和用途明确的命令子资源。
- 个人中心、组织岗位、角色权限矩阵、用户有效权限、会话和历史均定义稳定请求与响应对象。
- 路径中的目标用户 ID 不再要求在请求体重复提交；可信操作者、权限范围和组织范围只从服务端上下文获得。
- 新增禁止自改、超出管理范围、授权超限、不可委派、最后管理员、循环汇报和版本冲突等稳定错误码。
- OpenAPI、后端校验、前端 TypeScript 类型和错误码映射在每个实施任务中同步更新。

### 审计方案

- 账号、个人资料、员工档案、组织、岗位、直属管理者、角色矩阵、用户授权、数据范围、密码重置和会话撤销分别使用可识别审计动作。
- 授权与任职历史保存操作者、目标对象、修改前后值、原因、有效期、结果和发生时间，不再用“用户状态变更”代替所有动作。
- 调岗、完成离职和返聘关闭或新建任职、直属与代理汇报事实时，必须在同一事务写入组织历史权威投影；组织页面与用户时间线不得各自维护互不一致的历史来源。
- 批量操作记录批次摘要和逐项结果，不在循环中输出高频日志。
- 邀请、激活、联系方式验证、登录标识切换、自动锁及管理员保护阻断、初始化门禁和 break-glass 使用独立脱敏动作；批量授权同时保存每个目标的成功事实或在事务失败时不保存任何成功摘要。
- 凭证限流、无效/过期/已消费/用途错误凭证、错误恢复密钥以及初始化门禁拒绝使用独立安全失败审计事务；调用方业务事务回滚时拒绝事实仍需保留。资源只保存不可逆摘要、失败分类和请求来源摘要，不保存原始凭证、恢复密钥或完整联系方式。

### 公开凭证与会话并发方案

- 忘记密码、联系方式验证、邀请重签和 break-glass 申请按账号、联系方式摘要和来源地址进行分层限流；保持公开响应同形，服务端记录脱敏拒绝原因与告警指标。
- 重发冷却在凭证签发事务中先锁目标用户，再查询该用途族最近一次签发事实；冷却依据包含已撤销和投递失败记录，不能只检查当前活动凭证。`SELF_RESET/ADMIN_RESET` 共享密码重置用途族，并发申请最多提交一条凭证摘要和一条 Outbox。
- 联系验证签发、资料变化和验证消费统一使用账号后员工的加锁顺序，并把验证绑定到签发时资料版本，消除旧联系方式验证新值的竞争窗口。
- 会话创建按用户级锁串行执行“读取有效会话—撤销超限最旧会话—插入新会话—提升 revision”；Redis 删除与索引刷新只在事务提交后执行。

## 风险与约束

- 不能通过删除用户处理离职。
- 不能用前端路由守卫替代后端授权。
- 管理员绕过和本人访问必须有明确规则，禁止散落硬编码角色名。
- 不能给普通业务角色默认授予敏感导出、退款、开票、交付和审计权限。
- 不能先开放角色或权限开关，再补禁止自改、上下级关系和授权上限；安全委派规则是前置条件。
- 不能以“销售经理”等角色名代替真实管理关系，岗位、管理关系和权限角色必须分离。
- 不能在权限变化后只刷新前端缓存，后端实时鉴权和会话撤销才是安全边界。
- 不能把个人资料编辑接口扩展成可提交组织、角色、权限或账号状态的万能更新接口。
- 不能物理删除账号、授权历史、任职历史和安全审计。
- 不在本方案中建设 ERP、财务、人事外接、薪酬绩效、完整 SSO 或 MFA 平台。
- 本 Plan 主关闭账号、组织、任职、角色、个人权限、数据范围计算、用户工作台、负责人资格、个人中心和会话；客户、交易、财务、库存、统计等业务 Mapper 的范围接入由各业务 Task 负责。

## 验收标准

- 禁用或锁定账号不能继续访问受保护接口。
- 用户能够维护自己的个人资料、密码和会话，但不能修改自己的授权或任职信息。
- 管理者只能管理下属，不能管理本人、同级、上级和范围外用户，也不能授予自己没有或不可委派的权限。
- 公司、门店、部门、团队、岗位和直属管理者能够被维护，循环汇报、无归属在职员工和带人员组织停用被拒绝。
- 角色权限矩阵和用户继承、允许、拒绝权限能够维护并展示来源，临时授权到期自动失效。
- 同一权限的每个角色或个人来源及其对应数据范围能够逐项展示；`CUSTOM_ORGS` 保存明确组织集合并校验操作者覆盖范围、停用和到期。
- 普通业务人员只能看到职责范围内的数据。
- 导出、审批、收款、退款、开票、交付和审计查看权限独立控制。
- 人员调岗或离职时业务数据可以交接。
- 登录账号、密码、状态或授权变化后旧会话失效，用户可以查询和撤销自己的会话。
- 账号、组织、任职、角色、权限、数据范围和会话变化产生可追溯审计记录。
- 初始化门禁、联系方式验证、自动锁保护和 break-glass 场景通过；恢复账号始终被日常业务门禁拒绝。
- 普通人员始终有目标组织内合法直属管理者，唯一根公司负责人例外；首次普通管理员创建失败不留下部分事实。
- 后端完整测试、前端检查和启动后的手工验收全部通过，OpenAPI 与实际请求响应一致。

## 核心闭环补充

- 当前阶段先建立支撑用户管理的最小组织、岗位和汇报关系，再让数据范围依赖真实组织关系，不能继续用固定角色猜测团队。
- 销售顾问默认处理本人负责数据；销售经理处理其真实管理团队或明确授权范围；财务处理其所属门店或明确授权范围内进入财务阶段的业务；受保护管理员按授权处理全局。
- 交易审批必须拒绝自建自批。
- 最后一个管理员保护必须覆盖禁用、锁定和角色分配。
- 负责人候选只允许启用、未锁定且具备销售职责的账号。

## 业务协同关系

- 依赖组织职责、账号状态、角色、岗位和业务授权规则。
- 影响所有业务模块的数据范围、动作授权、审批边界和审计记录。
- 权限控制本身覆盖用户管理、角色分配、权限变更、会话失效和数据交接。
- 审计记录覆盖账号状态、角色权限、数据范围和关键授权变化。
- 统计口径依赖用户责任归属和数据范围。

## 状态与事件方案

- 状态列表：账号管理状态为待激活、启用、禁用；安全属性为锁定、账号到期、凭证到期、首次改密；任职状态为待入职、在职、待交接、已离职。
- 触发事件：账号邀请与激活、启禁用、锁定、角色分配、权限变更、授权到期、调岗、离职、返聘和交接；返聘是动作而不是持久状态。
- 非法迁移：不得自改授权、不得越级授权、不得形成循环汇报、不得移除最后一个管理员、不得以前端隐藏替代后端授权。
- 异常策略：禁用、锁定、改密或授权变化撤销会话，离职必须先处理业务交接，并发版本不一致返回冲突。

## 数据与历史方案

- 必须保留账号状态、组织任职、角色历史、权限变更、数据交接、会话撤销和管理员保护事实。
- 用户删除不能破坏历史业务负责人解释。
- 账号状态、组织岗位、管理关系、角色分配、权限和数据范围变化必须审计。
- 权限数据决定统计和明细下钻范围。
