# 用户权限与数据范围治理方案

## 关联 Spec

- docs/spec/用户权限/00-业务范围与边界.md
- docs/spec/用户权限/01-流程规则与验收规格.md

## 背景

用户权限决定谁可以访问账号、线索、客户、商机、订单、收款、退款、发票、交付和审计等能力。前端隐藏只改善体验，后端权限和数据范围才是安全边界。

## 目标

- 用户账号状态清楚，禁用或锁定账号不能继续操作业务。
- 角色、权限和数据范围稳定可追溯。
- 导入、导出、审批、收款、退款、开票、交付和审计查看具备独立权限。
- 人员调岗或离职时业务数据可以交接。
- 权限变化能够被审计追溯。

## 当前现状

- 后端已有 `UserController`、`UserServiceImpl`、`TUser`、`TRole`、`TPermission`、`PermissionCodes`。
- 后端已有 `DataScopeAspect` 和 `CurrentUserProvider`。
- 前端已有 `dealer-web/src/modules/user/`、用户管理页和权限存储。
- 当前数据范围、岗位团队、离职交接和跨模块权限粒度需要继续治理。

## 设计方案

### 账号模型

账号状态应覆盖启用、禁用、锁定、账号过期、凭证过期等安全状态。业务人员离职或调岗不应只通过删除账号表达。

### 权限模型

权限编码使用稳定英文 code，区分菜单、查看、新增、编辑、删除或关闭、导入、导出、分配、转派、审批、收款、退款、开票、交付、审计查看。

### 后端方案

- 在 `UserServiceImpl` 中保持账号创建、更新、启禁用、锁定解锁、角色分配和密码变更的业务规则。
- `PermissionCodes` 与前端 `permissions.ts` 保持一致。
- 数据范围必须在 Mapper 查询条件中体现，不允许查全部后过滤。
- 离职或调岗交接需要批量转移线索、客户、商机和待办责任人。

### 前端方案

- 用户管理页展示账号状态、角色、数据范围和业务引用风险。
- 权限按钮只做展示控制，接口错误按稳定 code 处理。
- 离职交接需要明确原负责人、新负责人和交接范围。

### 数据方案

- 权限种子使用权限 code 建立关系，不依赖漂移数字 ID。
- 角色权限变更和账号状态变更必须审计。
- 禁用或锁定用户时清理 Redis 会话。

## 风险与约束

- 不能通过删除用户处理离职。
- 不能用前端路由守卫替代后端授权。
- 管理员绕过和本人访问必须有明确规则，禁止散落硬编码角色名。
- 不能给普通业务角色默认授予敏感导出、退款、开票、交付和审计权限。

## 实施阶段

1. 梳理用户、角色、权限、数据范围和前端权限常量。
2. 补齐权限编码、角色种子和一致性测试。
3. 补齐数据范围和离职交接能力。
4. 调整前端用户管理、角色分配和权限展示。
5. 补充账号状态、权限边界、数据范围、会话失效和审计测试。
6. 更新 API、后端、前端和集成文档。

## 验收标准

- 禁用或锁定账号不能继续访问受保护接口。
- 普通业务人员只能看到职责范围内的数据。
- 导出、审批、收款、退款、开票、交付和审计查看权限独立控制。
- 人员调岗或离职时业务数据可以交接。
- 权限变化产生可追溯审计记录。

## 核心闭环补充

- 当前阶段先基于固定角色建立数据范围，不等待组织架构模块。
- 销售顾问默认处理本人负责数据；销售经理处理团队或审批范围内待审批交易；财务处理进入财务阶段的交易、发票、收款和退款；管理员处理全局。
- 交易审批必须拒绝自建自批。
- 最后一个管理员保护必须覆盖禁用、锁定和角色分配。
- 负责人候选只允许启用、未锁定且具备销售职责的账号。

## 业务协同关系

- 依赖组织职责、账号状态、角色、岗位和业务授权规则。
- 影响所有业务模块的数据范围、动作授权、审批边界和审计记录。
- 权限控制本身覆盖用户管理、角色分配、权限变更、会话失效和数据交接。
- 审计记录覆盖账号状态、角色权限、数据范围和关键授权变化。
- 统计口径依赖用户责任归属和数据范围。

## 状态与事件方案

- 状态列表：启用、禁用、锁定、过期、待交接和已离职。
- 触发事件：账号创建、启禁用、锁定、角色分配、权限变更、调岗、离职和交接。
- 非法迁移：不得移除最后一个管理员，不得以前端隐藏替代后端授权。
- 异常策略：禁用或锁定账号清理会话，离职必须先处理业务交接。

## 数据与历史方案

- 必须保留账号状态、角色历史、权限变更、数据交接和管理员保护事实。
- 用户删除不能破坏历史业务负责人解释。
- 账号状态、角色分配、权限和数据范围变化必须审计。
- 权限数据决定统计和明细下钻范围。
