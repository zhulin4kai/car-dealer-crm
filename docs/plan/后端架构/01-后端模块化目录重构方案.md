# 后端模块化目录重构方案

## 关联依据

- `docs/spec/业务闭环/00-业务范围与边界.md`
- 各业务域 `docs/spec/`、`docs/plan/` 与 `docs/task/`。
- `docs/rule/01-开发流程与架构边界.md`
- `docs/rule/02-Java后端代码风格.md`
- `docs/rule/04-数据库与MyBatis规范.md`
- `docs/rule/07-测试编写执行与验收规范.md`
- `docs/rule/10-文档与Spec治理规范.md`

## 背景与现状

当前后端仍以 `web/service/mapper/model/dto/query/result` 等技术层作为主要目录。随着业务扩展，同一业务域的 Controller、用例、持久化对象、查询和返回类型分散在多个大目录中，跨域依赖也只能通过类名辨认。

本方案开始时的基线为：

- 615 个生产 Java 文件、133 个测试 Java 文件。
- 36 个 Controller。
- 77 个 Mapper 接口，其中 44 个显式标注 `@Mapper`。
- 75 个 Mapper XML。
- `TranServiceImpl`、`OrganizationServiceImpl`、`AiConversationServiceImpl` 等大型实现同时承担多个用例族。
- AI 代码已经采用业务模块优先目录，说明单体应用内按模块组织可行。

## 目标

- 保留单个 Spring Boot 应用、单个 Maven 工程和现有部署方式，建设模块化单体。
- 代码目录与现有业务 Spec、Plan、Task 的领域边界对齐。
- 跨模块只依赖公开应用接口，禁止直接依赖其他模块的 Controller、内部实现、Mapper 和持久化对象。
- 第一阶段只迁移包和资源位置，保持 HTTP、稳定错误码、JSON、数据库、事务、权限和缓存行为不变。
- 第二阶段拆分大型 Service，消除跨模块持久化依赖和隐式业务边界。

## 非目标

- 不拆微服务，不引入远程调用、消息中间件或分布式事务。
- 不改数据库 Schema、业务状态机、权限规则和外部 API。
- 不在目录迁移批次同时重写业务逻辑、批量格式化或更换框架。
- 不为了制造分层而创建空目录、透传 Service、万能 Manager 或通用事件总线。
- 不保留旧包入口、转发类、重复 Spring Bean 或新旧双写路径。

子域只创建实际需要的层级：

```text
<subdomain>
├── web
├── application
│   ├── api
│   │   ├── dto/query/model
│   │   └── port
│   └── internal
├── domain
└── persistence
    ├── mapper
    └── model
```

- `web` 只处理 HTTP、校验、权限入口和统一响应。
- `application.api` 保存跨模块允许使用的用例接口、Command、Query、Result、公开数据模型和数据端口。
- `application.internal` 保存用例实现和显式业务编排。
- `domain` 只保存真实领域状态、值对象、枚举和策略，不强制每个模块存在。
- `persistence` 保存 MyBatis Mapper 和仅限模块内部的持久化对象，不对其他模块开放；需要跨模块传递的模型必须直接归属 `application.api.model`，不得在 persistence 中保留副本。

## 依赖规则

- 模块内依赖方向为 `web -> application.api -> application.internal/domain/persistence`。
- 跨模块只能引用目标模块的 `application.api`。
- 禁止跨模块引用 `web`、`application.internal`、`domain`、`persistence.mapper`、`persistence.model`。
- 跨模块数据访问通过目标模块的 `application.api.port`；MyBatis Mapper 在模块内部实现该端口，调用方不得直接注入 Mapper。
- `shared` 不得依赖 `modules`，并且只保留稳定通用契约；具体权限码、Redis Key 和业务常量归还所属模块。
- `bootstrap` 负责 Spring、Security、MyBatis 和基础设施装配，不承载业务状态迁移。
- 跨模块只读报表可以由分析模块持有专用读模型 SQL，但不得复用其他模块的写 Mapper。
- 跨模块写流程由发起用例显式调用目标模块应用接口，不通过 AOP、反射或事件总线隐藏事务边界。

## 实施阶段

1. 冻结文件、接口、Bean、Mapper、XML 和测试基线，建立架构检查。
2. 用经营分析模块验证目录、包扫描、测试镜像和跨模块依赖约束。
3. 统一 Mapper 标注、扫描与递归 XML 资源布局，整理 `bootstrap/shared`。
4. 按 `audit/dictionary/identity/commerce/sales/fulfillment/ai` 顺序迁移，每批同时移动生产、测试和 XML。
5. 拆分交易、组织、账号、线索和 AI 会话等大型实现，删除跨模块 Mapper/Model 依赖。
6. 删除旧横向业务包，清零临时依赖清单，更新长期规则和 `docs/backend.md`。

## 迁移约束

- 每批迁移前确认工作区，记录本批文件所有权，不能覆盖无关修改。
- 包迁移与职责拆分分开验证；发现功能缺陷时退出重构批次，按对应业务 Task 修复。
- Mapper 接口、XML namespace、resultMap 类型和测试必须在同一批次更新。
- 不以类行数作为唯一拆分门禁；锁序、事务、CAS、状态机、审计和提交后副作用必须继续显式可定位。
- 每批完成后旧路径不得残留同名生产类或测试类。

## 验收标准

- HTTP method/path、权限注解、稳定 code、JSON 和 OpenAPI 无非预期变化。
- Spring Context 中没有丢失或重复的 Controller、Service 和 Mapper Bean。
- 所有 Mapper XML 被递归发现，namespace 与类型引用有效。
- 模块边界检查阻止新增跨模块内部依赖；最终临时依赖清单为空。
- 旧 `web/service/mapper/model/dto/query/result` 业务包清空。
- 定向测试、完整 `./mvnw test`、静态路径检查和 `git diff --check` 通过。
- `docs/backend.md` 和架构规则只描述实际落地结构，不把未完成阶段写成现状。
