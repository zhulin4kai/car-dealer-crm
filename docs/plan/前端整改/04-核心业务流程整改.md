# 核心业务流程整改

## FE-005 促销结算价只存在于前端，后端仍按原价结算

- 严重级别：P1
- 性质：已确认缺陷
- 文件和准确行号：`dealer-web/src/pages/dashboard/tran/[id].vue:66-96,323-352,643-679`；`dealer-web/src/modules/tran/api/tran-api.ts:26-28`；`dealer-server/src/main/java/com/autodealer/crm/service/impl/TranServiceImpl.java:183-225`
- 当前行为：用户选择促销后，前端计算并在确认框显示折后价；`settleTran` 只发送交易 ID。后端从交易商品快照重新计算 `price × quantity`，没有促销 ID或折扣参数，最终持久化原价。
- 正确行为：促销适用性和最终金额必须由后端基于稳定促销 ID、商品、有效期和状态计算；前端只展示后端预览结果，并在结算后展示持久化金额。
- 触发方式：待报价交易选择任意有效促销，确认折后金额后点击结算。
- 业务影响：用户确认的价格与交易、发票、应收金额不一致，属于直接财务风险。
- 修复建议：设计服务端 quote/settlement DTO，保存促销引用、原价、优惠额、最终价和规则快照；结算命令带版本防并发，前端禁止自行成为金额事实来源。
- 可能受影响的后端接口或其他页面：`POST /api/tran/{id}/settlement-preview`、`PUT /api/tran/{id}/settle`、交易详情、审批、发票、收款、统计、促销管理。

## FE-006 发票 PENDING 到 ISSUED/VOID 的前端流程不可达

- 严重级别：P1
- 性质：已确认缺陷
- 文件和准确行号：`dealer-web/src/pages/dashboard/tran/invoice/[id].vue:55-156,255-258,348-390`；`dealer-server/src/main/java/com/autodealer/crm/service/impl/TranServiceImpl.java:428-468`；`dealer-server/src/main/java/com/autodealer/crm/web/TranController.java:175-181`
- 当前行为：创建发票后后端状态为 `PENDING`。前端模板没有渲染发票列表或“标记已开具/作废”按钮，虽然 script 中有未被模板调用的 `markAsIssued`。禁用提交只检查 `ISSUED`，所以 PENDING 时仍可重复点击创建，后端因已有发票返回 409。
- 正确行为：已有任意发票时停止显示创建表单；PENDING 状态显示受权限和状态控制的开具/作废操作，ISSUED/VOID 显示终态；所有命令有二次确认和刷新。
- 触发方式：对 APPROVED 交易创建一次发票，随后留在当前页继续操作。
- 业务影响：发票状态长期停在待开具，重复操作持续失败；交易已进入 PAYMENT，但发票业务状态不完整。
- 修复建议：以服务端发票列表为事实源重构页面状态机；接入 `updateInvoiceStatus` 的可达按钮；创建后导航/刷新到发票详情态。
- 可能受影响的后端接口或其他页面：`POST /api/tran/invoice`、`PUT /api/tran/invoice/{invoiceId}/status`、交易详情和支付入口。

## FE-010 审批拒绝后的重新提交能力缺失

- 严重级别：P2
- 性质：已确认缺陷
- 文件和准确行号：`dealer-web/src/pages/dashboard/tran/index.vue:87-114`；`dealer-web/src/modules/tran/api/tran-api.ts:1-74`；`dealer-server/src/main/java/com/autodealer/crm/web/TranController.java:230-237`
- 当前行为：后端把拒绝交易置为 LOST，并提供 `PUT /api/tran/resubmit/{id}`；前端 API 没有该函数，列表对 LOST 没有编辑或重新提交操作。
- 正确行为：具备 `tran:resubmit` 的用户应能查看拒绝原因、修订允许字段并重新提交；操作项必须与状态机一致。
- 触发方式：主管拒绝一笔 PENDING 交易，销售返回交易列表。
- 业务影响：业务对象在前端永久停滞，只能依赖外部调用或删除重建，破坏历史连续性。
- 修复建议：补模块 API、状态按钮和拒绝原因展示；明确重新提交前允许编辑范围及库存恢复/再次扣减提示。
- 可能受影响的后端接口或其他页面：`PUT /api/tran/resubmit/{id}`、审批信息、库存、交易历史。

## FE-015 系统开关状态编码跨层不一致

- 严重级别：P2
- 性质：高风险疑点
- 文件和准确行号：`dealer-web/src/pages/dashboard/system.vue:226-229,438-446,974-986`；`dealer-server/src/main/java/com/autodealer/crm/dto/ToggleSystemStatusRequest.java:6-13`；`dealer-server/src/main/resources/CarDealerCRM.sql:738`
- 当前行为：前端只把字符串 `'true'` 视为开启并提交 `'true'/'false'`；DTO 注释声明合法值为 `Y/N`；数据库默认值又是小写 `y`。
- 正确行为：定义单一稳定枚举并在数据库、DTO、响应和前端映射一致；前端 Switch 只在边界转换一次。
- 触发方式：加载数据库默认状态的系统记录，或切换任意状态。
- 业务影响：开关回显可能与数据库相反，提交后形成更多混合编码，依赖该配置的业务判断不可靠。
- 修复建议：先由后端确定权威编码并直接固化到 `CarDealerCRM.sql` 和初始化数据，再更新 Response/Request DTO 和前端类型；不要在前端兼容无限多字符串。
- 可能受影响的后端接口或其他页面：`GET /api/system/list`、`POST/PUT /api/system*`、系统运行开关消费者。
- 缺少证据：当前服务业务是否把 `true/false/y/Y` 都视为等价未在现有 Service 中体现，因此具体运行结果需结合配置消费者确认。

## 其他状态机核对

- 收款按钮只在 PAYMENT 显示，退款按钮条件与后端“COMPLETED、单笔、全额”规则基本一致。
- 删除单笔按钮只在 QUOTATION 显示，与后端 `requireDeletable` 一致；批量删除按钮没有预先过滤状态，但后端会整体拒绝并回滚，属于反馈可改进而非越权。
- 审批按钮只在 PENDING 显示，后端还通过原子状态更新防止并发重复审批。
- 当前前端没有独立交付流程页面；业务 Spec 要求收款交付闭环，但后端也没有明确交付命令，本轮无法把它归因成单纯前端缺陷，应在业务能力计划中跨端设计。

## Agent 执行说明

### FE-005：促销结算必须先固定后端权威契约

该问题不能仅靠前端修改完成。当前 `settleTran(id)` 没有促销参数，后端 `settleTransaction(Integer tranId)` 只对商品快照执行 `price × quantity`。在后端提供权威计价前，前端唯一安全的短期修复是移除或禁用促销结算预览，结算确认只显示服务端当前可证明的原价。

#### 推荐跨端契约

```text
POST /api/tran/{id}/settlement-preview
request:  { promotionId?: string, expectedVersion?: string }
response: { tranId, promotionId, originalAmount, discountAmount,
            finalAmount, currency, promotionSnapshot, version, expiresAt }

PUT /api/tran/{id}/settle
request:  { promotionId?: string, previewVersion: string, expectedTranVersion: string }
response: { tranId, stage, originalAmount, discountAmount, finalAmount,
            appliedPromotion, version }
```

路径和字段最终以 API 设计为准，但必须满足：预览与结算使用同一后端规则；结算重新验证商品、促销状态、适用产品、时间、交易阶段和版本；持久化原价、优惠额、最终金额与促销规则快照。

#### 前端具体函数改法

1. 删除 `originalTotalAmount/finalAmount` 中的权威促销算法，尤其是 `discount > 1` 时除以 100 这种猜测。
2. 新增 `fetchSettlementPreview(tranId, request)` 和精确 `SettlementPreview` 类型。`onPromotionChange()` 只更新选中 ID并请求预览；预览期间禁用结算。
3. `handleSettle()` 必须要求当前 preview 与当前 `tranId/promotionId/transactionVersion` 一致，再把 preview token/version 提交给结算 API。
4. 结算成功后使用响应或重新拉取交易详情，展示持久化金额；状态冲突、促销过期、库存变化时清除旧 preview 并要求重新预览。
5. 金额只按服务端十进制值展示。不得把前端 `number.toFixed()` 的结果回传作为最终金额。

#### 隐藏问题

- 当前促销列表只筛 `status === '进行中'`，没有验证促销是否属于交易中的商品、是否在有效期、是否已耗尽或可叠加。
- 促销 ID Select 可能出现数字/字符串不相等，导致 `find` 找不到；FE-014 必须统一 ID 表示。
- 预览后商品、数量、促销或交易阶段可能被他人修改，必须有版本或一次性预览 token，不能相信几分钟前的预览。
- 结算影响交易金额、审批、发票、收款、统计与审计，任何一处仍读原始 `money`/旧字段都会形成双事实源。

#### 回归断言

- 同一输入的预览金额与结算持久化金额一致。
- 促销过期、不适用、版本冲突和重复结算均不进入成功态，并清除旧预览。
- 前端请求不包含自算 finalAmount；UI 不能在无预览时声称折后价。

### FE-006：以发票列表驱动可达状态机

#### 页面派生状态

- `currentInvoice = invoiceList[0] ?? null`，但如果后端理论上只允许一张而实际返回多张，页面必须显示数据异常，不能任取一张。
- `canCreate = no invoice && tran.stage === APPROVED`。
- `canIssue = invoice.status === PENDING`。
- `canVoid = invoice.status === PENDING || invoice.status === ISSUED`，最终以当前后端 `validTransition` 为准。
- `isTerminal = invoice.status === VOID` 或后端定义的其他终态。

#### 具体函数改法

1. 模板先渲染已有发票摘要和状态操作，再按 `canCreate` 渲染创建表单。已有 PENDING、ISSUED 或 VOID 时都不得继续显示可提交的创建表单。
2. 当前 `hasInvoiceIssued` 改为 `hasAnyInvoice` 与精确状态派生，避免 PENDING 时重复创建。
3. 把 `markAsIssued(invoice)` 接到 PENDING 行的按钮，并实现 `voidInvoice(invoice)`；两个动作都二次确认、维护各自 command loading、成功后 `await Promise.all([fetchInvoiceList(), fetchTranDetail()])`。
4. `updateInvoiceStatus` 的参数从 `string` 收紧为 `InvoiceStatusCommand`，只允许后端可接受的目标状态。
5. 创建金额默认值来自交易持久化金额，但用户是否可编辑应由业务规则决定。后端已校验发票金额与交易金额时，前端应只读展示，不提供会必然失败的任意金额输入。
6. 路由 ID 不使用 `parseInt` 静默截断，使用严格解析器。ID 策略与 FE-014 保持一致。

#### 隐藏问题

- `createTranInvoice` 会把交易从 APPROVED 原子迁移到 PAYMENT；发票 PENDING 已经意味着交易阶段变化，页面必须刷新交易，不能只刷新发票。
- 作废发票可能把交易从 PAYMENT 退回 APPROVED；这会影响支付入口和其他已打开页面，成功后必须重新读取服务端状态。
- 创建成功后刷新失败时不能提示“创建失败”；重复提交会得到 409，且可能让用户误判数据未保存。
- 页面进入权限是 `tran:invoice`，但详情、商品、发票列表接口当前要求 `tran:view`。权限依赖按 `02` 的矩阵解决。
- 后端唯一性/CAS 仍必须保留；前端 `hasAnyInvoice` 只能改善体验，不能防并发双开。

#### 回归断言

- APPROVED 无发票可创建；创建后 PENDING 表单消失并显示开具/作废。
- PENDING -> ISSUED、PENDING/ISSUED -> VOID 的按钮、确认、loading、刷新正确。
- 多发票异常、409、状态冲突、刷新失败有明确反馈，不允许重复创建。

### FE-010：把拒绝后的修订与重新提交分成两个动作

当前后端 `resubmitTransaction(id)` 会将 LOST 原子改回 QUOTATION、重新扣减库存并删除旧审批记录。前端不能把“重新提交”理解成单纯切换状态。

#### 具体函数改法

1. 在 `tran-api.ts` 增加 `resubmitTran(id: EntityId): Promise<...>`，返回类型按后端真实响应定义。
2. 在交易列表和详情为 `stage === LOST` 且有 `tran:resubmit` 的用户显示“重新提交”。同时展示最近审批拒绝原因；如果当前列表响应没有该信息，按详情/审批信息接口加载。
3. 明确修订流程：若 LOST 交易允许修改商品、数量或交付日期，先进入编辑并保存，再执行 resubmit；若当前后端 update 只允许 QUOTATION，则需要后端先提供“拒绝后修订”契约，前端不能绕过状态校验。
4. `handleResubmit(row)` 的确认文案必须说明会重新占用库存。提交期间锁定该行；成功后刷新列表/详情和库存相关事实。
5. 库存不足、状态冲突、无权限分别提示；失败时保留 LOST，不做乐观状态更新。

#### 隐藏问题

- 后端重提会 `deductTransactionStock`，说明审批拒绝流程很可能已恢复库存。重复点击或错误重试涉及库存一致性，必须依赖后端事务/CAS。
- 后端会删除旧审批记录。若业务需要保留拒绝历史，删除与审计要求存在冲突；前端上线入口前应确认历史是否另存于交易历史/审计表。
- 当前交易列表对 LOST 不显示编辑按钮。只增加 resubmit 会把未经修订的原交易再次提交，可能重复被拒。
- resubmit 成功后的阶段是 QUOTATION，不是直接 PENDING；用户是否还要再次点击结算必须在文案和流程中明确。

#### 回归断言

- 只有 LOST + `tran:resubmit` 显示入口；其他阶段不显示且后端仍拒绝。
- 库存不足、状态冲突不改变 UI 阶段；成功后按服务端返回显示 QUOTATION。
- 拒绝原因在重提前可见，历史保留策略有明确证据。

### FE-015：先统一状态 code，再修 Switch

#### 决策和落地顺序

1. 后端确定唯一 code，建议沿用 DTO 注释的 `Y/N`，但必须由项目决策确认。
2. `CarDealerCRM.sql` 直接把 `isopen` 定义为 `CHAR(1) NOT NULL DEFAULT 'Y'`，并限制为 `Y/N`；初始化数据只写权威 code。
3. `ToggleSystemStatusRequest` 加枚举/正则校验，Service/Mapper 只接受权威 code；响应也只返回同一 code。
4. 前端定义 `SystemOpenStatus = 'Y' | 'N'` 和 `isSystemOpen(status)`；Switch 只在一个适配函数中做 boolean/code 转换。

#### 前端具体函数改法

1. `system.types.ts` 收紧 `isopen`；`toggleSystemStatus(id, status)` 不再接收 `boolean | string`。
2. 模板不要在点击时先直接改 `row.isopen`。`handleStatusChange(row, checked)` 保存旧值，进入行级 loading，命令成功后提交新值；失败恢复旧值。
3. 避免用户在请求期间连续切换；若要支持最后意图获胜，需要串行命令队列，不能并发写状态。
4. 创建表单和编辑表单都使用同一 code 适配，不能一处 `true/false`、一处 `Y/N`。

#### 隐藏问题

- 只在前端同时兼容四种字符串会延长脏数据寿命，无法确认下游消费者看到什么。
- 当前后端 DTO 只有 `@NotBlank`，注释写 Y/N 但不会拒绝 `true`；必须补服务端验证，否则前端修复不构成契约。
- 乐观改 `row.isopen` 后失败回滚可能覆盖另一次成功响应；请求期间禁用最简单可靠。

#### 回归断言

- 初始化数据库和接口响应只出现权威 code；非法 code 后端拒绝。
- Switch 正确回显，成功提交正确 code，失败恢复且无并发乱序。
