## FE-017 后端错误被统一文案吞掉

- 严重级别：P3
- 性质：体验改进
- 文件和准确行号：`dealer-web/src/pages/dashboard/product/promotion.vue:227-236,264-277`；`dealer-web/src/pages/dashboard/product/stock.vue:374-384`；`dealer-web/src/pages/dashboard/tran/invoice/[id].vue:369-389`
- 当前行为：catch 多数只显示“操作失败”，不区分 403、409、501、状态冲突或字段校验；有些地方直接把 `error.message` 拼到 UI，策略不一致。
- 正确行为：共享错误适配器按稳定 code 映射可理解提示；表单字段错误回填字段，状态冲突提示刷新，403 提示权限，未知错误使用通用文案。
- 触发方式：提交缺 productId 的促销、重复发票、无权限库存操作或后端状态冲突。
- 业务影响：用户无法修正输入，容易反复提交；开发者也难以从用户反馈定位真实问题。
- 修复建议：定义 `presentApiError(error, context)` 和字段错误契约；禁止页面自行匹配中文 msg。
- 可能受影响的后端接口或其他页面：全部命令接口和导入接口。

## 最需要补充的回归测试（本轮不编写）

1. 客户导出：断言 Token 位于 Header、URL 无 Token、Blob 文件名正确、401 会清理会话。
2. 用户新增/编辑：断言 JSON DTO 字段精确，编辑不带密码/状态，后端字段错误可回填。
3. 库存页：mock 非空 PageResult 后断言表格和分类选项渲染；筛选、重置和补货后刷新。
4. 促销表单：productId 必填，时间顺序和折扣范围校验，编辑完整回显。
5. 交易结算：促销预览来自后端，确认价与结算结果一致；并发状态冲突后刷新。
6. 发票：APPROVED→PENDING→ISSUED/VOID 全状态流，已有发票不可重复创建。
7. 权限守卫：无首页权限、有其他菜单、无菜单、直接 URL、401、403、权限加载失败。
8. 会话失效：多个并发 512 只触发一次清理和一次跳转；退出清理 Store 与两种 storage。
9. 分页：搜索回到第一页，删除最后一条回到合法页，旧请求不得覆盖新请求。
10. 时间与金额：GMT+8 日期不回退；BigDecimal 显示/提交保持两位精度；Long ID 不转 JS number。

## Agent 执行说明

### FE-017：建立错误呈现策略，不建立万能中文 message 匹配器

#### 共享能力边界

建议新增 `shared/api/present-api-error.ts`，但它只做协议到展示模型的转换，不直接弹 Toast：

```text
toErrorPresentation(error, context)
  -> { kind, message, fieldErrors?, shouldRefresh, isSessionInvalid }
```

页面根据 context 决定 Toast、字段错误、页内错误态或刷新。稳定分支只依据 HTTP 状态和业务 code；服务端 `msg` 可作为安全兜底文本，但不得作为程序判断条件。

#### 最小分类

- `validation`：字段错误映射到 vee-validate `setFieldError`，保留表单。
- `forbidden`：保留会话，提示无权；路由级可转 403。
- `conflict`：状态/版本冲突，提示数据已变化并刷新服务端事实。
- `session-invalid`：交给 FE-013，全局完成清理；页面不重复 Toast。
- `network/server/unknown`：通用安全文案和重试入口，不展示堆栈、Axios 配置或原始响应。

#### 具体改法

1. 扩展 `ApiError` 只保存必要协议事实，例如 `code/httpStatus/details`；不要让所有页面解析 `raw` 的任意形状。
2. 先迁移 FE-001 至 FE-013 触达页面。每个 catch 明确：是否消费、是否重新抛出、是否刷新、是否保留输入。
3. 写操作拆分“命令失败”和“命令成功后的刷新失败”；成功事实不可被后续刷新异常覆盖。
4. 取消类异常使用统一类型守卫，不能比较 `error.message !== 'cancel'`。

#### 隐藏问题

- `error.message` 可能来自浏览器、Axios 或服务端，不适合直接展示，且可能包含内部 URL。
- 一个全局 Toast 拦截器会让页面无法把字段错误定位到输入框，也可能与页面 catch 重复提示。
- 未知 code 必须可观察但不泄露；开发日志可记录 code/correlationId，禁止打印客户、Token、完整请求体。

#### 回归断言

- 相同稳定 code 在不同页面得到一致分类；字段错误能落到对应字段。
- session invalid 只有全局反馈；403 不登出；冲突触发一次刷新。
- 未知错误不展示堆栈和内部对象。

### FE-018：按触达范围清理迁移残留

#### 必须删除的模式

- `if (true)` 和 Promise 成功后的不可达 `else`。
- 页面直接 `doGet/doPost/doPut/doDelete`；改为领域模块 API。
- 未类型化 `ref([])`、`ref({})`、参数隐式 any、`Record<string, unknown>` 再强转业务字段。
- 生产 `console.log` 和包含响应对象的日志。
- 无职责组件，例如只透传 slot 且没有语义、样式或契约的 `ActivityFormDialog`。

#### 执行原则

1. 只清理当前 FE 修复触达文件；其余残留登记后分批处理，不做全仓机械替换。
2. 删除恒真分支后保留真实失败来源：Promise reject、ApiError、Schema 失败和状态冲突。
3. 领域 API 返回值是业务数据，不恢复 AxiosResponse 形状来兼容旧页面。
4. 空壳组件若已被多处 import，先用图谱追踪调用方；确认没有公共职责后删除并同步测试。

#### 隐藏问题

- `if (true)` 删除后经常暴露局部变量仅为旧 Axios envelope 服务，需一并简化，不能留下未使用 `res`。
- 直接 API 调用迁移到模块层时可能改变请求体或返回类型，必须用契约测试保护，不是单纯移动代码。
- 清掉 console 后仍需要故障可观察性时，应使用项目统一日志/遥测策略，不能完全吞错。

#### 测试实现要求

1. 回归测试先能在旧实现下失败，再实现修复。测试名称表达原缺陷条件。
2. 页面测试使用 Testing Library 从用户可见行为查询，不断言内部 ref 或函数调用细节；API mock 返回已经解包的业务类型。
3. 请求体精确性使用 `toEqual` 或字段集合断言，不能只用 `objectContaining` 放过多余敏感字段。
4. 异步竞态使用可控 deferred Promise，禁止 sleep。
5. 路由/权限测试必须初始化真实 Pinia Store 状态并验证实际导航结果与接口调用次数。
6. 所有 timer、object URL、mock server 和 Pinia 在 `afterEach` 清理，防止测试串扰。

#### 每项最低验证

- 页面或模块定向 Vitest。
- `npm run typecheck`。
- 修改 `http-client`、路由守卫、共享类型或共享 composable 时运行完整 `npm run check`。
- 跨端金额、库存、发票和状态迁移还需后端定向测试/集成测试；不能仅以前端 mock 证明正确。
