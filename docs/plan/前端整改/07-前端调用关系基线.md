# 前端调用关系基线

本文件记录本轮通过 codebase-memory-mcp 和源码交叉核对得到的结构基线，供整改时做影响面检查，不代替 API 文档。

## 应用主链路

```text
main.ts
  -> Pinia
  -> v-has-permission
  -> Vue Router
      -> guards.ts
          -> auth.store.ts -> user-api.ts -> /api/login/info
          -> permission.store.ts -> permission-storage.ts
      -> DashboardLayout.vue
          -> menuPermissionList
          -> pages/dashboard/**
              -> modules/*/api/*-api.ts
                  -> shared/api/http-client.ts
                      -> dealer-server Controller
```

认证事实来源当前分为：Token storage、Auth Store 内存状态、Permission storage、Permission Store 内存菜单/功能码和后端 Redis/数据库会话。整改时必须保持后端会话为权威，前端只缓存并可完整清理。

## Store 与权限调用关系

- `auth.store.ts`：负责 Token、rememberMe、当前用户、登录/退出和会话恢复；调用 `user-api.ts`。
- `permission.store.ts`：负责功能权限码和菜单树；既可从 sessionStorage 恢复功能码，也可通过 `/api/login/info` 重新加载完整权限。
- `guards.ts`：进入受限路由前恢复 Token/权限；菜单树为空时拉取当前用户；按 `route.meta.permission` 判定页面权限。
- `has-permission.ts`：按 Permission Store 功能码移除无权 DOM，只用于体验控制，不承担后端授权。
- `DashboardLayout.vue`：直接消费后端 `menuPermissionList` 生成菜单；退出时同时清理 Auth Store 和 Permission Store。

## 整改影响面规则

- 修改页面按钮权限时，同时核对路由 meta、`PERMISSIONS`、后端 `PermissionCodes`、Controller `@PreAuthorize` 和初始化角色权限。
- 修改 API 请求时，同时核对模块类型、Controller 方法、Request DTO、Response DTO/PageInfo 和错误码。
- 修改交易操作时，同时核对 `TranStage`、`TranServiceImpl` 原子状态迁移、库存、发票、支付和交易历史。
- 修改退出或失效处理时，同时清理 Token、currentUser、permissionList、menuPermissionList 和持久化缓存。

## 关键状态流

### 统一请求响应

```text
页面 handleXxx
  -> modules/<domain>/api 函数
  -> httpClient.request
  -> axiosClient request interceptor 写 Authorization
  -> 后端 R<ApiEnvelope>
  -> httpClient 只解包一次 envelope.data
  -> 页面直接消费业务 DTO

失败：
Axios/Envelope error
  -> ApiError
  -> session invalid? 全局单飞清理 : 页面错误呈现策略
```

文件下载是例外：成功响应是 Blob 而非 `R`；失败响应仍可能是 Blob 包裹的 JSON envelope。因此下载函数必须有独立适配，但认证和 session-invalid 处理不能分叉。

### 列表查询

```text
criteria/page change
  -> buildQuery(不可变快照)
  -> latest request run
  -> commit list + total + pageSize
  -> normalize page if required
  -> clear selection on query identity change
```

`loading`、`error` 和 `selection` 都属于同一列表状态机。任何只更新 `list` 而不更新 `total/page/selection` 的快捷路径都会重建 FE-011/012。

### 交易结算、发票与重提

```text
QUOTATION
  -> 后端结算预览（可选促销）
  -> 后端结算命令 + CAS
  -> PENDING
  -> 审批通过 APPROVED / 拒绝 LOST

APPROVED
  -> 创建发票 PENDING（交易进入 PAYMENT）
  -> 发票 ISSUED 或 VOID（交易阶段按后端状态机变化）

LOST
  -> 修订（业务规则待确认）
  -> resubmit：重新扣库存、清旧审批、回 QUOTATION
```

前端所有按钮只能从服务端阶段派生。命令成功后必须重新读取交易、发票、支付或库存等受影响事实，不得在本地手工推进阶段。

## 图谱结果不足时的定位规则

当前知识图谱能稳定定位 TypeScript 模块函数、Java Controller/Service/DTO，但部分 Vue SFC 内部 `<script setup>` 局部函数只索引到文件级节点。遇到这种情况：

1. 先用 `search_graph` 定位模块 API、后端符号和调用边界。
2. SFC 局部函数图谱无结果时，再用 `rg` 搜索准确函数名或模板事件。
3. 不得因为 SFC 图谱结果为空就跳过页面调用方、模板按钮和现有测试。

## 隐含跨问题依赖

- FE-001 依赖 FE-013：下载错误必须进入统一失效处理。
- FE-003、FE-011、FE-012 依赖 FE-016：否则修好分页后仍可能被旧响应破坏。
- FE-004、FE-005、FE-006、FE-008 依赖 FE-014 的 ID/金额/时间边界，但不应等待全仓类型迁移。
- FE-005 与 FE-006 共享交易金额事实；结算金额契约未固定前，发票默认金额也不可靠。
- FE-009 的轮询会放大 FE-013 和 FE-016；权限拆分时必须同时处理请求重叠与卸载取消。
- FE-010 的重提会重新扣库存，不能作为单纯 UI 按钮任务交付。
