# 前后端契约与数据类型整改

## FE-001 客户导出认证方式错误并泄露 Token

- 严重级别：P1
- 性质：已确认缺陷
- 文件和准确行号：`dealer-web/src/pages/dashboard/customer.vue:149-157`；`dealer-server/src/main/java/com/autodealer/crm/config/filter/TokenVerifyFilter.java:43-50`；`dealer-server/src/main/java/com/autodealer/crm/web/CustomerController.java:75-78`
- 当前行为：前端创建隐藏 iframe，把 JWT 作为 `Authorization` 查询参数拼进 URL。后端过滤器只读取 `Authorization` Header，不读取查询参数。
- 正确行为：下载请求应通过共享请求层发送 Header，并以 Blob 处理文件名和内容；JWT 不应出现在 URL、浏览历史、代理日志或 Referer 中。
- 触发方式：登录后进入客户页，点击“全部导出”或“选择导出”。
- 业务影响：接口返回 Token 为空，导出不可用；同时 JWT 会暴露到浏览器和基础设施日志。
- 修复建议：在 customer 模块增加 typed blob API，复用 `axiosClient` 的 Token 拦截器，解析 `Content-Disposition` 后主动下载；删除 iframe 和查询串认证。
- 可能受影响的后端接口或其他页面：`GET /api/exportExcel`；其他未来文件下载页面也必须禁止查询串 Token。

## FE-002 用户新增和编辑的 Content-Type 与后端不一致

- 严重级别：P1
- 性质：已确认缺陷
- 文件和准确行号：`dealer-web/src/pages/dashboard/user.vue:386-404`；`dealer-web/src/modules/user/api/user-api.ts:35-40`；`dealer-server/src/main/java/com/autodealer/crm/web/UserController.java:61-71`
- 当前行为：页面绕过已经存在的 typed user API，把表单转换为 `FormData` 后调用通用 `doPost/doPut`。后端两个方法均使用 `@RequestBody` DTO，要求 JSON。
- 正确行为：页面应分别构造 `CreateUserRequest` 和 `UpdateUserRequest`，调用模块 API，以 `application/json` 提交；编辑请求不得携带密码和账号状态字段。
- 触发方式：用户管理页填写新增表单或编辑已有用户并提交。
- 业务影响：请求可能以 415/501 失败，用户维护主流程不可用；宽松表单还把后端不接受的字段一并提交。
- 修复建议：删除页面级 `doPost/doPut`，接入 `createUser/updateUser`；创建与编辑使用不同 Zod Schema 和请求映射。
- 可能受影响的后端接口或其他页面：`POST /api/user`、`PUT /api/user`；用户详情和列表刷新。

## FE-003 库存列表对统一响应执行了二次解包判断

- 严重级别：P1
- 性质：已确认缺陷
- 文件和准确行号：`dealer-web/src/shared/api/http-client.ts:70-79`；`dealer-web/src/modules/product/api/product-api.ts:33-42`；`dealer-web/src/pages/dashboard/product/stock.vue:268-289,293-323`
- 当前行为：`httpClient` 已返回 envelope 的 `data`，页面却要求 `res.data` 存在才赋值。`PageResult` 没有 `data` 字段，因此分类选项和库存预警列表都不会进入成功分支。
- 正确行为：直接使用 `res.list`、`res.total`；失败由 Promise reject 进入 catch。
- 触发方式：进入 `/dashboard/product/stock` 或点击刷新/筛选。
- 业务影响：页面一直显示空库存预警，掩盖真实缺货风险；分类筛选只有“全部”。
- 修复建议：移除 `res.data` 检查并使用明确 `PageResult<ProductCategory/StockAlert>`；补回归测试验证非空响应真正渲染。
- 可能受影响的后端接口或其他页面：`GET /api/products/stockalerts`、`GET /api/product-categories`、库存记录弹窗。

## FE-004 促销写请求缺少必填 productId

- 严重级别：P1
- 性质：已确认缺陷
- 文件和准确行号：`dealer-web/src/pages/dashboard/product/promotion.vue:73-126,183-190,240-270`；`dealer-server/src/main/java/com/autodealer/crm/dto/CreateProductPromotionRequest.java:16-20`；`dealer-server/src/main/java/com/autodealer/crm/dto/UpdateProductPromotionRequest.java:16-20`
- 当前行为：促销表单只有名称、类型、折扣、时间和状态，从未选择或提交产品；后端创建和更新 DTO 均对 `productId` 使用 `@NotNull`。
- 正确行为：表单必须选择有效商品 ID，并在编辑回显及提交时保持该稳定 ID；不能只使用商品展示名。
- 触发方式：新增任意促销，或编辑历史数据中没有被当前表单保留的促销。
- 业务影响：所有新增促销必然校验失败；编辑可能因丢失 productId 失败，促销维护不可用。
- 修复建议：新增商品选择器和专用 `PromotionForm`/请求类型；校验商品、起止时间、折扣范围和状态；编辑前按详情契约回显。
- 可能受影响的后端接口或其他页面：`POST/PUT /api/product-promotions[/{id}]`；交易详情的促销选择。

## FE-014 领域类型不能约束真实 DTO

- 严重级别：P2
- 性质：高风险疑点
- 文件和准确行号：`dealer-web/src/shared/types/common.ts:3-5`；`dealer-web/src/modules/activity/model/activity.types.ts:4-12`；`dealer-web/src/modules/product/model/product.types.ts:4-25`；`dealer-web/src/modules/tran/model/tran.types.ts:4-44`；`dealer-web/src/shared/types/id.ts:1-4`
- 当前行为：多个领域对象继承 `LooseRecord`，表单直接是 `LooseRecord`；ID 普遍为 `number | string`，金额为 JS `number`，枚举为任意 `string`。
- 正确行为：请求 DTO、响应 DTO、表单模型和展示模型应独立、精确建模；Long ID 从网络边界起使用字符串；金额明确使用十进制定点策略；状态使用稳定联合类型/常量。
- 触发方式：后端字段重命名、返回 null、Long 超出 `Number.MAX_SAFE_INTEGER`、新增枚举，或页面提交后端不接受字段时。
- 业务影响：TypeScript 无法发现当前已经出现的 `res.data`、缺 productId、错误字段名等契约漂移；Long ID 和金额存在静默损坏风险。
- 修复建议：逐模块替换 `LooseRecord`，优先交易、支付、发票、商品、库存；在 API 边界做日期/金额/ID 映射和 runtime validation。
- 可能受影响的后端接口或其他页面：全部模块 API；尤其 Long 商品 ID、BigDecimal 金额、LocalDateTime、布尔/状态字段。
- 缺少证据：当前数据库 ID 是否会达到 JS 不安全整数、线上金额精度案例无法从静态代码确认，因此 Long/精度损坏列为高风险而非已发生事故。

## Agent 执行说明

### FE-001：改为可鉴权、可识别错误的文件下载

#### 目标调用链

```text
customer.vue::handleExport(ids)
  -> customer-api.ts::exportCustomers(params)
  -> http-client.ts::download(url, config)
  -> GET /api/exportExcel（Authorization Header + ids query）
  -> { blob, filename }
  -> browser-download.ts::saveBlob(blob, filename)
```

#### 具体函数改法

1. 在 `shared/api/http-client.ts` 增加下载专用返回类型，例如 `DownloadResult`，至少包含 `blob`、`headers` 或已经解析好的 `filename`。不要继续使用只返回 `Blob` 的现有 `blob()`，因为它丢掉了 `Content-Disposition`。
2. 下载请求仍必须走 `axiosClient`，使 `interceptors.request` 自动写入 Token。`ids` 通过 `config.params` 发送，禁止手工拼 URL，禁止出现 `Authorization` 查询参数。
3. 下载响应不能走普通 `ApiEnvelope<T>` 解包。成功时读取 Blob；失败时若响应体也是 Blob，按响应 `Content-Type` 或 `blob.text()` 尝试解析 `ApiEnvelope<unknown>`，转换成 `ApiError`，并复用会话失效处理。
4. 在 `modules/customer/api/customer-api.ts` 增加 `exportCustomers(ids?: EntityId[])`。该函数负责把选择 ID 转成后端当前接受的逗号字符串；页面不得知道 `/api/exportExcel` 路径和 Axios 配置。
5. 在共享下载工具中：解析 `filename*=` 优先于 `filename=`，对 RFC 5987 值执行 `decodeURIComponent`，去掉包裹引号；缺失响应头时使用稳定默认名，例如 `customers.xlsx`。
6. `customer.vue` 删除 `env`、`getToken`、iframe 创建逻辑和 `customerIdArray` 这份重复选择状态。保留唯一 `selectedIds`，实现 `handleExport(ids?)`、`batchExportExcel()`、`chooseExportExcel()`；请求期间用独立 `exporting` 防止重复点击。
7. 下载工具通过 `URL.createObjectURL` 创建临时链接，触发后必须移除 `<a>` 并在 `finally` 中 `URL.revokeObjectURL`。

#### 隐藏问题

- 只把 iframe 改成 `window.open` 仍无法设置 Header，也仍会泄露 Token，不能视为修复。
- 只复用当前 `httpClient.blob()` 会丢失文件名，并且 Blob 形式的 401/512 可能绕过普通 envelope 处理。
- “全部导出”传空数组和“不传 ids”语义不同。当前后端以缺失/空白 `ids` 表示全部，API 层应使用 `undefined`，不能发送 `ids=` 后再依赖偶然兼容。
- 导出写入已经完成后，浏览器保存失败不应重新请求接口；需要提示本地保存失败，避免重复生成和重复审计。

#### 回归断言

- `exportCustomers(['1', '2'])` 发出 `params: { ids: '1,2' }`，URL 中没有 Token，Header 中有 Token。
- UTF-8 和普通 `Content-Disposition` 都能得到正确文件名，缺失文件名时使用默认值。
- Blob 形式的 session-invalid envelope 只进入一次统一失效流程。
- 页面无选择时不发请求；请求期间两个导出按钮不可重复触发；成功与失败均恢复 `exporting`。

### FE-002：让用户创建和编辑严格匹配两个 JSON DTO

#### 目标类型和函数

- `createUserSchema` 对应 `CreateUserRequest`：只含 `loginAct/loginPwd/name/phone/email`。
- `updateUserSchema` 对应 `UpdateUserRequest`：只含 `id/loginAct/name/phone/email`，不含密码和四个账号状态字段。
- `toCreateUserRequest(values)` 与 `toUpdateUserRequest(values, id)`：在提交边界显式挑选字段，不使用对象展开传递页面状态。
- `userSubmit()`：只负责根据 `isEditMode` 调用 `createUser` 或 `updateUser`、维护提交状态和刷新。

#### 具体函数改法

1. `user.vue` 的 import 改为使用 `fetchUserPage/fetchUserDetail/createUser/updateUser` 及对应类型，删除该流程的 `doGet/doPost/doPut`。
2. 创建和编辑不能继续共享包含所有账号状态字段的万能表单。可以使用两个 Schema，或以基础 Schema 加 `createSchema/updateSchema` 组合，但提交类型必须是两个互斥分支。
3. `add()` 只初始化创建字段；`edit(id)` 先进入详情 loading，`loadUser(id)` 成功后用 `setValues` 写入编辑字段。详情失败时不能打开一个可提交的空表单。
4. `userSubmit()` 使用 `await` 和 `try/catch/finally`，不混用 `.then()`。成功后关闭 Dialog 并刷新；失败时保留输入和 Dialog，提交按钮恢复。
5. 编辑 ID 不能以 `id > 0` 从表单内容推断模式，应由 `isEditMode` 与只读 `editingUserId` 决定；提交前验证两者一致。
6. 账号启用、锁定、密码修改必须继续走独立命令 API，不能重新塞入通用更新 DTO。

#### 隐藏问题

- 仅把 `FormData` 改成普通对象仍可能把 `loginPwd`、账号状态和详情对象一起提交；必须显式映射 DTO。
- 当前 `UpdateUserRequest.id` 是 `number`，而共享 ID 类型允许字符串。执行时应核对后端仍为 `Integer`，在路由/详情边界验证后只转换一次，禁止 `Number(undefined)`。
- 成功写入后列表刷新失败时，提示应区分“用户已保存，但列表刷新失败”，否则用户可能重复创建。
- 编辑载入较慢时快速打开另一用户会出现旧详情覆盖新 Dialog，应复用 FE-016 的最后请求获胜规则，或在 `loadUser` 中校验当前 `editingUserId`。

#### 回归断言

- 创建请求为 JSON，字段集合精确等于五个创建字段。
- 编辑请求为 JSON，包含 `id`，不含 `loginPwd/accountEnabled/accountNoLocked/accountNoExpired/credentialsNoExpired`。
- 详情失败、重复点击提交、后端字段校验失败和列表刷新失败都有确定 UI 状态。

### FE-003：删除二次解包并统一库存列表状态

#### 具体函数改法

1. 把 `stockAlertList/categoryOptions/stockRecords/currentProduct` 改成明确泛型，禁止 `ref([])` 和 `ref(null)` 依赖隐式 `never[]/any`。
2. `loadCategoryOptions()` 直接读取 `const { list } = await fetchCategoryPage(...)`，总是执行 `categoryOptions.value = [ALL_OPTION, ...mapped]`。删除 `res.data` 判断。
3. `loadStockAlerts()` 直接赋值 `res.list`、`res.total` 和服务端实际 `pageSize`；请求失败时保留上一份成功数据并显示失败状态，或明确清空，二者必须固定，不能半更新。
4. 查询参数类型不要复用过宽的 `ProductQuery`。为库存预警建立 `StockAlertQuery`，字段固定为 `page/size/sku/name/categoryId`，空字符串和 `null` 在 API 边界移除。
5. `handleRestockSubmit()` 成功后 `await loadStockAlerts()`；若补货成功而刷新失败，显示分离反馈。关闭 Dialog 前后顺序应固定，避免用户误以为补货失败。

#### 隐藏问题

- 条件写成 `if (res && res.data)` 或调换顺序都不是修复，`PageResult` 本来就没有 `data`。
- 当前分类接口是分页接口，固定 `size: 100` 可能漏掉第 101 个分类。短期至少检测 `total > list.length` 并报告；长期应使用后端 option/list-all 契约。
- `categoryId` 不能用简单 truthy 判断，否则合法值 `0` 会被丢弃。应判断 `!== null && !== undefined && !== ''`。
- 补货成功会改变列表是否仍属于“预警”，因此不能只修改当前行库存数；应重新获取服务端列表事实。

#### 回归断言

- 非空 PageResult 渲染分类和库存行；空结果正确更新 `total=0`。
- 筛选、重置、补货刷新均只消费一次解包后的数据。
- 分类超过单页上限时不会静默伪装成完整选项集。

### FE-004：建立促销专用表单和请求契约

#### 新增类型

在 `modules/product/model/product.types.ts` 中拆出：

- `PromotionType`、`PromotionStatus` 稳定 code 类型；展示中文通过映射得到，不直接把中文标签当协议值，除非后端契约明确以中文为 code。
- `ProductPromotion` 完整响应类型，至少包含 `id/productId/name/type/discount/startTime/endTime/status`。
- `CreatePromotionRequest` 与 `UpdatePromotionRequest`；两者字段对应后端 DTO，ID 类型按后端 Long 边界处理。
- `PromotionFormValues`；`toCreatePromotionRequest()`、`toUpdatePromotionRequest()` 负责 datetime-local 和请求格式转换。

#### 具体函数改法

1. `product-api.ts` 的 `createPromotion/updatePromotion` 不再接收 `ProductForm`，分别接收专用请求类型。
2. `promotion.vue` 加载商品选项，并在表单加入必填 `productId`。选项 value 使用稳定 ID，label 可显示 SKU + 商品名。
3. 用 vee-validate + Zod 替换手写 `ref<ProductForm>`：校验名称、productId、开始早于结束、折扣/金额范围；提交期间禁用按钮。
4. `handleAdd()` 重置全部字段；`handleEdit(row)` 必须保留 `productId` 并把后端时间转换成 `datetime-local` 格式。若列表响应不含完整字段，先调用促销详情 API，不能拿列表行猜完整 DTO。
5. `handleSubmit()` 根据模式调用精确映射函数。成功后关闭并刷新；失败时保留输入，根据 `ApiError.code` 呈现字段或冲突信息。

#### 隐藏问题

- 补上一个 Product Select 但仍用 `ProductForm = LooseRecord`，缺字段问题会再次出现。
- `datetime-local` 不携带时区。必须先确认后端 `LocalDateTime` 的语义，再按固定 `yyyy-MM-dd HH:mm:ss` 或 ISO local 格式转换，不能调用 `toISOString()`。
- 当前页面用“折扣/满减/直降”和数值推断算法，但没有最低消费门槛字段；“满减”是否真的可表达需要后端业务契约确认。未确认前不得在前端虚构规则。
- 促销状态如果应由起止时间派生，就不应让用户任意编辑；这是后端业务决策，执行前必须核对 Service，而不是只修 productId。

#### 回归断言

- productId 缺失时不发请求；创建、编辑都发送 productId。
- 编辑回显不丢 productId，时间转换不跨日。
- 不同促销类型的数值边界分别验证，结束时间早于开始时间时禁止提交。

### FE-014：按边界逐步移除 LooseRecord

#### 实施顺序

1. 先定义共享协议基础类型：`EntityId` 的网络表示、`MoneyText` 或明确的金额边界策略、`LocalDateText`、`LocalDateTimeText`、`PageQuery/PageResult`。
2. 按 `tran -> product/promotion/stock -> user -> customer/clue -> dict/system` 迁移。每次只改一个模块的 API、类型、页面和测试。
3. 每个模块区分 Response、Request、FormValues、ViewModel。禁止一个 `TranForm` 同时用于创建交易、审批、发票和支付。
4. API 函数只返回业务类型；页面不得访问 AxiosResponse 或 envelope。
5. 对外部数据需要运行时保护的位置使用 Zod/类型守卫；TypeScript interface 不能验证真实网络数据。

#### 必须明确的策略

- Long ID：前端内部以字符串保存，不经过 `parseInt`；如果当前后端仍返回 JSON number，应先修后端序列化契约或明确安全上限。
- 金额：权威计算留在后端；前端展示使用后端十进制字符串或经过约束的解析器，不使用浮点结果作为提交依据。
- nullability：后端可能为空的字段明确 `| null`；未提交字段才用 `undefined`。
- 枚举：协议 code 与中文 label 分离，未知 code 显示兜底并保留原值，不静默映射成某个正常状态。
- 日期：分别提供 local-date、local-datetime、instant 解析/格式化函数，函数名体现语义。

#### 隐藏问题

- 一次性删除 `LooseRecord` 会暴露大量真实契约漂移，不应靠批量 `as` 恢复编译。每个断言都必须有边界验证证据。
- `number | string` 看似兼容，实际会让 `includes`、Map key 和 Select value 出现 `1 !== '1'`；同一实体 ID 进入前端后必须规范成一种表示。
- 类型收紧可能揭示后端列表/详情字段不一致。应新增适配器，不要把所有字段重新改成 optional。

#### 完成标准

- 本轮触达模块不再新增 `LooseRecord/any/Record<string, any>` 或无证据断言。
- 请求体字段可由类型测试或 API mock 精确断言。
- `npm run typecheck` 通过，且没有以双重断言掩盖错误。
