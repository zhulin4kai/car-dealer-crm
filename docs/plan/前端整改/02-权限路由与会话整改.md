# 权限、路由与会话整改

## FE-009 系统配置与系统监控共用页面但权限不匹配

- 严重级别：P2
- 性质：已确认缺陷
- 文件和准确行号：`dealer-web/src/router/routes.ts:120-124`；`dealer-web/src/pages/dashboard/system.vue:478-512,611-625,994-999`；`dealer-server/src/main/java/com/autodealer/crm/web/SystemMonitorController.java:16-18,75-77`
- 当前行为：路由只校验 `system:list`。页面一挂载就请求 `/api/monitor/all`，随后每秒继续请求监控接口；后端监控 Controller 独立要求 `monitor:view`。请求失败后页面把浏览器模拟数据标为替代数据。
- 正确行为：系统配置和系统监控应拆分路由/页面并分别声明权限；至少应按 `monitor:view` 控制监控区和轮询，403 不得伪装成真实系统指标。
- 触发方式：给角色授予 `system:list` 但不授予 `monitor:view`，进入系统管理页。
- 业务影响：持续产生 403 请求和误导性模拟指标；反向只拥有监控权限的用户也无法通过当前路由进入监控能力。
- 修复建议：拆分 `/dashboard/system` 与 `/dashboard/system/monitor`，或在组件中按权限惰性加载；403 展示“无监控权限”，禁止 fallback 冒充服务端数据。
- 可能受影响的后端接口或其他页面：全部 `/api/monitor/*`、`GET /api/system/list`、菜单配置。

## FE-013 会话失效处理缺少单飞与内存状态清理

- 严重级别：P2
- 性质：已确认缺陷
- 文件和准确行号：`dealer-web/src/shared/api/http-client.ts:29-47,50-67`；`dealer-web/src/stores/auth.store.ts:52-58`
- 当前行为：每个失效响应都会独立调用确认框；取消后各自设置 1.5 秒定时跳转。请求层只清 storage，不调用 Store 的 `forceLogout`，当前页面内存中的 `token/currentUser/menuPermissionList` 在重载前仍存在。
- 正确行为：同时只运行一个失效流程，立即清理所有认证与权限事实来源，并通过 Router replace 到登录页；用户不应能取消一个已经失效的会话。
- 触发方式：Token 过期时页面同时发出详情、产品、发票、支付等多个请求。
- 业务影响：弹出多个确认框、重复定时器和重复跳转；短窗口内 UI 仍显示旧用户和旧权限。
- 修复建议：实现全局 session-invalid single-flight 处理器；Store 注册统一清理回调；401/Token code 直接清理并 replace，403 单独进入无权页。
- 可能受影响的后端接口或其他页面：所有认证接口；交易详情和系统监控最容易并发触发。

## 路由权限核对结果

- `routes.ts:21-123` 的页面权限码与 `PermissionCodes.java:11-86` 中的稳定功能权限码拼写一致。
- 活动、线索、商品、字典、交易、用户页面的主要按钮均使用与后端 `@PreAuthorize` 相同的编码。
- 详情子路由均声明了权限，但页面本身还会调用其他权限接口。例如审批/发票路由要求 `tran:approve`/`tran:invoice`，页面加载详情和产品仍要求 `tran:view`。当前初始化角色同时拥有这些权限；自定义角色是否允许拆分尚无产品规则证据，应在权限矩阵中明确依赖关系。
- `/403` 本身不要求功能权限，守卫不会在已认证状态下把它再次重定向到 `/403`，未发现确认的循环。

## 无法完全确认的权限项

- 菜单权限、页面权限和按钮权限在数据库中是三层节点；当前路由使用功能 `*:list/view` 而不是 `page:*`。需要产品侧明确“能看到菜单但没有列表权限”是否是合法角色配置，才能决定路由应校验一个权限还是权限组合。
- 当前没有前端角色管理页面，无法从 UI 证明任意权限组合能否被创建；这里只报告代码允许出现的依赖风险，不推断线上角色配置。

## Agent 执行说明

### FE-009：拆开系统配置与监控的可达性和生命周期

#### 推荐结构

- `/dashboard/system`：`SystemConfigView`，路由权限 `system:list`，只加载 `/api/system/*`。
- `/dashboard/system/monitor`：`SystemMonitorView`，路由权限 `monitor:view`，只加载 `/api/monitor/*` 并持有轮询和图表生命周期。
- 菜单是否新增独立监控项必须与后端菜单数据一致；若短期不能改菜单，可在系统页内用权限控制监控 Tab，但仍应把监控逻辑提成独立组件/composable。

#### 具体函数改法

1. 从 `system.vue` 提取 `getLocalSystemInfo/getSystemInfoWithRetry/startAutoRefresh/stopAutoRefresh/initCharts/updateCharts/fallbackToWebAPI` 及相关状态到监控页面或 `useSystemMonitor()`。
2. 路由拆分方案下，在 `routes.ts` 新增 `system-monitor`，声明 `PERMISSIONS.monitor.view`。页面挂载前由守卫拒绝无权用户，系统配置页不再 import 监控 API。
3. Tab 兼容方案下，使用 `permissionStore.hasPermission(PERMISSIONS.monitor.view)` 计算 `canViewMonitor`；只有为 true 时才初始化图表、请求数据和启动 timer。
4. 403 必须设置显式 `forbidden` 状态并停止重试/轮询。网络错误可提供手动重试，但不得转换成“真实系统指标”。
5. `startAutoRefresh()` 不使用 `setInterval(async () => ...)` 直接并发叠加。改为上一次请求完成后再安排下一次 `setTimeout`，或增加 `isRefreshing` 锁；卸载时清除 timer 和进行中的请求。
6. 浏览器 `performance.memory` 只能标为“当前浏览器标签页估算”，不得放进服务端 JVM/主机监控卡片。若无真实数据，展示不可用状态，而不是模拟百分比。

#### 隐藏问题

- 仅在模板隐藏监控区域不够；`onMounted()` 仍会调用接口和启动定时器。
- 当前 retry 内部调用的 `getLocalSystemInfo()` 已消费异常并 fallback，外层未必能按预期捕获；重构时应让数据函数抛出，让页面状态层统一决定是否重试。
- `setInterval` 周期小于请求耗时时会累计并发请求，引发 FE-013 多重失效弹窗和 FE-016 旧数据覆盖。
- 页面路由有 `monitor:view` 不代表 `/api/system/list` 可用；监控页面不得顺带加载配置接口。

#### 回归断言

- 只有 `system:list`：配置页正常、监控 API 调用次数为 0。
- 只有 `monitor:view`：可进入监控页，配置 API 调用次数为 0。
- 监控 403：不 fallback、不重试、不启动下一轮请求，展示无权限。
- 慢请求期间不会叠加轮询，卸载后不再更新状态或图表。

### FE-013：统一会话失效为不可取消的单飞流程

#### 所有权设计

会话失效不能继续由 `http-client.ts` 直接操作 storage 和 `window.location`。建议新增 `shared/auth/session-invalid-handler.ts`：

- `registerSessionInvalidHandler(handler)`：应用启动时注入使用 Pinia 和 Router 的处理函数。
- `notifySessionInvalid(error): Promise<void>`：请求层调用；内部持有 `inFlight` Promise，已有流程时直接返回同一个 Promise。
- 实际 handler 顺序：`authStore.forceLogout()` -> `permissionStore.clearPermissions()` -> `router.replace({ name: 'login', query: { redirect } })`。

也可以由请求层通过事件总线发出一次事件，但必须保持单一所有者，不能让每个页面订阅并分别跳转。

#### 具体函数改法

1. 删除 `handleInvalidSession()` 中的确认框、1.5 秒 timer、重复 storage 清理和 `window.location.href`。
2. 响应拦截器只识别稳定 session-invalid code，并调用 `notifySessionInvalid`。无论失效 code 出现在 HTTP 成功 envelope 还是 Axios error response，都走同一入口。
3. 普通 `request<T>()` 在 `envelope.code !== 200` 时抛 `ApiError` 前也要通知失效；否则 HTTP 200 + code 512 只会在拦截器异步触发，调用方仍可能出现竞争反馈。
4. `forceLogout()` 负责 Auth Store；`clearPermissions()` 负责 Permission Store。不要只清 `permission-storage`，否则内存 `menuPermissionList` 仍会渲染菜单。
5. 导出等 Blob 请求复用同一失效识别，见 FE-001。
6. 登录、主动退出与被动失效要区分。主动 `logout()` 的后端调用失败仍本地清理；被动失效不再请求 `/api/logout`，避免无效会话再次触发失效处理。

#### 401、403 和业务 code

- 未登录/Token 缺失、无效、过期、不匹配：清理会话并跳登录。
- 已认证但无功能/数据权限：保留会话，跳 403 或显示操作无权，绝不能登出。
- 业务状态冲突：保留会话，提示并刷新对应业务事实。
- 网络失败/5xx：保留会话，允许重试，不能因无法确认会话就主动清 Token，除非后端安全规范明确要求 fail closed 的前端行为。

#### 隐藏问题

- `inFlight` 必须在完成后重置，允许未来新登录再次发生一次失效处理；但路由跳转完成前不能重置，避免同批请求再次触发。
- `router.replace` 可能被当前导航守卫并发执行。处理器应先清状态，再 replace；守卫看到未认证后自然回登录页。
- 登录页本身若收到 session-invalid code，不应产生重定向循环。
- 统一 handler 不能吞掉原始 `ApiError`；调用方仍需停止 loading，但页面不应再弹一份“请求失败”。可给 `ApiError` 增加 `isSessionInvalid` 或让错误展示层识别 code。

#### 回归断言

- 5 个并发 code 512 只调用一次 `forceLogout`、一次 `clearPermissions`、一次 `router.replace`。
- Auth/Permission Store、localStorage、sessionStorage 全部清空。
- 403 不清会话；网络错误不清会话；新登录后下一次失效仍可触发。

### 权限依赖矩阵的执行要求

详情子页存在“进入权限”和“加载依赖权限”不同的问题，执行 Agent 必须在改路由前产出并验证下表：

| 页面 | 进入权限 | 初始化接口权限 | 命令权限 | 未满足依赖时的行为 |
|---|---|---|---|---|
| 交易详情 | `tran:view` | `tran:view` | 结算、审批、开票、支付分别独立 | 只隐藏无权命令 |
| 交易审批 | `tran:approve` | 当前详情/产品接口仍需 `tran:view` | `tran:approve` | 若产品要求权限可独立授予，则后端需提供审批专用详情；不能靠前端绕过 |
| 交易发票 | `tran:invoice` | 发票列表当前需 `tran:view` | `tran:invoice` | 同上，明确角色依赖或拆专用读取接口 |
| 系统配置 | `system:list` | `system:list` | add/edit/delete 独立 | 无监控权限时绝不请求监控 |
| 系统监控 | `monitor:view` | `monitor:view` | 无 | 无配置权限时绝不请求配置 |

这张矩阵最终应进入测试夹具或可执行一致性检查，不能只停留在人工说明。
