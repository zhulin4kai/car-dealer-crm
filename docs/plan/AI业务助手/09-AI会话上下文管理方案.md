# AI 会话上下文管理方案

## 关联 Spec

- docs/spec/AI业务助手/00-业务范围与边界.md

## 背景

当前 AI 助手只有 Run 和 Run trace。每次用户发送问题都会创建独立 Run，模型只接收当前问题和本轮工具摘要，无法理解“刚才”“继续”“上一笔交易”等多轮业务引用。

## 目标

- Conversation 作为多轮业务对话容器。
- Run 作为 Conversation 中的一次执行。
- 同一用户和同一业务对象默认复用一个活跃 Conversation。
- 无业务对象时使用通用 Conversation。
- 模型上下文使用会话摘要和最近 8 条用户可见消息。
- 用户可以新建、重命名和归档会话，归档不删除审计链。
- 用户可以编辑或撤回自己发送的消息，旧版本和失效分支保留审计但退出模型上下文。

## 状态与数据方案

- 新增 `t_ai_conversation` 保存会话编号、用户、标题、状态、入口、业务对象上下文、脱敏摘要、最近 Run 和最近消息时间。
- `t_ai_run` 增加 `conversation_id`、`parent_run_id` 和 `turn_no`。
- `t_ai_message` 增加 `conversation_id` 和 `visible_to_user`。
- `t_ai_message` 增加稳定消息编号、状态、修订号、被替代消息、是否进入上下文、并发版本和编辑/撤回审计字段。
- `t_ai_run` 增加当前上下文是否有效及失效原因，历史分支不物理删除。
- `t_ai_tool_call` 增加 `display_payload_json`，只保存脱敏、限长、用于前端业务卡片恢复的结构化展示结果。
- Conversation 状态固定为 `ACTIVE` 和 `ARCHIVED`。
- Conversation 归档只影响用户默认列表，不删除 Run、Message、ToolCall、Proposal、Workflow、Approval 或 ExecutionEvent。

## 会话恢复模型

- `GET /api/ai/conversations/{conversationNo}` 返回 `turns`，每个 turn 对应一个 Run。
- 每个 turn 必须包含用户问题、AI 回答、工具结果、Proposal、Workflow、Approval 和 ExecutionEvent。
- 前端恢复 Conversation 时以 `turns` 为主，不得只读取 `latestRunTrace`。
- `latestRunTrace` 只作为兼容字段，不能代表完整 Conversation。
- 旧 ToolCall 没有展示 payload 时只展示安全摘要和空状态，禁止回退展示原始 JSON 或英文字段。

## API 方案

- `GET /api/ai/conversations` 查询当前用户活跃会话列表。
- `POST /api/ai/conversations` 创建会话。
- `GET /api/ai/conversations/{conversationNo}` 查询会话详情、消息、最近 Run 和可恢复状态。
- `PATCH /api/ai/conversations/{conversationNo}/title` 重命名会话。
- `POST /api/ai/conversations/{conversationNo}/archive` 归档会话。
- `PATCH /api/ai/conversations/{conversationNo}/messages/{messageNo}` 编辑用户消息并创建替代 Run。
- `POST /api/ai/conversations/{conversationNo}/messages/{messageNo}/withdraw` 撤回用户消息并使相关上下文分支失效。
- `POST /api/ai/runs` 增加 `conversationNo`，未传时由后端按当前用户和业务对象上下文解析默认会话。

## 运行时方案

- Spring Boot 创建 Run 前解析或创建 Conversation。
- 同一 Conversation 下 Run 的 `turnNo` 必须递增。
- Spring Boot 调用 `dealer-ai` 时下发 `conversationNo`、`conversationSummary` 和 `messageHistory`。
- `messageHistory` 固定最多最近 8 条用户可见消息。
- `messageHistory` 只读取当前活动分支中 `included_in_context = true` 的消息，条数由全局 AI 策略在 1 到 8 之间控制。
- `conversationSummary` 只保存脱敏业务摘要，不保存权限、数据范围、API Key、Provider runtime config、服务间 token 或供应商原始响应。
- dealer-ai 只把会话摘要和最近消息放入模型输入，不持久化会话。

## 前端方案

- 独立 AI 页面展示会话列表、新建会话、重命名和归档入口。
- 右侧栏保持轻量，只显示当前会话、新建会话和切换入口。
- `AiAssistantPanel` 持有 `activeConversationNo`，发送消息时携带会话编号。
- `AiAssistantPanel` 使用 turn 视图渲染，业务卡片、Proposal 和处理过程必须绑定当前轮回答。
- 刷新、切换会话和展开独立页面后恢复完整 Conversation，而不是只恢复单个 Run。
- 业务对象页面打开 AI 时默认恢复该对象的活跃 Conversation。
- 用户消息提供编辑和撤回入口；运行中禁止修改，编辑成功后直接订阅替代 Run 的流式结果。
- 编辑或撤回历史消息后刷新当前 Conversation，失效分支不再作为主对话展示，但后台审计和按 Run trace 查询继续保留。
- AI 回答 Markdown 必须通过安全渲染组件处理，禁用模型 HTML，只允许基础 Markdown 标签。

## 风险与约束

- 不能把会话摘要变成敏感数据存储点。
- 不能为了多轮上下文绕过权限和数据范围。
- 不能让 `dealer-ai` 访问数据库或持久化 Conversation。
- 本方案只要求 `dealer-ai` 稳定接收会话摘要、最近消息和输出结构化工具结果，不负责重构 LangGraph 节点图；LangGraph 节点化收敛由 `docs/task/AI业务助手/03-dealer-ai LangGraph编排任务.md` 负责。
- 旧 Run API 必须后向兼容，未传 `conversationNo` 时自动解析默认会话。
- 工具展示 payload 不能保存 Provider 原始响应、权限、数据范围、API Key 或服务间 token。
- 会话切换期间如果当前 Run 正在生成，前端必须先停止生成或阻止切换，不能让两个会话共享临时状态。
- 编辑和撤回不得撤销已执行的 Proposal 或 CRM 业务事实；未确认 Proposal 应随分支失效而过期。
- Conversation 摘要必须从当前活动分支重建，禁止继续追加已编辑或已撤回的旧内容。

## 验收标准

- 同一业务对象连续提问能理解上一轮上下文。
- 新建会话后不带旧会话历史。
- 刷新后恢复同一 Conversation 的消息和最近 Run。
- 刷新和切换会话后能恢复每一轮的业务卡片、Proposal、Workflow 和处理过程。
- 待审批交易、客户、库存、跟进和商品工具结果不丢失展示 payload。
- AI 返回 Markdown 列表、表格和代码块时可读展示，模型 HTML 不会执行或插入页面。
- 归档会话后默认列表隐藏，但审计链保留。
- 编辑消息后旧版本和后续失效轮不进入模型上下文，新 Run 使用新文本。
- 撤回消息后旧内容不进入消息历史和会话摘要，已执行业务动作不回滚。
- `providerRuntimeConfig`、API Key、权限和数据范围不进入 Conversation summary、messageHistory、SSE 或 trace。
