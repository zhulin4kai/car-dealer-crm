# 收款退款流水与幂等方案

## 关联 Spec

- docs/spec/收款退款/00-业务范围与边界.md
- docs/spec/收款退款/01-流程规则与验收规格.md

## 背景

收款和退款用于表达资金事实，必须以流水、状态和金额校验为核心。交易状态可以观察资金进度，但不能替代支付和退款记录。

## 目标

- 收款记录追加保存，不通过删除覆盖资金事实。
- 退款以反向流水或退款记录关联原收款。
- 累计收款、可退款金额和交易应付金额由服务端计算。
- 创建收款、确认收款、退款处理具备幂等和并发保护。
- 财务权限独立控制收款确认和退款处理。

## 当前现状

- 后端已有 `TPayment`、`TPaymentMapper`、`CreatePaymentRequest`、`TranController` 的 payment/refund 接口。
- 后端已有 `TranServiceImpl.recordPayment` 和 `TranServiceImpl.refundPayment`。
- 前端已有 `dealer-web/src/modules/tran/model/tran.types.ts` 中支付相关类型和交易详情支付展示。
- 当前幂等键、退款额度并发和资金状态口径需要补齐。

## 设计方案

### 流水模型

收款记录应包含交易、金额、类型、方式、状态、业务发生时间、操作人、外部流水号或幂等键。

退款记录应关联原收款，记录退款金额、原因、状态和处理人。

### 后端方案

- 在 `TranServiceImpl` 中保持资金动作事务边界。
- 创建收款和退款使用幂等键或唯一业务约束，避免重复请求重复入账。
- 退款金额校验必须使用数据库事实计算可退额度。
- 支付状态迁移必须校验当前状态、交易状态和操作者权限。
- 资金动作必须写操作审计。

### 前端方案

- 交易详情展示收款、退款、累计金额、应收金额和可退金额。
- 创建收款和退款表单禁用重复提交，但最终幂等由后端保证。
- 无财务权限用户不能看到或触发确认收款、退款处理入口。

### 数据方案

- 支付流水禁止物理删除。
- 外部流水号或幂等键需要唯一约束。
- 金额使用 DECIMAL/BigDecimal，不允许浮点。

## 风险与约束

- 客户端不能提交可信累计金额、可退款金额或交易已收汇总。
- 重复请求不得重复收款、重复退款。
- 退款处理中不能让交易错误进入完成状态。
- 支付清算不是本模块第一阶段范围。

## 实施阶段

1. 梳理 `TPayment`、支付状态、收款和退款接口。
2. 补齐收款、退款状态和幂等约束。
3. 调整金额校验、可退款计算和事务边界。
4. 调整前端交易详情收款退款展示和表单。
5. 补充金额精度、重复请求、并发退款和权限测试。
6. 更新 API、后端、前端和集成文档。

## 验收标准

- 重复提交同一收款请求不会产生两条成功收款。
- 退款金额不能超过可退款金额。
- 交易应收、已收、已退和待退金额由服务端计算。
- 无财务权限用户不能确认收款或处理退款。
- 支付和退款记录不可通过普通业务接口删除。

## 核心闭环补充

- 非空外部支付参考号必须具备幂等判断。
- 每一笔成功收款、退款、退回和冲正都要保留审计事实。
- 部分收款也必须审计，不能只在交易全额完成时审计。
- 交易完成应由交易履约规则判断，收款满额只是必要条件之一。

## 业务协同关系

- 依赖订单、交易履约、客户付款责任、财务确认和权限数据范围。
- 影响交易履约、退款处理、应收分析、客户资金视图和审计日志。
- 权限控制覆盖收款登记、财务确认、退款申请、退款审批、退款执行和导出。
- 审计记录覆盖每笔收款、退款、退回、冲正和金额变更。
- 统计口径依赖应收、已收、未收、已退、待退和逾期金额。

## 状态与事件方案

- 收款状态：待确认、已确认、已退回、已冲正和已作废。
- 退款状态：退款申请、待审批、待执行、已完成、已驳回、执行失败和已撤销。
- 可退金额 = 已确认有效收款 - 已完成退款 - 已批准或执行中的冻结退款金额 - 已完成冲正金额。
- 待审批退款不减少业务可退金额，但占用可申请退款额度。
- 触发事件：订单成立、收款登记、到账确认、收款退回、订单取消、退款申请和冲正。
- 非法迁移：未确认收款不能作为交易完成依据，退款不能删除原收款。
- 异常策略：重复参考号幂等处理，超额退款拒绝，部分收款也必须审计。

## 数据与历史方案

- 必须保留外部参考号、金额、币种、确认人、退款关联和冲正原因。
- 收款和退款流水禁止普通物理删除。
- 每笔成功收款、退款、退回和冲正必须审计。
- 资金数据进入应收、实收、退款、逾期和成交完成条件。
