## 修复路线总览

修复顺序按“风险优先、依赖优先、先建基础再修业务”的原则安排：

1. 先修认证、授权、当前用户、数据权限这些系统边界。否则后续业务修复仍可能被越权调用绕过。
2. 再修交易、客户转换、库存、收款、退款、开票等核心业务一致性问题。
3. 再修数据库模型、SQL 契约、字典状态、删除策略和统计口径。否则业务修复缺少持久层保护。
4. 再修导入导出、缓存、Redis、序列化等基础设施问题。
5. 再统一 DTO/Query/API 响应/异常，这一步会让后续接口改造更稳。
6. 最后清理冗余文件、补审计链路、整理目录架构和工程规范。

## 阶段间依赖

- `01` 是基础安全边界，建议最先修。
- `02` 依赖 `01` 的当前用户和权限边界，否则审计字段仍不可信。
- `03` 应与 `02` 交替推进，尤其是唯一约束、外键、状态 code 会影响业务修复质量。
- `04` 建议在核心业务稳定后修，避免导入、导出、缓存继续制造脏数据。
- `05` 是接口契约收口，适合配合前端联调和后续测试补齐。
- `06` 是长期治理项，其中操作审计可以提前和 `01/02` 并行设计。

## 建议提交节奏

1. 安全认证与权限边界单独提交。
2. 交易/客户/库存/财务一致性单独提交，配回归测试。
3. SQL schema、初始化数据、mapper 约束单独提交，附迁移说明。
4. Excel/Redis/缓存单独提交。
5. DTO/API/异常响应统一单独提交。
6. 架构目录和冗余清理单独提交，避免和业务修复混在一起。
