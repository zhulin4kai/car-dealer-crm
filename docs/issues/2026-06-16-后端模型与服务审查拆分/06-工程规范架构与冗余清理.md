## 问题详情

### 18. 模型层类型和注释风格不统一

类型：编写风格 / 可维护性

位置：
- `dealer-server/src/main/java/com/autodealer/crm/model/TProduct.java:12`
- `dealer-server/src/main/java/com/autodealer/crm/model/TSystem.java:6`
- `dealer-server/src/main/java/com/autodealer/crm/model/TTran.java:1`
- `dealer-server/src/main/java/com/autodealer/crm/model/TUser.java:1`

问题：
旧模型多数使用 `Integer`、`Date`、`Serializable`、字段 JavaDoc；产品/系统相关模型使用 `Long`、`LocalDateTime`，部分没有类级表名注释和字段 JavaDoc。`TProduct` 把类说明写在 `id` 字段上，并混用行尾注释。

影响：
- mapper、DTO、JSON 序列化风格不稳定。
- 自动生成文档和字段审计困难。

建议：
- 统一模型模板：类级说明包含表名，字段级说明包含来源、含义、是否 DB 字段。
- 统一时间类型策略，新增代码优先使用一种类型，并补 Jackson/MyBatis 处理规范。


### 19. 多个 Query 子类继承 BaseQuery 但未声明 equals/hashCode 父类策略

类型：编译警告 / 编写风格

位置：
- `dealer-server/src/main/java/com/autodealer/crm/query/ActivityQuery.java:9`
- `dealer-server/src/main/java/com/autodealer/crm/query/ClueQuery.java:9`
- `dealer-server/src/main/java/com/autodealer/crm/query/UserQuery.java:1`

问题：
编译警告显示 Lombok 在生成 `equals/hashCode` 时没有调用父类。若这些对象进入缓存 key、集合去重或日志比对，会忽略 `token/filterSQL/current/pageSize`。

建议：
- 根据语义显式添加 `@EqualsAndHashCode(callSuper = true/false)`。
- 对纯请求对象通常可不依赖 equals/hashCode，必要时移除 `@Data` 改更窄的 Lombok 注解。


### 20. Service 接口文档不均衡

类型：规范化 / 可维护性

位置：
- `dealer-server/src/main/java/com/autodealer/crm/service/ActivityService.java:8`
- `dealer-server/src/main/java/com/autodealer/crm/service/CustomerService.java:8`
- `dealer-server/src/main/java/com/autodealer/crm/service/TranService.java:10`

问题：
`CustomerService`、`TranService` 有较完整 JavaDoc，而 `ActivityService`、`ClueService`、`ProductService` 等大量接口只有方法签名或历史注释。接口作为业务契约，缺少前置条件、状态变化、副作用说明。

建议：
- 公共 service 方法必须说明：用途、参数、返回值、异常、事务副作用。
- 不建议给所有私有小函数机械添加注释；应优先补业务契约和状态机说明。

## 规范化建议

建议新增并遵守 `docs/specs/backend-model-service-spec.md`，核心规则：
- SQL 是模型契约源头：字段含义、非空、唯一、外键、状态可选值必须写清。
- Java model 只表达数据库字段和明确的关联/派生字段，关联字段必须标注“非数据库字段”。
- 业务状态用枚举 code 或字典 code，不直接依赖自增 ID。
- Service 方法 JavaDoc 重点写业务前置条件、事务副作用、状态迁移、幂等要求。
- Controller 不信任客户端传入的审计字段，操作人必须来自登录上下文。
- 删除优先状态化，核心业务数据避免物理删除。

## 建议修复顺序

1. 先修复批量删除交易误删问题。
2. 统一客户转换的当前用户来源，移除客户端可写 `createBy`。
3. 统一产品状态 code，修正 SQL 初始化数据和 `selectAllOnSale` 契约。
4. 补线索手机号、产品 SKU、交易审批/发票/支付相关唯一与幂等约束。
5. 梳理 SQL 外键和删除策略。
6. 统一模型注释、时间类型、Query Lombok 策略。

### 42. 有操作日志模型和 mapper，但没有写入链路

类型：功能完整性 / 审计缺失

位置：
- `dealer-server/src/main/java/com/autodealer/crm/model/TOperationLog.java:12`
- `dealer-server/src/main/java/com/autodealer/crm/mapper/TOperationLogMapper.java:9`
- `dealer-server/src/main/resources/mapper/TOperationLogMapper.xml:17`

问题：

影响：

建议：
- 建立统一操作审计切面，覆盖新增、修改、删除、审批、导入、导出、退款等动作。
- 日志中记录操作者、模块、业务 id、请求 ip、变更前后摘要。

## DTO / Query 专项补审问题


### 52. 存在未使用或边界不清的 Query/DTO，增加维护噪音

类型：工程规范 / 可维护性

位置：
- `dealer-server/src/main/java/com/autodealer/crm/query/SystemQuery.java:8`
- `dealer-server/src/main/java/com/autodealer/crm/query/TranProductQuery.java:8`
- `dealer-server/src/main/java/com/autodealer/crm/dto/ProductSimpleDTO.java:12`
- `dealer-server/src/main/java/com/autodealer/crm/dto/ProductSimpleDTO.java:17`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/ProductServiceImpl.java:120`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/ProductServiceImpl.java:125`

问题：
`SystemQuery`、`TranProductQuery` 当前没有看到实际 controller/service 使用。`ProductSimpleDTO` 使用 `Integer id/state` 承接产品模型的 `Long id/status`，service 中存在 `product.getId().intValue()` 和 `"on_sale".equals(status) ? 0 : 1` 的隐式转换。

影响：
- 未使用 Query 会让后续开发误以为已有请求契约。
- 产品 ID 从 Long 转 Integer 存在溢出风险。
- DTO 的 `state` 用 0/1 表达，而产品模型用字符串 status，状态语义再次漂移。

建议：
- 删除未使用 Query，或补齐对应接口并明确契约。
- 产品 DTO 的 ID 类型与产品模型保持一致。
- 产品状态统一为稳定 code，不在 DTO 层转换为新的 0/1 语义。

## 冗余文件与缺失业务契约专项


### 53. `SystemQuery` 当前没有接入业务链路，属于可疑冗余文件

类型：冗余文件 / 契约漂移

位置：
- `dealer-server/src/main/java/com/autodealer/crm/query/SystemQuery.java:8`
- `dealer-server/src/main/java/com/autodealer/crm/query/SystemQuery.java:9`
- `dealer-server/src/main/java/com/autodealer/crm/query/SystemQuery.java:23`
- `dealer-server/src/main/java/com/autodealer/crm/web/SystemController.java:29`
- `dealer-server/src/main/java/com/autodealer/crm/web/SystemController.java:35`

问题：
`SystemQuery` 定义了系统配置相关字段，并继承 `BaseQuery`，但当前系统配置接口没有使用它。`SystemController` 的创建、更新、状态切换都直接接收 `TSystem` model。

影响：
- 文件存在会让后续开发误以为系统配置已有专用请求契约。
- 实际接口却绕过该 Query，导致字段校验、权限、审计和数据权限约定无法落在 Query 上。
- 直接接收 model 会把数据库字段暴露给外部请求，后续字段一增加就可能变成隐式 API。

建议：
- 如果短期不使用，删除 `SystemQuery`，降低维护噪音。
- 如果要保留，应把系统配置接口改成明确的 Request DTO，例如 `CreateSystemRequest`、`UpdateSystemRequest`、`ToggleSystemStatusRequest`。
- 系统配置不建议使用通用 Query 承担写命令，读查询和写命令应拆开。


### 54. `TranProductQuery` 当前没有接入业务链路，交易产品请求契约实际缺失

类型：冗余文件 / 缺失契约

位置：
- `dealer-server/src/main/java/com/autodealer/crm/query/TranProductQuery.java:8`
- `dealer-server/src/main/java/com/autodealer/crm/query/TranProductQuery.java:10`
- `dealer-server/src/main/java/com/autodealer/crm/query/TranProductQuery.java:13`
- `dealer-server/src/main/java/com/autodealer/crm/query/TranProductQuery.java:16`
- `dealer-server/src/main/java/com/autodealer/crm/dto/TranCreateRequest.java:25`
- `dealer-server/src/main/java/com/autodealer/crm/dto/TranCreateRequest.java:37`

问题：
`TranProductQuery` 定义了交易产品字段，但当前交易创建/更新实际使用的是 `TranCreateRequest.ProductDetail`。`TranProductQuery` 没有被 controller/service/mapper 作为请求对象使用。

影响：
- 交易产品实际契约分散在内部类里，缺少可复用、可校验、可文档化的请求 DTO。
- `TranProductQuery` 作为未使用文件，会误导后续开发以为已有完整交易产品查询/写入能力。
- 交易产品的 `quantity/price/productId` 校验没有统一入口。

建议：
- 删除未使用的 `TranProductQuery`，或改造成真正使用的 `TranProductRequest`。
- 交易创建和更新建议使用独立 DTO：`CreateTranRequest`、`UpdateTranRequest`，其中产品明细使用 `TranProductItemRequest`。
- 不建议把 Query 用作写命令；Query 只表达筛选条件。


### 56. 商品库存存在两个入库入口和两个内部 `RestockRequest`

类型：重复入口 / 业务边界不清

位置：
- `dealer-server/src/main/java/com/autodealer/crm/web/ProductController.java:60`
- `dealer-server/src/main/java/com/autodealer/crm/web/ProductController.java:66`
- `dealer-server/src/main/java/com/autodealer/crm/web/ProductStockController.java:13`
- `dealer-server/src/main/java/com/autodealer/crm/web/ProductStockController.java:22`
- `dealer-server/src/main/java/com/autodealer/crm/web/ProductStockController.java:36`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/ProductServiceImpl.java:90`

问题：
`ProductController` 暴露 `/api/products/stock/restock`，`ProductStockController` 暴露 `/api/productstock/restock`，两个接口都调用 `productService.restock(...)`。两个 controller 内部还各自定义了一个结构相同的 `RestockRequest`。

影响：
- 同一业务动作存在两个 API，权限、审计、限流、前端调用和接口文档都会分叉。
- 后续修复入库校验时容易只改一个入口，另一个入口继续放过非法请求。
- 内部类 DTO 无法被统一校验和复用。

建议：
- 保留一个入库入口，另一个删除或做兼容迁移。
- 抽出独立 DTO：`RestockRequest`，并加 `productId` 必填、`quantity > 0`、`remark` 长度限制。
- 库存记录查询可以保留在 `ProductStockController`，入库动作也可以统一归它管理，但需要明确模块边界。


### 58. 操作日志只有 model/mapper，没有 service/aspect 写入链路

类型：缺失业务文件 / 审计缺失

位置：
- `dealer-server/src/main/java/com/autodealer/crm/model/TOperationLog.java:12`
- `dealer-server/src/main/java/com/autodealer/crm/mapper/TOperationLogMapper.java:9`
- `dealer-server/src/main/resources/mapper/TOperationLogMapper.xml:17`

问题：
项目已经定义 `TOperationLog`、`TOperationLogMapper` 和 XML insert，但没有对应的 `OperationLogService`、`OperationLogAspect` 或 controller/service 调用链路。

影响：
- 当前审计能力只停留在数据库和 mapper 层，业务动作不会自动写日志。
- 字典删除、用户删除、商品入库、交易审批、退款、导入导出等关键动作无法追溯。
- 这不是单纯“多余文件”，而是“已建表但业务功能缺半截”。

建议：
- 补 `OperationLogService` 负责写入操作日志。
- 补 `OperationLogAspect` 或明确的 service 调用，覆盖关键写操作。
- 日志内容至少包含：操作人、模块、动作、业务 ID、变更摘要、IP、创建时间。
- 如果近期不做审计，应明确标记该 mapper/model 未接入，避免误以为系统已有审计。




## 架构整改建议：推荐目录结构

类型：项目规范化 / 架构演进 / 可维护性

背景：
当前 `crm` 包整体采用横向技术分层：

```text
web
service
service/impl
mapper
model
query
dto
manager
config
util
result
```

这种结构在项目早期简单直观，但随着业务模块增加，会出现以下问题：
- 同一业务模块分散在多个顶层目录中，理解一个功能需要跨目录跳转。
- DTO、Query、Model、Result 边界容易混用。
- 基础设施能力和业务能力混在一起，例如 Redis、JWT、Excel、数据权限。
- 新增业务时缺少统一骨架，容易继续堆文件。
- 权限、审计、异常、缓存等横切能力难以统一治理。

建议采用“模块化单体 + 轻量 DDD 分层”的 Java/Spring Boot 目录结构。该结构不是为了微服务而设计，而是为了让单体项目本身更正规、更可持续、更容易扩展。

### 模块内部职责

每个业务模块建议统一使用以下骨架：

```text
modules/{module-name}
├── controller
├── application
├── domain
│   ├── entity
│   ├── enums
│   └── service
├── infrastructure
│   ├── mapper
│   └── repository
├── dto
│   ├── request
│   ├── response
│   └── query
├── converter
└── facade
```

职责说明：
- `controller`：HTTP 接口层，只负责参数接收、基础校验、调用 application。
- `application`：应用服务层，负责一个完整业务用例、事务边界、跨模块编排。
- `domain`：领域层，负责核心业务规则、状态机、领域对象。
- `infrastructure`：基础设施适配层，负责 MyBatis mapper、repository、外部存储等技术实现。
- `dto/request`：创建、更新、状态变更等写请求。
- `dto/response`：返回给前端的响应对象。
- `dto/query`：列表筛选、分页查询条件。
- `converter`：DTO、entity、response 之间的转换。
- `facade`：暴露给其他模块调用的稳定入口，避免跨模块直接调用 mapper。

### 当前项目迁移原则

1. 不建议一次性全量搬迁所有文件，应先制定规范，再按模块逐步迁移。
2. 新增代码优先使用新目录结构，旧代码逐步迁。
3. 先整理横切能力：
   - `common/response`
   - `common/exception`
   - `security/currentuser`
   - `infrastructure/cache`
   - `infrastructure/excel`
4. 再迁移业务边界最混乱的模块：
   - `transaction`
   - `product`
   - `customer`
   - `dictionary`
   - `user`
5. 模块之间禁止直接调用对方 mapper。
6. 模块之间如需协作，优先调用对方 `facade` 或应用服务接口。
7. 写接口不直接接收数据库 model。
8. Query 只用于查询，不承担创建/更新命令。
9. 审计、权限、异常、缓存、导入导出应作为统一基础能力治理。

### 可接受的简化版

如果短期觉得轻量 DDD 分层过重，也可以采用过渡版本：

```text
modules/{module-name}
├── controller
├── service
├── service/impl
├── mapper
├── model
├── dto
│   ├── request
│   ├── response
│   └── query
├── converter
└── enums
```

但最终更推荐逐步演进到：

```text
modules/{module-name}
├── controller
├── application
├── domain
├── infrastructure
├── dto
├── converter
└── facade
```

这样项目会从“按技术层堆文件”转为“按业务能力组织代码”，更适合长期管理和后续开发扩展。
