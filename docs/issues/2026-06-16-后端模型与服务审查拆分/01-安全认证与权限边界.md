## 问题详情

### 21. 自定义 Token 过滤器与 Spring Security 放行规则不一致

类型：认证链路 / 可用性 / 安全边界

位置：
- `dealer-server/src/main/java/com/autodealer/crm/config/SecurityConfig.java:58`
- `dealer-server/src/main/java/com/autodealer/crm/config/SecurityConfig.java:60`
- `dealer-server/src/main/java/com/autodealer/crm/config/SecurityConfig.java:61`
- `dealer-server/src/main/java/com/autodealer/crm/config/filter/TokenVerifyFilter.java:40`
- `dealer-server/src/main/java/com/autodealer/crm/config/filter/TokenVerifyFilter.java:58`

问题：
`SecurityConfig` 放行了 `POST /api/login`、`/api/login/free` 和所有 `OPTIONS` 请求，但 `TokenVerifyFilter` 只跳过 `Constants.LOGIN_URI`，也就是 `/api/login`。因此：
- `/api/login/free` 虽然在 Spring Security 中 `permitAll`，仍会被自定义过滤器要求 token。
- CORS 预检 `OPTIONS` 也可能被过滤器返回 `TOKEN_IS_EMPTY`。

影响：
- 前端跨域请求可能随机失败，尤其是正式部署和带自定义请求头时。
- 配置层看似放行，实际运行链路却没有放行，安全规则不可预测。

建议：
- 让 `TokenVerifyFilter` 与 Security 白名单共用同一份 matcher 规则。
- 明确跳过 `OPTIONS` 和所有公开接口。
- 对认证失败返回统一 HTTP 状态和业务码。


### 22. JWT payload 中包含密码哈希

类型：安全问题 / 敏感信息泄露

位置：
- `dealer-server/src/main/java/com/autodealer/crm/config/handler/MyAuthenticationSuccessHandler.java:34`
- `dealer-server/src/main/java/com/autodealer/crm/config/handler/MyAuthenticationSuccessHandler.java:37`
- `dealer-server/src/main/java/com/autodealer/crm/util/JWTUtils.java:48`

问题：
登录成功后创建 `tokenUser`，并把 `loginPwd` 写入 JWT 的 `user` claim。即使是 BCrypt 哈希，也不应该暴露给浏览器、日志、代理和任何拿到 token 的第三方。

影响：
- 密码哈希成为客户端可见数据，扩大撞库和离线攻击面。
- token 一旦被记录到日志，等同于同时泄露用户身份信息和密码哈希。

建议：
- JWT 只保存 `userId`、登录名、必要角色/权限版本号或 session id。
- 密码哈希只存在数据库和 Spring Security 内部认证流程中。


### 23. JWT 有效期与 Redis 登录态有效期冲突

类型：认证链路 / 业务可用性

位置：
- `dealer-server/src/main/java/com/autodealer/crm/util/JWTUtils.java:23`
- `dealer-server/src/main/java/com/autodealer/crm/constant/Constants.java:17`
- `dealer-server/src/main/java/com/autodealer/crm/constant/Constants.java:20`
- `dealer-server/src/main/java/com/autodealer/crm/config/handler/MyAuthenticationSuccessHandler.java:53`
- `dealer-server/src/main/java/com/autodealer/crm/config/filter/TokenVerifyFilter.java:133`

问题：
JWT 自身过期时间固定为 24 小时；Redis 中 remember-me 登录态设置为 7 天，普通登录为 30 分钟。过滤器只刷新 Redis TTL，不会续签 JWT。

影响：
- 勾选 remember-me 后，Redis 仍保留 7 天，但 JWT 24 小时后已失效。
- 普通登录的 JWT 仍可校验 24 小时，但 Redis 30 分钟后失效，行为由两套过期机制共同决定。
- 异步刷新逻辑还在后台线程读取 `HttpServletRequest`，请求结束后再访问 request 对象不稳。

建议：
- 统一 token 生命周期策略：短 JWT + refresh token，或 Redis session id + 服务端 TTL。
- 刷新时捕获 `rememberMe` 字符串值，不在异步线程访问 request。


### 24. Excel 导出接口从 URL 参数读取 token

类型：安全问题 / 凭证泄露

位置：
- `dealer-server/src/main/java/com/autodealer/crm/config/filter/TokenVerifyFilter.java:46`
- `dealer-server/src/main/java/com/autodealer/crm/config/filter/TokenVerifyFilter.java:48`
- `dealer-server/src/main/java/com/autodealer/crm/constant/Constants.java:31`
- `dealer-server/src/main/java/com/autodealer/crm/web/CustomerController.java:86`

问题：
`/api/exportExcel` 会从请求参数 `Authorization` 读取 token。URL 参数会出现在浏览器历史、服务器访问日志、反向代理日志和 Referer 中。

影响：
- token 泄露概率明显高于请求头传递。
- 导出功能越常用，凭证出现在日志中的概率越高。

建议：
- 导出也统一使用 `Authorization` 请求头。
- 如果浏览器下载限制导致前端处理困难，可以先申请一次性导出任务 id，再用短期下载凭证下载文件。


### 25. 大量核心控制器只有登录校验，没有方法级权限

类型：授权缺口 / 业务安全

位置：
- `dealer-server/src/main/java/com/autodealer/crm/web/ActivityController.java:26`
- `dealer-server/src/main/java/com/autodealer/crm/web/ActivityController.java:38`
- `dealer-server/src/main/java/com/autodealer/crm/web/ActivityController.java:51`
- `dealer-server/src/main/java/com/autodealer/crm/web/ActivityRemarkController.java:17`
- `dealer-server/src/main/java/com/autodealer/crm/web/ClueRemarkController.java:17`
- `dealer-server/src/main/java/com/autodealer/crm/web/DicController.java:40`
- `dealer-server/src/main/java/com/autodealer/crm/web/ProductController.java:31`
- `dealer-server/src/main/java/com/autodealer/crm/web/ProductCategoryController.java:29`
- `dealer-server/src/main/java/com/autodealer/crm/web/ProductPromotionController.java:29`
- `dealer-server/src/main/java/com/autodealer/crm/web/ProductStockController.java:22`
- `dealer-server/src/main/java/com/autodealer/crm/web/SystemController.java:28`
- `dealer-server/src/main/java/com/autodealer/crm/web/SystemMonitorController.java:23`

问题：
Spring Security 当前对这些接口只要求 `authenticated()`。活动、备注、字典、商品、商品分类、促销、库存、系统配置、系统监控等核心接口缺少 `@PreAuthorize`。

影响：
- 任意已登录用户可能新增、修改、删除商品/系统配置/字典数据。
- 系统监控接口会向普通用户暴露 CPU、内存、磁盘、网络和 JVM 信息。
- 权限模型没有覆盖完整后端能力，前端隐藏按钮不能作为后端保护。

建议：
- 为每个控制器建立权限矩阵：list/view/add/edit/delete/export/import/refresh/monitor。
- 所有写接口必须有方法级权限。
- 系统监控和系统配置接口应限制到管理员或明确的 system 权限。


### 26. 退出登录使用 GET 且处理器未处理空认证

类型：认证链路 / 稳定性

位置：
- `dealer-server/src/main/java/com/autodealer/crm/config/SecurityConfig.java:77`
- `dealer-server/src/main/java/com/autodealer/crm/config/SecurityConfig.java:79`
- `dealer-server/src/main/java/com/autodealer/crm/config/handler/MyLogoutSuccessHandler.java:31`
- `dealer-server/src/main/java/com/autodealer/crm/config/handler/MyLogoutSuccessHandler.java:33`

问题：
退出登录配置为 `GET /api/logout`，且 success handler 直接使用 `authentication.getPrincipal()` 并强转为 `TUser`，没有判空和类型判断。

影响：
- GET 退出可以被链接、图片或预加载误触发。
- token 过期或认证上下文为空时可能抛出空指针或类型转换异常。

建议：
- 改为 `POST /api/logout`。
- 先从认证上下文或 token 安全解析用户 id，空认证也应返回幂等成功或明确失败。


### 27. 登录失败直接返回底层异常消息

类型：安全问题 / 错误处理

位置：
- `dealer-server/src/main/java/com/autodealer/crm/config/handler/MyAuthenticationFailureHandler.java:23`
- `dealer-server/src/main/java/com/autodealer/crm/config/handler/MyAuthenticationFailureHandler.java:26`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/UserServiceImpl.java:60`

问题：
登录失败时把 `exception.getMessage()` 直接返回前端，`UserServiceImpl` 对不存在账号返回“登录账号不存在”。

影响：
- 可以枚举系统中已存在的登录账号。
- 底层异常文案会成为外部 API 契约，后续难以统一。

建议：
- 对外统一返回“账号或密码错误”。
- 内部日志保留具体失败原因。


### 28. 数据权限切面依赖 request 和第一个参数，且会静默失效

类型：授权缺口 / 数据权限 / SQL 风险

位置：
- `dealer-server/src/main/java/com/autodealer/crm/aspect/DataScopeAspect.java:43`
- `dealer-server/src/main/java/com/autodealer/crm/aspect/DataScopeAspect.java:51`
- `dealer-server/src/main/java/com/autodealer/crm/aspect/DataScopeAspect.java:57`
- `dealer-server/src/main/java/com/autodealer/crm/aspect/DataScopeAspect.java:67`
- `dealer-server/src/main/resources/mapper/TUserMapper.xml:68`
- `dealer-server/src/main/resources/mapper/TActivityMapper.xml:76`

问题：
切面直接从 `RequestContextHolder` 取 request，并再次解析 JWT，而不是使用 SecurityContext。它假设被切方法第一个参数是 `BaseQuery`；如果不是，就不会加数据权限条件。最终条件通过 `filterSQL` 字符串拼到 mapper 中。

影响：
- 非 Web 调用、异步调用或参数顺序变化可能导致异常或数据权限失效。
- 数据权限依赖字符串拼接，前文第 16 条的 SQL 注入/拼接风险会进一步扩大。

建议：
- 从 SecurityContext 获取当前用户。
- 注解应声明参数名或统一查询对象位置，无法注入数据权限时应失败而不是静默放行。
- 使用结构化查询条件，不把 SQL 字符串暴露在 query 对象上。

### 60. 缺少统一当前登录用户上下文，导致 JWT 解析和 principal 强转散落各处

类型：缺失基础设施 / 认证上下文

位置：
- `dealer-server/src/main/java/com/autodealer/crm/aspect/DataScopeAspect.java:51`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/UserServiceImpl.java:132`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/ActivityRemarkServiceImpl.java:36`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/ClueRemarkServiceImpl.java:36`
- `dealer-server/src/main/java/com/autodealer/crm/web/TranController.java:59`
- `dealer-server/src/main/java/com/autodealer/crm/web/TranController.java:60`

问题：
当前系统有多种获取当前用户的方式：service 直接解析 token，aspect 直接解析 header，controller 直接从 `SecurityContext` 强转 principal。这些方式没有统一入口。

影响：
- token 格式、Bearer 前缀、过期异常、匿名 principal 等处理逻辑重复且不一致。
- 后续如果调整认证机制，需要改很多文件。
- 当前用户来源不统一，会影响审计字段和数据权限的可信度。

建议：
- 补统一组件，例如 `CurrentUserProvider` 或 `LoginUserContext`。
- 对外提供 `getCurrentUser()`、`getCurrentUserId()`、`hasRole()` 等方法。
- service 层不直接依赖原始 token，controller/aspect 也不直接解析 JWT。


### 63. 缺少结构化数据权限条件对象，当前依赖 `filterSQL` 字符串

类型：缺失基础设施 / 数据权限

位置：
- `dealer-server/src/main/java/com/autodealer/crm/query/BaseQuery.java:16`
- `dealer-server/src/main/java/com/autodealer/crm/aspect/DataScopeAspect.java:67`
- `dealer-server/src/main/resources/mapper/TActivityMapper.xml:76`
- `dealer-server/src/main/resources/mapper/TUserMapper.xml:68`
- `dealer-server/src/main/resources/mapper/TClueRemarkMapper.xml:62`
- `dealer-server/src/main/resources/mapper/TActivityRemarkMapper.xml:51`

问题：
数据权限通过 `BaseQuery.filterSQL` 字符串注入，mapper 使用 `${filterSQL}` 拼接。缺少结构化的数据权限对象或白名单构建器。

影响：
- 数据权限条件和 SQL 语法绑定，难以测试和复用。
- 一旦 `filterSQL` 被外部传入或构造不当，就会形成 SQL 注入风险。
- 查询对象承载 SQL 片段，破坏 Query 作为请求条件的边界。

建议：
- 补 `DataScopeCondition` 或 `DataScopeCriteria`。
- 由后端白名单构建表别名、字段和用户 ID。
- mapper 使用固定 SQL 条件或安全参数，不直接拼接任意 SQL 字符串。


### 16. `filterSQL` 使用 `${}` 拼接，存在 SQL 注入扩散风险

类型：安全 / SQL 编写

位置：
- `dealer-server/src/main/java/com/autodealer/crm/query/BaseQuery.java:16`
- `dealer-server/src/main/resources/mapper/TActivityMapper.xml:76`

问题：
`filterSQL` 是字符串字段，mapper 中用 `${filterSQL}` 直接拼接 SQL。如果该字段来源控制不严，容易引入 SQL 注入。

影响：
- 数据权限过滤可能被绕过。
- 影响所有复用 `BaseQuery` 的查询模式。

建议：
- 数据权限应通过受控条件对象或 MyBatis 参数化条件构造。
- 如必须使用 SQL 片段，只能由服务端白名单生成，禁止客户端传入。
