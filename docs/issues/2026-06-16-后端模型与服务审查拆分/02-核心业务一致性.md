# 核心业务一致性

来源：[后端模型与服务审查索引](../2026-06-16-后端模型与服务审查.md)

修复目标：修复交易、客户转换、库存、财务、用户账号这些会直接造成数据错误或业务损失的问题。

## 建议修复顺序

1. 1. 批量删除交易会绕过阶段限制，可能删除非待报价交易

2. 2. 客户转换接口信任请求体中的 createBy，审计字段可被伪造

3. 6. 退款逻辑可能重复恢复库存，也没有阻止重复退款

4. 7. 发票创建先推进交易阶段，再检查是否已开票

5. 8. 交易创建没有写初始历史，阶段历史不完整

6. 36. 交易创建未校验产品列表为空

7. 37. 交易结算金额可以完全由前端覆盖

8. 38. 商品入库接口未校验数量，负数会被记录成“入库”

9. 40. 用户新增/删除缺少核心业务保护


## 问题详情

### 1. 批量删除交易会绕过阶段限制，可能删除非待报价交易

类型：业务逻辑 / 数据完整性

位置：
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/TranServiceImpl.java:393`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/TranServiceImpl.java:416`
- `dealer-server/src/main/resources/mapper/TTranMapper.xml:322`

问题：
`batchDeleteTransactions` 循环中只对 `QUOTATION` 阶段恢复库存和删除关联记录，非 `QUOTATION` 交易只是 `continue`。但循环结束后调用 `tranMapper.deleteByIds(ids)`，传入的仍是原始 `ids`，会把被跳过的非待报价交易一起物理删除。

影响：
- `PENDING`、`APPROVED`、`PAYMENT`、`COMPLETED` 交易可能被批量删除。
- 被跳过交易的产品、备注、发票、审批、支付记录不会同步清理，产生孤儿数据。
- 已完成交易也可能消失，影响统计、审计和财务记录。

建议：
- 构造 `deletableIds`，只删除实际通过阶段校验的交易。
- 如发现请求中包含不可删除状态，建议返回失败并明确提示。
- 进一步在 SQL 层增加带阶段条件的批量删除，避免 service 逻辑漏拦。


### 2. 客户转换接口信任请求体中的 createBy，审计字段可被伪造

类型：权限 / 审计 / 调用链

位置：
- `dealer-server/src/main/java/com/autodealer/crm/web/CustomerController.java:63`
- `dealer-server/src/main/java/com/autodealer/crm/manager/CustomerManager.java:41`
- `dealer-server/src/main/java/com/autodealer/crm/manager/CustomerManager.java:52`
- `dealer-server/src/main/java/com/autodealer/crm/manager/CustomerManager.java:63`

问题：
客户转换入口没有从 `SecurityContext` 或 token 中获取当前用户，而是直接使用 `CustomerQuery.createBy`。调用方可以伪造 `createBy`，最终会写入线索编辑人、客户创建人、交易创建人、交易产品创建人。

影响：
- 审计链路不可信。
- 数据权限依赖 `create_by` 时，可能造成越权查看或隐藏数据。
- 后续追责、销售归属、统计报表会失真。

建议：
- Controller 层统一从登录上下文获取当前用户 ID，并覆盖请求体中的操作人字段。
- Query/DTO 中不应暴露 `createBy` 作为客户端可写字段；如需要筛选，应使用单独的查询 DTO。


### 6. 退款逻辑可能重复恢复库存，也没有阻止重复退款

类型：业务逻辑 / 财务 / 库存

位置：
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/TranServiceImpl.java:539`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/TranServiceImpl.java:544`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/TranServiceImpl.java:570`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/TranServiceImpl.java:575`

问题：
`refundPayment` 只校验原支付状态是 `COMPLETED`，随后将原支付改为 `REFUNDED` 并恢复交易产品库存。并发请求下，两个事务都可能先读到 `COMPLETED`，分别创建负数退款记录并恢复库存。即使非并发，多个完成收款记录逐笔退款也会对同一批交易产品重复恢复库存。

影响：
- 库存可能被多次加回。
- 支付流水可能出现重复退款。
- 交易阶段可能被错误回退。

建议：
- 原支付状态更新应使用 CAS：`WHERE id = ? AND payment_status = 'COMPLETED'`。
- 库存恢复应绑定“交易取消”动作，而不是绑定“单笔支付退款”动作。
- 交易取消、退款、库存回滚需要明确状态机和幂等键。


### 7. 发票创建先推进交易阶段，再检查是否已开票

类型：业务逻辑 / 事务边界

位置：
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/TranServiceImpl.java:263`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/TranServiceImpl.java:270`

问题：
`createTranInvoice` 先把交易从 `APPROVED` 原子推进到 `PAYMENT`，随后才检查已有发票。如果历史数据已经存在发票但交易仍处于 `APPROVED`，会先改状态再抛异常。虽然当前方法带事务，普通异常会回滚，但逻辑顺序仍不稳，且未来若异常处理或事务配置变化，容易留下半完成状态。

影响：
- 逻辑可读性差，事务依赖隐蔽。
- 并发开票场景主要靠 `uk_invoice_no`，不是靠 `tran_id` 的唯一约束或业务幂等。

建议：
- 先校验交易存在、金额、是否已开票，再推进状态并插入发票。
- 对 `t_tran_invoice.tran_id` 增加唯一约束，或明确支持多张发票并设计拆票规则。


### 8. 交易创建没有写初始历史，阶段历史不完整

类型：审计 / 业务完整性

位置：
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/TranServiceImpl.java:64`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/TranServiceImpl.java:596`
- `dealer-server/src/main/resources/CarDealerCRM.sql:1005`

问题：
`createTransaction` 插入 `t_tran` 后没有写入 `t_tran_history`。后续审批、开票、收款会写历史，但初始 `QUOTATION` 状态缺失。

影响：
- 交易历史不是完整审计链。
- 问题排查时无法判断初始创建金额、预计日期、创建人。

建议：
- 创建交易后立即写入初始历史。
- 历史表中的 `stage` 存储应统一为枚举 code，而不是有时 label、有时 code。

## 中优先级问题


### 36. 交易创建未校验产品列表为空

类型：业务逻辑 / 请求校验

位置：
- `dealer-server/src/main/java/com/autodealer/crm/web/TranController.java:57`
- `dealer-server/src/main/java/com/autodealer/crm/web/TranController.java:81`

问题：
创建交易时直接 `request.getProducts().stream()`，没有判断 `request`、`products` 是否为空，也没有校验产品数量、价格、productId。

影响：
- products 为空会触发 NPE。
- 非法数量/价格可能进入 service，再影响库存和交易金额。

建议：
- 为 `TranCreateRequest` 增加 Bean Validation。
- 创建交易要求至少一个产品，数量大于 0，价格非负，产品存在且状态可售。


### 37. 交易结算金额可以完全由前端覆盖

类型：业务逻辑 / 财务风险

位置：
- `dealer-server/src/main/java/com/autodealer/crm/web/TranController.java:168`
- `dealer-server/src/main/java/com/autodealer/crm/web/TranController.java:180`
- `dealer-server/src/main/java/com/autodealer/crm/web/TranController.java:195`
- `dealer-server/src/main/java/com/autodealer/crm/web/TranController.java:198`

问题：
结算接口允许前端传入 `amount`，后端只校验非负数，然后直接把交易金额更新为该值并进入待审批。

影响：
- 客户端可把金额改得低于产品合计或促销规则。
- 审批看到的是已被客户端覆盖的金额，缺少后端计算依据。

建议：
- 后端根据交易产品、促销、折扣规则计算结算金额。
- 如果允许人工改价，应记录改价原因、改价人、审批链和原始金额。


### 38. 商品入库接口未校验数量，负数会被记录成“入库”

类型：业务逻辑 / 库存一致性

位置：
- `dealer-server/src/main/java/com/autodealer/crm/web/ProductController.java:60`
- `dealer-server/src/main/java/com/autodealer/crm/web/ProductStockController.java:22`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/ProductServiceImpl.java:90`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/ProductServiceImpl.java:97`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/ProductServiceImpl.java:98`

问题：
两个控制器都暴露了 restock 入口，均未校验 `productId` 和 `quantity`。service 直接 `updateStock(productId, quantity)`，并把库存记录类型写成“入库”。

影响：
- 传负数时可能形成“入库记录减少库存”的异常业务记录。
- 重复入口增加权限、审计和前端调用混乱。

建议：
- 入库 quantity 必须大于 0。
- 出库/调整库存应走单独业务动作，并使用明确的库存变动类型。
- 合并重复入口或明确分工。


### 40. 用户新增/删除缺少核心业务保护

类型：业务逻辑 / 权限与数据完整性

位置：
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/UserServiceImpl.java:121`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/UserServiceImpl.java:128`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/UserServiceImpl.java:161`
- `dealer-server/src/main/java/com/autodealer/crm/service/impl/UserServiceImpl.java:167`
- `dealer-server/src/main/java/com/autodealer/crm/web/UserController.java:105`

问题：
新增用户没有在 service 层检查登录名/手机号/邮箱唯一性，也没有明确密码必填和密码策略。删除用户直接物理删除，没有保护当前登录用户、管理员账号、最后一个管理员，也没有检查该用户是否仍是线索/客户/活动/交易负责人。

影响：
- 用户数据可能违反唯一性或产生重复账号。
- 删除负责人会造成历史业务数据失去可解释的归属。
- 批量删除接口对删除 0 行也可能返回成功。

建议：
- 用户删除优先禁用账号，不直接物理删除。
- 删除/禁用前检查业务引用和管理员保护规则。
- 新增和更新用户时统一唯一性校验、密码策略和角色分配规则。
