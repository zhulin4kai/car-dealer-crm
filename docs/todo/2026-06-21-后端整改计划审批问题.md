### P0-2 交易整改核心入口仍使用旧 Map 契约，并继续信任客户端结算金额

关联 Plan：05。

证据：

- `TranController.settle`（约 138-176 行）仍接收 `Map<String, Object>`，并直接采用客户端传入的 `amount` 作为交易结算金额。
- `approve`、`updateInvoiceStatus`、`batchDelete` 同样仍接收无类型 Map。
- 已新增的 `CreateTranRequest`、`SettleTranRequest`、`ApproveTranRequest`、`BatchDeleteTranRequest`、`UpdateInvoiceStatusRequest` 等 DTO 没有生产调用。

影响：客户端仍可覆盖服务端应计算的应付金额；错误字段类型只能在运行时失败；Plan 05 的金额可信来源和 DTO 目标均未完成。

修复要求：

1. 将新增交易 DTO 真正接入 Controller 和 Service，增加 Bean Validation。
2. 结算金额由服务端根据商品快照和明确优惠规则计算，客户端只能提交优惠依据或确认信息，不能提交最终可信金额。
3. 增加金额篡改、缺字段、类型错误和合法结算测试。

详细实施方案：

1. 修改 `TranController`：
   - `create` 改为 `@Valid @RequestBody CreateTranRequest`；
   - `update` 改为 `@Valid @RequestBody UpdateTranRequest`；
   - `settle` 只接收路径参数 `id`，不再接收请求体；
   - `approve` 改为 `@Valid @RequestBody ApproveTranRequest`；
   - `updateInvoiceStatus` 改为 `@Valid @RequestBody UpdateInvoiceStatusRequest`；
   - `batchDelete` 改为 `@Valid @RequestBody BatchDeleteTranRequest`；
   - `recordPayment`、`createInvoice` 分别接入 `CreatePaymentRequest`、`CreateTranInvoiceRequest`；
   - 删除上述方法中的 `Map.get()`、强制类型转换、手工空值判断和内部请求类。
2. 删除 `SettleTranRequest`。当前系统没有正式优惠审批模型，空 DTO 没有存在价值；结算接口不得接受客户端最终金额，前端调用时不发送请求体。
3. 修改 `TranService.settleTransaction` 和 `TranServiceImpl.settleTransaction`：只接收 `tranId` 和服务端操作者；在同一事务内查询交易及交易商品快照，按 `price × quantity` 计算金额。商品为空、价格/数量为空或非正数时抛出稳定 `BusinessException`，不得继续结算。
4. 结算更新必须使用 Mapper CAS：`WHERE id = #{id} AND stage = 'QUOTATION'`。影响行数不是 1 时返回 `409 + TRAN_STATE_CONFLICT`，不得返回 `R.OK(false)`。
5. Controller 只做 DTO、权限和 Service 调用；金额计算、阶段判断、历史写入放在 Service。成功后交易金额、阶段和历史记录必须在同一事务提交。
6. 同步修改 `dealer-web/src/modules/tran/api/tran-api.ts`、交易类型和调用页面，删除前端传 `amount` 的逻辑。前端展示金额可以计算，但不能作为服务端事实。
7. 新增或更新测试：
   - 即使构造请求额外携带伪造 `amount`，最终金额仍完全等于服务端商品快照合计；
   - 正常结算金额等于服务端商品快照合计；
   - 空商品、零/负数量、非法旧阶段失败且交易和历史不变；
   - CAS 更新为 0 时返回冲突；
   - DTO 缺字段和类型错误返回 400；
   - 批量删除空 IDs 和审批空意见由 Bean Validation 拒绝。

禁止事项：不要保留旧 Map 入口与新 DTO 入口并行；不要在 Controller 中重新拼 `TTran`；不要为了兼容前端继续接受可信 `amount`。

### P0-3 线索 Excel 导入仍走旧流程，新校验链完全未接入

关联 Plan：07。

证据：

- `ClueController.importExcel`（约 34-41 行）直接读取 `MultipartFile.getInputStream()`，未校验空文件、扩展名、Content-Type、大小和行数。
- `ClueServiceImpl.importExcel`（约 64-71 行）仍直接使用旧 `UploadDataListener`，返回 `void`。
- 新增的 `ClueImportValidator` 入度为 0，没有生产调用；`ImportContext`、`ImportResult` 和逐行错误 DTO 没有接入导入接口。
- Excel converter 仍读取 `DealerCRMApplication.cacheMap`。

影响：未知字典/商品仍可能沿旧转换路径处理，导入失败无法定位行和字段，也无法证明“先完整校验、再单事务写入”的全成功语义。

修复要求：

1. 接入 `ImportContext + ClueImportValidator + ImportResult`，移除旧全局缓存依赖。
2. Controller 完成文件边界校验，Service 完成全量解析校验后单事务写入。
3. 补齐任一行失败时零写入、重复手机号、未知字典/商品、公式内容和空文件测试。

详细实施方案：

1. 修改 `ClueController.importExcel`：
   - 参数使用 `@RequestPart("file") MultipartFile file`；
   - 文件为 `null` 或 `isEmpty()` 时返回 400；
   - 只允许 `.xlsx`；Content-Type 只接受标准 xlsx 类型或浏览器通用二进制类型；
   - 使用配置项限制文件大小，不在 Controller 写魔法数字；
   - 调用 Service 后返回 `R<ImportResult>`，不再固定返回空成功。
2. 修改 `ClueService.importExcel` 签名为 `ImportResult importExcel(InputStream inputStream)`，实现方法添加 `@Transactional(rollbackFor = Exception.class)`。
3. 导入开始时一次性从 `DicService`/Mapper、负责人查询、活动查询和商品查询构造 `ImportContext`。扩充 `ImportContext`，增加负责人名称到用户 ID、活动名称到活动 ID 的只读映射。禁止读取 `DealerCRMApplication.cacheMap`，禁止让 converter 在解析过程中查询数据库。
4. EasyExcel 第一阶段只解析 `ClueExcelRaw` 到内存列表。新增一个仅收集原始行的 Listener；此 Listener 不调用 Mapper、不批量插入、不转换成 `-1`。
5. 补全 `ClueImportValidator`：当前实现只校验手机号和部分文本，并没有“transform”。必须同时校验并转换负责人、活动、称呼、贷款状态、意向状态、意向商品、线索状态和来源；匹配不到时生成包含 Excel 实际行号、列名和安全原因的 `ImportRowError`。
6. 不要让 `ImportResult` 承载待写实体。新增仅在 Service 内部使用的 `ValidatedClueImport`，包含 `ImportResult` 和 `List<TClue>`。只有 `failedRows == 0` 时才进入批量写入。
7. 写入前一次性查询数据库中已存在的手机号，与文件内重复一起汇总为错误；并发时仍依赖数据库唯一约束，将 `DuplicateKeyException` 转成稳定导入冲突错误并回滚全部写入。
8. 批量写入前检查集合非空；Mapper 返回影响行数必须等于待写行数，否则抛异常回滚。写入成功后设置 `importedCount=totalRows`。
9. 删除旧 `UploadDataListener` 的写数据库职责和所有 converter 对静态缓存的读取。若 converter 已无调用则删除；不能保留两套导入链。
10. 测试至少覆盖：空文件、错误扩展名、超限文件、空工作表、超过 1000 行、公式前缀、同文件重复手机号、数据库重复手机号、未知字典、未知商品、任一行错误时零写入、全部合法时完整写入和返回数量准确。

完成标准：Controller 测试断言 HTTP 状态和 `ImportResult`；Service 集成测试在失败后查询 `t_clue` 确认为零新增。

### P1-1 Redis 安全配置仍被应用入口覆盖，旧 Redis API 也未删除

关联 Plan：03、07、10。

证据：

- `DealerCRMApplication`（约 18-48 行）仍实现 `CommandLineRunner`，启动后修改 `RedisTemplate`，并启用 `ObjectMapper.DefaultTyping.EVERYTHING`。
- 虽然新增了 `RedisConfig`，应用入口仍会再次修改同一个模板，安全配置没有真正收口。
- `RedisService` 和 `RedisServiceImpl` 仍存在。
- `DealerCRMApplication.cacheMap` 仍存在，并被 Excel converter 和 `DicServiceImpl.clearCache` 使用。
- `DicServiceImpl.clearCache(String pattern)`（约 238-256 行）忽略传入的 `pattern`，固定清理三组 Key。

影响：Redis 实际序列化行为不由唯一配置决定；全局内存缓存和 Redis 缓存继续并存，字典更新和导入可能读取到不一致数据。

修复要求：

1. 应用入口只保留启动职责，删除运行时 RedisTemplate 修改和 `cacheMap`。
2. 确认无调用后删除 `RedisService/RedisServiceImpl`。
3. converter 使用导入上下文，字典缓存只通过 `RedisKeys + RedisManager` 管理。
4. 增加实际 Bean 序列化配置测试，而不是只测试新配置类本身。

详细实施方案：

1. 修改 `DealerCRMApplication`：移除 `implements CommandLineRunner`、`RedisTemplate` 字段、`run()` 方法、`cacheMap` 和相关 Jackson/Redis import。类中只保留 `@SpringBootApplication`、`@MapperScan` 和 `main()`。
2. 保留 `RedisConfig` 作为唯一 `RedisTemplate<String, Object>` Bean。禁止其他位置再次调用 `setKeySerializer/setValueSerializer/activateDefaultTyping`。配置测试必须从 Spring Context 获取真实 `RedisTemplate`，断言 key/value/hash serializer 类型。
3. 全项目搜索 `RedisService` 调用；当前只有接口和实现自身时，删除：
   - `service/RedisService.java`；
   - `service/impl/RedisServiceImpl.java`；
   - 对应旧测试。
4. 扩充 `RedisKeys`，只提供业务语义方法，不让调用方传任意 pattern。字典至少提供：类型详情、类型值列表、分页列表和 `dictCachePattern()`；调用方禁止手工拼 `dic:*`、`dict:*` 等平行 Key。
5. 将 `DicService.clearCache(String pattern)` 改成职责明确的私有/包内方法，例如 `evictDictionaryCaches()`；内部只调用 `redisManager.deletePattern(RedisKeys.dictCachePattern())`。删除形同虚设的 `pattern` 参数和 `DealerCRMApplication.cacheMap.clear()`。
6. Excel converter 不再访问 Redis 或静态 Map。按 P0-3 改成原始文本解析后，converter 若无调用直接删除。
7. Redis 故障处理：
   - 认证会话读取失败必须拒绝请求，不能当作会话不存在后继续匿名或放行；
   - 普通业务缓存读取失败可以回源数据库；
   - 缓存写入/失效失败只记录基础设施错误，不得重复执行业务数据库写入。
8. 测试覆盖 Object/List/Hash、TTL、删除、SCAN 模式删除和未知类型反序列化失败；认证测试继续覆盖 Redis 会话缺失、禁用账号和登出失效。

禁止事项：不要保留 `RedisConfig` 和 `DealerCRMApplication.run()` 两套配置；不要为了测试方便恢复 unrestricted `DefaultTyping.EVERYTHING`；不要新增第三套缓存封装。

### P1-2 多个模块只创建了 DTO，但 Controller 仍直接接收 Model 或内部类

关联 Plan：08、10、11，以及 Plan 07 的备注接口。

证据：

- `CreateActivityRemarkRequest`、`CreateClueRemarkRequest` 无生产调用。

影响：客户端仍可绑定持久化字段，Bean Validation 和写入白名单没有落地；商品重复入库入口依旧存在。

修复要求：按 Plan 08、10、11 和备注契约逐一接入 DTO，删除重复内部类和重复入口，并为每个写接口增加请求校验测试。

详细实施方案：

1. 商品模块：
   - `ProductController.addProduct/updateProduct` 分别改为 `@Valid CreateProductRequest/UpdateProductRequest`；Service 内显式转换为 `TProduct`，服务端设置 ID、状态和审计字段；
   - 删除 `ProductController.restock` 和两个 Controller 中的内部 `RestockRequest`；
   - 只保留 `ProductStockController.POST /api/product/stock/restock`，接收公共 `@Valid RestockRequest`；
   - `RestockRequest.productId` 必填，`quantity` 必须大于 0，`remark` 限长；Service 原子增加库存并写库存流水，任一步失败全部回滚；
   - 分类和促销创建/更新分别接入已有 Request DTO，禁止直接接收 Model。
2. 字典模块：
   - `DicController` 的创建/更新接口分别接入 `CreateDicTypeRequest`、`UpdateDicTypeRequest`、`CreateDicValueRequest`、`UpdateDicValueRequest` 并加 `@Valid`；
   - Controller 不再接收 `TDicType/TDicValue`；Service 只复制白名单字段，ID 从路径或更新 DTO 获取，`createBy/editBy` 来自 `CurrentUserProvider`；
   - 删除前调用统一引用检查；存在引用时抛 `DIC_IN_USE`，禁止删除任何备注或历史业务数据；
   - typeCode/valueCode 使用稳定 code，并与 P0-1 的数据库唯一约束一致。
3. 系统模块：
   - `SystemController.create/update/toggle` 分别接入 `CreateSystemRequest`、`UpdateSystemRequest`、`ToggleSystemStatusRequest`，全部 `@Valid`；
   - 返回 `SystemResponse`，不直接返回 `TSystem`；
   - 状态切换使用路径 ID + DTO 目标状态，Mapper SQL 带旧状态条件，影响行数为 0 返回冲突；
   - 删除未使用 `SystemQuery` 和空的缓存清理代码。
4. 活动/线索备注：
   - 创建接口接入 `CreateActivityRemarkRequest/CreateClueRemarkRequest`；

### P1-3 统一响应和异常治理没有完成

关联 Plan：01。

证据：

- `result/Result.java` 仍存在，`ResultTest` 也仍在执行，项目没有只保留 `R`。
- `GlobalExceptionHandler.handRuntimeException`（约 40-45 行）仍把 `RuntimeException.getMessage()` 直接返回客户端。
- 生产代码中仍有大量裸 `RuntimeException`，没有全部迁移到 `BusinessException + CodeEnum`。

影响：业务错误和系统错误仍可能混成 code 500，并把内部异常文本返回客户端；这也解释了部分集成测试期望权限/业务 code、实际得到 500 的现象。

修复要求：

1. 删除无调用的 `Result` 及其测试，只保留 `R`。
2. `BusinessException` 单独映射稳定 HTTP 状态和业务 code；未知 `RuntimeException` 返回统一安全错误并记录完整异常。
3. 优先迁移本次 Plan 涉及的 Service 裸异常，不要求一次清理完全无关模块。

详细实施方案：

1. 删除 `result/Result.java` 和 `ResultTest.java`。删除前用代码图确认无生产调用；禁止把任何 Controller 改回 `Result`。
2. 保留 `R<T>` 的固定结构：成功 `code=200`，失败 code 来自 `CodeEnum`，空 data 序列化规则保持现有前端可解析行为。
3. 修改 `GlobalExceptionHandler` 的处理顺序：
   - `BusinessException`：使用异常携带的 `CodeEnum`、安全文案和对应 HTTP 状态；
   - `MethodArgumentNotValidException/BindException/ConstraintViolationException`：HTTP 400，返回统一参数错误 code；
   - `HttpMessageNotReadableException`：HTTP 400，不返回 Jackson 原始 message；
   - `DataIntegrityViolationException/DuplicateKeyException`：已识别唯一冲突转稳定 409，无法识别的数据库错误返回 500；
   - `AccessDeniedException`：交给统一 403 契约；
   - 最终 `Exception`：记录一次完整堆栈，HTTP 500 + 统一系统错误。
4. 删除当前 `handRuntimeException` 直接返回 `e.getMessage()` 的逻辑。普通 `RuntimeException` 进入最终未知异常处理，客户端不得看到 SQL、类名或内部 message。
5. 在本次 Plan 涉及的 `TranServiceImpl`、`ClueServiceImpl`、`DicServiceImpl`、`ProductServiceImpl`、`SystemServiceImpl`、`UserServiceImpl`、`CustomerServiceImpl` 中，将预期业务失败改为 `BusinessException(CodeEnum...)`。不要机械替换工具类中用于参数断言的所有异常。
6. `CodeEnum` 缺少明确错误码时先补稳定枚举，再同步前端错误码类型和 `docs/api.md`。禁止继续用通用 `FAIL` 表达不存在、冲突、被引用和非法状态四种不同处理方式。
7. 测试同时断言 HTTP 状态、`$.code`、`$.msg` 是否为安全文案和 `$.data` 结构；未知异常测试必须断言响应不含原始异常文本。

完成标准：生产代码不存在 `Result`；`GlobalExceptionHandler` 不再向客户端返回任意 `RuntimeException.message`。

### P1-4 审计基础能力只接入了两个业务动作，横向审计目标未闭环

关联 Plan：04 至 11。

证据：全生产代码只有以下两个 `auditRecorder` 调用：

- `CustomerManager.convertCustomer`
- `CustomerController.exportExcel`

用户创建/编辑/状态/角色、交易审批/支付/退款/发票、商品与库存、字典、系统配置、活动/线索/备注等 Plan 明确要求的审计均未接入。

影响：关键状态变化无法从操作日志还原，Plan 04 提供的基础能力没有被后续模块使用。

修复要求：在各模块 Service 的成功事务路径接入审计；核心审计失败按业务要求回滚，普通读取审计可使用非阻断方式。补充成功、回滚和操作者来源测试。

详细实施方案：

1. 审计调用放在实际状态变化的 Service/Manager 事务中，禁止放在 Controller。将当前 `CustomerController.exportExcel` 保留为例外：导出是无事务读取，可在写出成功后用 `recordQuietly` 记录摘要。
2. 以下写动作必须调用 `auditRecorder.record(...)`，不使用 `recordQuietly`：
   - 用户：创建、资料修改、启用/禁用、锁定/解锁、密码修改、角色分配；
   - 交易：创建、结算、审批、重提、支付、退款、发票创建/状态变化、取消；
   - 商品：创建、编辑、上/下架、入库、扣减、恢复；
   - 客户/线索：转换、归属变化、手机号等关键资料修改；
   - 字典和系统配置：创建、编辑、状态变化、删除。
3. 调用顺序固定为：校验 → 业务数据库写入 → 检查影响行数 → 写审计 → 方法返回。审计 Mapper 使用同一个事务连接；审计插入失败抛异常，使业务和审计一起回滚。
4. 审计摘要只记录字段白名单：业务 ID、动作、旧状态、新状态、数量、原因 code。禁止记录密码、Token、完整手机号、完整邮箱、完整客户备注、支付敏感信息和整个 DTO。
5. `resourceId` 使用真实业务主键；支付、退款、库存审计摘要必须包含原业务流水 ID，不能只写中文描述。
6. `recordQuietly` 只允许用于不改变业务事实的读取事件，例如导出和监控访问。代码注释中列出允许场景，禁止写 Service 随意调用。
7. 每个模块至少增加：成功写入审计、业务中途失败无成功审计、审计插入失败业务回滚、操作者来自 `CurrentUserProvider` 四类测试。无需为普通列表查询增加审计。

完成标准：代码搜索应能在用户、交易、商品库存、客户线索、字典和系统 Service/Manager 中找到审计调用；不能仍然只有客户转换和导出两个调用点。
