# 汽车经销商客户关系管理系统业务方向

## 项目愿景

建设一个面向汽车经销商的客户关系管理系统，覆盖从线索获取、客户培育、商机推进、试驾体验、报价订单、收款开票、车辆交付到经营分析的完整业务闭环。

系统应帮助门店把分散的销售线索、客户资料、跟进任务、商机阶段、试驾安排、车辆商品、库存占用、订单履约、资金票据和经营数据统一管理起来，让销售过程可追踪、业务责任可识别、经营结果可衡量。

项目追求的是稳定、清晰、可信的业务管理能力，而不是单纯堆叠页面和功能。每个核心业务动作都应能回答：

- 谁发起了动作。
- 动作发生在什么业务对象上。
- 动作改变了什么业务状态。
- 动作是否符合业务规则。
- 动作产生了哪些后续影响。

## 业务定位

汽车经销商 CRM 围绕门店销售经营建立业务闭环，核心路径为：

线索进入 -> 客户沉淀 -> 商机培育 -> 跟进推进 -> 试驾体验 -> 报价协商 -> 订单成交 -> 收款开票 -> 车辆交付 -> 经营复盘。

系统的业务规格以商业化汽车经销场景为准，而不是以当前实现、页面数量或当前数据形态为准。现有实现不完整、状态不合理或业务边界混乱时，应以本目录业务规格作为改造方向。

## 目标用户

主要用户包括：

- 汽车经销商门店销售人员。
- 销售主管和门店管理者。
- 客服或市场活动跟进人员。
- 库存、商品和促销管理人员。
- 财务或收款确认人员。
- 交付协同人员。
- 系统管理员。

销售人员关注线索、客户、跟进、商机、试驾、报价和订单推进。

管理者关注团队业绩、销售漏斗、客户来源、成交效率、业务风险和异常数据。

商品和库存人员关注车辆商品、分类、库存数量、库存变化和库存预警。

财务人员关注订单金额、发票、收款、退款和应收情况。

交付协同人员关注车辆准备、资料移交、客户签收和交付异常。

系统管理员关注用户、权限、字典、登录安全、关键操作追溯和基础业务数据的可控性。

## 核心业务问题

汽车经销商的销售业务存在以下核心问题：

- 线索来源多，质量不一，缺少统一归集和持续跟进。
- 客户信息分散，客户状态、意向、历史沟通和交易记录难以形成完整视图。
- 销售过程依赖个人经验，商机阶段、试驾、报价、审批、收款、交付等环节容易缺少明确状态。
- 车辆商品、库存和订单之间联动不足，可能出现库存不准、重复占用或业务记录脱节。
- 权限、责任人和操作记录不清晰，业务归属、异常追溯和风险控制困难。
- 字典、状态、分类等基础数据不统一，导致统计口径和业务判断不一致。
- 管理者缺少可信的销售漏斗、来源分析、成交金额和业务进展数据。

## 业务功能地图

### 销售获客与客户经营

- 线索管理：统一接收、登记、去重、分配、跟进和转化销售线索。
- 客户管理：沉淀客户资料、意向、联系历史、归属责任和生命周期状态。
- 商机管理：管理客户明确购车意向后的销售机会、阶段推进、赢单和输单原因。
- 跟进任务：承载销售人员的待办、回访、预约、沟通记录和逾期管理。
- 试驾管理：管理试驾预约、车辆占用、客户到店、试驾结果和安全确认。
- 市场活动：管理获客活动、线索来源、活动成本、转化效果和 ROI 观察。

### 车辆、价格与库存

- 车辆商品：维护可销售车型、配置、指导价、展示状态和销售属性。
- 库存管理：管理可售车辆、库存占用、释放、变动、预警和库存周转。
- 促销政策：管理优惠政策、适用车型、时间范围、预算、核销和叠加限制。

### 成交履约与财务协同

- 报价订单：管理报价方案、价格审批、合同或订单确认和成交基础事实。
- 交易履约：管理订单成交后的履约状态、关闭、作废、变更和业务历史。
- 收款退款：管理订金、尾款、退款、应收状态、确认责任和资金风险。
- 发票管理：管理开票申请、开票状态、作废、红冲和票据业务关系。
- 交付管理：管理交车准备、交付确认、客户签收、资料移交和交付后回访。

### 管理治理与经营观察

- 经营分析：提供销售漏斗、来源转化、成交金额、库存周转、应收和活动效果。
- 用户权限：管理账号、角色、岗位职责、数据可见范围和关键业务动作授权。
- 数据字典：治理来源、状态、分类、原因、枚举口径等基础业务数据。
- 审计日志：记录登录和关键业务操作，支撑责任追溯与风险控制。

## 业务范围

线索业务覆盖线索登记、导入、查重、分配、跟进、状态维护、转化客户和转化商机。

客户业务覆盖客户资料维护、意向记录、历史跟进、关联线索、关联商机、关联订单和客户选择。

商机业务覆盖客户购车需求、意向车型、销售阶段、试驾、报价、赢单、输单和停滞管理。

跟进任务业务覆盖销售待办、首次联系、回访、邀约、延期、逾期和完成结果。

市场活动业务覆盖活动创建、活动维护、活动关联线索和活动效果观察。

试驾业务覆盖预约、到店、安全确认、试驾结果、取消、爽约和试驾后跟进。

商品业务覆盖车辆商品、分类、状态、价格、库存、促销政策和库存变动记录。

报价订单业务覆盖报价版本、价格审批、客户确认、订单创建、订单变更和订单取消。

交易履约业务覆盖订单状态、库存占用、资金票据进度、异常处理、关闭和完成。

收款与发票业务覆盖订金、尾款、退款、开票申请、开票结果、作废、红冲和票据交付。

交付业务覆盖车辆准备、资料准备、客户签收、交付异常和交付后回访。

基础治理与审计业务覆盖用户、权限、字典、登录记录和关键业务操作追溯。

## 主业务闭环

主业务闭环由 `docs/spec/业务闭环/` 统一约束：

- `00-业务对象关系与主流程.md` 定义线索、客户、商机、报价、订单、履约、收款、发票、库存、交付和经营分析之间的职责边界。
- `01-状态事件与完成条件.md` 定义核心业务事件、状态推进条件和交易完成条件。
- `02-异常取消与历史保留.md` 定义取消、作废、红冲、退款、异常和历史保留规则。

模块级 Spec 必须服从业务闭环 Spec。任何模块不得把上游业务对象、下游履约对象或并行协作状态压缩成自己的单一状态。

## 主要能力

### 线索到客户的转化能力

系统应支持从不同来源沉淀线索，并让线索持续流转为可管理的客户。

主要能力包括：

- 记录线索基础信息。
- 识别线索来源。
- 维护线索意向状态。
- 记录跟进内容。
- 防止重复线索造成业务混乱。
- 将有效线索转化为客户。
- 保留线索转化前后的业务关联。

### 客户全生命周期管理能力

系统应围绕客户形成完整业务视图，让客户资料、跟进记录、意向商品和交易历史相互关联。

主要能力包括：

- 维护客户基础资料。
- 查询客户历史行为。
- 关联客户交易。
- 识别客户负责人。
- 支持销售人员持续跟进。
- 支持管理者查看客户沉淀质量。

### 商机与跟进推进能力

系统应把客户购车需求沉淀为可推进、可管理、可衡量的商机。

主要能力包括：

- 创建和维护商机。
- 管理商机阶段。
- 记录下一步跟进任务。
- 管理试驾预约和结果。
- 识别停滞商机。
- 记录赢单、输单和原因。
- 支持销售漏斗分析。

### 商品与库存管理能力

系统应让车辆商品成为交易和库存管理的基础对象。

主要能力包括：

- 维护车辆商品信息。
- 管理商品分类。
- 区分商品状态。
- 维护商品价格。
- 管理商品库存。
- 记录库存变动。
- 提供库存预警。
- 管理促销活动。

### 报价订单与交易履约能力

系统应把报价、订单、资金、发票和交付分清楚，避免把成交过程压缩成无法解释的单一状态。

主要能力包括：

- 创建报价。
- 管理报价版本。
- 审批特殊价格和优惠。
- 创建订单。
- 管理订单变更和取消。
- 管理库存占用。
- 创建和维护发票。
- 记录收款。
- 处理退款。
- 管理车辆交付。
- 关闭或完成交易履约。
- 保留订单和履约状态变化历史。

### 权限与责任归属能力

系统应明确不同用户在不同业务中的可见范围和操作边界。

主要能力包括：

- 管理用户账号。
- 管理角色。
- 管理权限。
- 区分查看、新增、编辑、删除、导入、导出、审批、收款等业务动作。
- 明确业务数据负责人。
- 支持按责任归属查看和管理数据。

### 经营分析能力

系统应为管理者提供可信的经营观察入口。

主要能力包括：

- 展示关键业务指标。
- 展示销售漏斗。
- 分析线索来源。
- 观察成交情况。
- 观察商品和库存状态。
- 识别业务异常和待处理事项。

### 基础数据治理与审计能力

系统应让状态、字典、分类、登录记录和关键操作追溯保持统一，避免不同模块各自定义业务口径或责任事实。

主要能力包括：

- 维护数据字典。
- 管理基础分类。
- 控制基础数据变更。
- 记录登录成功和失败。
- 记录关键业务操作。
- 保持业务展示值和业务判断值一致。
- 支持管理员追溯关键业务责任。

## 非目标范围

不覆盖以下范围：

- 面向消费者的线上购车商城。
- 公开营销官网。
- 金融贷款审批系统。
- 保险报价与承保系统。
- 车辆生产制造、维修保养工单和配件仓储。
- 二手车评估、拍卖和置换全流程。
- 第三方支付清算平台。
- 企业财务总账、税务申报和银行清结算。
- 多品牌集团级复杂组织、人力绩效和集团预算中台。
- 客户移动端应用。

相关业务可以保留必要协作入口或手工记录入口，但系统不承担专业外部系统的完整职责。

## 成功标准

业务成功标准包括：

- 销售人员能够清楚知道自己需要跟进哪些线索和客户。
- 每条线索都有明确来源、状态、负责人和跟进记录。
- 有效线索能够转化为客户，并保留转化关系。
- 客户资料、意向、跟进、商机、订单和交付历史能够形成完整视图。
- 商品、库存和订单之间保持一致。
- 订单履约状态清晰，报价、审批、发票、收款、退款、交付和完成状态能够被追踪。
- 商机、报价、订单、收款、发票和交付之间边界清楚，不互相替代。
- 试驾、报价和订单能够从商机中自然推进。
- 订单完成必须能够解释资金、票据、库存和交付结果。
- 每个核心业务对象都有明确状态、责任人、关键时间和关闭条件。
- 销售人员能够知道下一步该跟进谁、推进什么、风险在哪里。
- 管理者能够看见真实销售漏斗、来源质量、成交效率、库存压力和资金风险。
- 财务、库存和销售围绕同一订单协作，但各自状态不被粗暴合并。
- 关键业务动作有明确操作者和业务结果。
- 管理者能够查看可信的销售漏斗、来源分析和成交数据。
- 用户权限能够覆盖核心业务动作。
- 基础数据口径统一，状态、字典和分类不会在不同模块产生冲突。
- 业务异常能够被识别、追溯和处理。
- 系统能够支撑门店日常销售管理，而不是只完成单点记录。
