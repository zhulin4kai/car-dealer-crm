# 审计日志业务范围与边界

## 目的

审计日志用于帮助系统管理员追溯账号访问和关键业务变化，回答以下问题：

- 谁在什么时间尝试登录系统，结果是什么。
- 谁对哪个业务对象执行了什么动作。
- 动作是否成功，改变了哪些关键业务事实。
- 出现争议、异常或数据风险时，能否找到可靠的追溯依据。

审计日志是 CRM 的责任追溯和风险控制能力，不是服务器运维监控，也不是普通应用调试日志。

## 目标用户

主要使用者为系统管理员和经明确授权的审计人员。

销售、市场、财务、库存等普通业务角色默认不具备审计日志访问权限。角色本身参与业务操作，不代表有权查看其他人员的访问记录和操作记录。

## 功能范围

审计日志包含两个相互独立的业务能力：

- 登录记录：记录账号登录成功与失败的事实。
- 操作记录：记录关键业务命令及其结果。

两个能力必须拥有独立权限、独立筛选条件和独立页面，不得混为一张无法理解的技术请求列表。

## 非目标

第一阶段明确不包含：

- IP 归属地、经纬度或地图展示。
- 在线用户管理和强制下线。
- 服务器 CPU、内存、磁盘、网络、JVM 或进程监控。
- 系统名称、站点、Logo、版本等系统配置维护。
- 全量 HTTP 访问日志展示。
- 面向开发人员的异常堆栈、SQL、线程或基础设施诊断页面。
- 普通管理员手工删除、批量删除或清空审计记录。

## 与其他记录的关系

- 审计记录用于证明业务事实，必须长期稳定、可查询并具备明确业务语义。
- 应用日志用于故障诊断，可以包含技术上下文，但不得替代业务审计。
- 业务历史记录用于展示特定对象的生命周期，可以引用审计事实，但不得要求管理员在多个页面拼接才能确定责任人。
- 登录记录与用户账号状态相关，但不得直接成为自动封禁或安全评分的唯一依据。

## 核心原则

- 真实性：记录必须来源于服务端实际认证结果和最终业务结果。
- 可追溯性：记录必须能够关联操作者、时间、动作和业务对象。
- 最小披露：只记录追溯所需内容，不复制完整请求、响应或业务对象。
- 不可抵赖性：普通管理员和业务人员不得修改或删除既有审计事实。
- 稳定语义：动作和结果使用稳定含义，不能依赖页面中文或代码执行顺序解释。
- 业务优先：操作记录描述“审批交易”“调整库存”等业务动作，不以控制器方法名代替业务语义。

## 成功标准

- 管理员能够在合理时间内找到指定账号的登录记录。
- 管理员能够根据业务对象或操作人找到关键业务变化记录。
- 审计结果与实际提交结果一致，不出现已回滚业务被记录为成功的情况。
- 审计页面和导出数据不泄露认证凭证或不必要的客户敏感信息。
- 系统不再向业务管理员暴露无业务价值的服务器监控和临时系统配置功能。
