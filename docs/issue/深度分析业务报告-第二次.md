# 全量静态代码审计报告

> **审计对象**：`zhulin4kai/car-dealer-crm`，`main` 分支
> **审计方式**：只读静态审计；未修改文件、未生成补丁、未新增需求。
> **证据口径**：“确定”表示可由当前代码路径直接推出；“高概率”表示需要特定并发或数据条件，但代码缺少必要保护；“疑似”仅进入待确认项。
> **运行限制**：本报告未连接真实 MySQL、Redis、支付平台，也未执行生产数据压测。因此性能吞吐、数据库执行计划和 Redis 故障恢复能力只能按静态代码判断。

`openapi.yaml` 明确声明自己是当前对外接口契约，统一规则由 `api-conventions.md` 约束；业务基线则明确规定主链路为“线索→客户→商机→跟进/试驾→报价→订单→收款/发票/库存/交付→完成→经营分析”。本报告以这些文档反向检查代码，而不是以现有代码推定业务设计正确。

## 1. 系统整体判断

### 1.1 结论

| 判断项      | 结论                                                |
| -------- | ------------------------------------------------- |
| 当前系统更接近  | **半可用业务系统**                                       |
| 是否达到可试运行 | **未达到涉及真实库存、收款、退款和发票的业务试运行条件**                    |
| 是否达到可生产  | **否**                                             |
| 已确认 P0   | **10 个**                                          |
| 已确认 P1   | **21 个**                                          |
| 最高风险模块   | 交易、库存、收付款、发票、数据范围、Redis 会话、生产数据库结构                |
| 最不可信链路   | 客户/线索转化 → 报价式交易 → 提前扣库 → 开票/收款 → 仅凭收齐款完成 → 退款恢复库存 |
| 最需要统一的约束 | 业务状态机、数据范围、幂等键、库存流水、完成条件、DB 约束、HTTP 状态与稳定错误码      |

### 1.2 为什么不是普通 Demo

代码已经具备一些明显超出普通演示项目的工程能力：

* 使用 Spring Security 方法权限和服务端 JWT＋Redis 会话校验；
* 每次请求会重新读取用户状态和角色；
* 线索、客户、交易等查询已有后端数据范围过滤；
* 交易审批禁止创建人自批；
* 多个交易状态迁移使用旧状态或版本条件；
* 库存扣减 SQL 带有“扣减后不得小于零”的原子条件；
* 关键 Service 方法使用事务；
* 审计写入默认加入调用方业务事务；
* 前端已经统一使用模块 API 和 `httpClient`；
* 文件下载能够解析 Blob 形式的错误 envelope。

### 1.3 为什么仍不能用于真实业务

核心问题不是代码风格，而是**业务事实被压缩成少数表和状态字段**：

* 报价和交易共用 `t_tran`；
* 线索转客户会自动创建“待报价交易”；
* 报价创建时直接扣真实库存；
* 收款登记即视为已确认到账；
* 收齐款即可把交易置为完成；
* 没有独立订单、交付、车辆单位/VIN、库存占用事实；
* 退款会直接取消交易并恢复库存，但没有同步处理已开发票和已交付事实；
* 客户主档仍依附线索表，线索被删除后客户身份信息会丢失。

这与 Spec 中“报价不等于订单”“交易完成必须由订单、资金、票据、库存、交付共同支撑”“同一业务事实只能由一个模块拥有状态”的原则直接冲突。

### 1.4 文档阶段边界

本报告没有把所有未来设想都当作当前 Bug：

* **当前文档已经明确要求且当前代码应满足**：权限与数据范围、状态机、幂等、库存流水、收退款限制、发票历史、完成条件、API 契约、审计、统计可反算。
* **Plan 中规划但代码尚未实现**：作为能力差距描述，除非相同要求已经进入当前 Spec 或验收标准。
* **Spec 愿景之外的能力**：例如保险、信贷审批、会员、售后维修等，没有作为代码缺陷列出。
* 商机、试驾、订单、交付并非本报告擅自新增需求；它们已经写入当前核心业务 Spec 和对应模块 Spec，因此其完全缺失属于当前业务闭环缺口。

## 5. 核心业务闭环审计

### 5.1 线索 → 客户

**已闭环部分**

* 普通新增会把负责人强制设为当前用户，而不是信任客户端负责人；
* 列表、详情、更新和删除已带后端数据范围；
* 转化使用 scoped 查询和 CAS，能够阻止重复转换；
* 客户创建、交易创建和线索转换状态位于一个事务中，失败时不会留下半截客户；
* Excel 导入有 1000 行上限、文件内手机号去重、公式注入检查和全有或全无写入。

**缺口**

1. 生产手机号唯一约束缺失，查重不能抵御并发。
2. 转客户后自动创建报价交易，转化语义不纯。
3. 已转客户线索仍能物理删除。
4. 客户身份、来源和归属没有形成独立快照。
5. 客户归属转移和转移历史缺失。

**具体代码证据**

* `CustomerManager#convertCustomer` 插入客户后立即创建交易；
* `ClueServiceImpl#delClueById` 不检查客户引用；
* `t_customer` 只有 `clue_id` 等少量字段；
* 生产 `t_clue.phone` 没有唯一约束。

**是否阻塞真实业务：是。**

---

### 5.2 客户 → 商机 / 跟进 / 试驾 / 报价

**已闭环部分**

* 客户列表、详情和备注已有负责人数据范围；
* 客户备注可以记录基础跟进；
* 交易创建时商品价格从数据库读取，不接受客户端提交价格；
* 促销结算保存了促销快照，并使用版本和计价指纹防止预览后数据变化。

**缺口**

* 没有独立商机，一个客户多个购车意向只能继续增加 `TTran`；
* 没有待办式跟进任务，只存在备注；
* 没有试驾预约、安全确认、试驾车辆、爽约和反馈；
* 没有报价版本、有效期、客户确认和报价作废；
* 交易创建没有校验客户数据范围；
* 报价创建即扣库存。

核心 Spec 明确规定客户可以拥有多个商机、报价和订单；试驾完成不能自动产生报价；报价必须保存版本且不等于订单。

**是否阻塞真实业务：是。**

---

### 5.3 报价 → 订单 / 交易

**已闭环部分**

* 交易状态不是完全开放式任意更新；
* 结算使用 `QUOTATION → PENDING` 的原子 SQL和版本条件；
* 自建自批已被禁止；
* 结算金额由服务端基于全部商品行和促销重算；
* 促销结果保存快照。

**缺口**

* 报价、审批中的交易、订单和履约共用 `t_tran.stage`；
* 没有客户确认报价事件；
* 审批通过没有形成订单快照；
* 没有订单号、订单版本、付款责任、交付责任人；
* 重提删除原审批；
* 报价商品修改和报价创建直接改变库存；
* 交易可伪造客户 ID。

**是否阻塞真实业务：是。**

---

### 5.4 库存

**已闭环部分**

* `UPDATE stock = stock + delta WHERE stock + delta >= 0` 能阻止并发扣成负数；
* 事务中的库存更新会随交易失败回滚；
* 手工补货入口会写简单库存记录。

**缺口**

* 扣库时点发生在报价，不是订单锁车；
* 交易扣减和恢复没有写库存流水；
* 商品编辑可以直接覆盖库存；
* 库存流水没有绑定业务对象、原流水、动作幂等键；
* 恢复库存只按商品数量执行，不能证明原扣减存在且尚未恢复；
* 没有 VIN、车辆单位、门店、锁定到期、出库和退车状态。

**结论**

不会简单扣成负数不代表库存可信。当前最主要的库存风险是**时点、入口和可追溯性错误**。

**是否阻塞真实业务：是。**

---

### 5.5 收款 / 退款 / 发票

**已闭环部分**

* 收款前锁定交易记录；
* 服务端校验本次收款不会超过应收金额；
* 支付方式和支付类型有后端枚举校验；
* 发票金额由服务端要求等于当前交易总额；
* 发票状态更新有状态限制；
* 退款金额不是完全信任客户端，而是读取原收款。

**缺口**

* 无收款幂等约束；
* 登记收款即确认到账；
* 只审计收齐款，不完整审计部分收款；
* 退款模型只支持特定单笔全退；
* 可退金额没有按“累计已收－累计已退－处理中退款”统一计算；
* 发票只支持单张全额票；
* 没有部分开票、红冲、重开、失败；
* 退款不会联动发票和交付。

**是否阻塞真实业务：是。**

---

### 5.6 交易完成

**当前实现**

```text
PAYMENT 状态
    + COMPLETED 收款累计金额 >= 交易金额
    => 交易 COMPLETED
```

**文档要求**

```text
订单已成立
+ 车辆/占用明确
+ 应收满足
+ 必要票据完成
+ 交付签收完成
+ 库存已出库
+ 无阻断异常
=> 交易完成
```

代码和 Spec 是实质性冲突，不是命名差异。

**是否阻塞真实业务：是。**

---

### 5.7 统计反算

**已闭环部分**

* 成交金额单独使用 `COMPLETED` 状态；
* 基础统计均从数据库明细查询，而不是从 Redis 读取。

**缺口**

* `COMPLETED` 本身由错误完成条件生成；
* 总交易额包含报价、流失、取消等状态；
* “交易数”实际是去重客户数；
* 无时间口径；
* 无退款净额；
* 无角色数据范围；
* 统计结果不能下钻到同范围明细。

因此即使 SQL 数学计算没有错误，输入事实和指标定义也不可信。

**是否阻塞真实业务：是。**

## 6. API 契约一致性审计

### 6.1 OpenAPI 与 Controller 不一致

| 类型                | 契约                                | 当前实现                                                 | 结论                |
| ----------------- | --------------------------------- | ---------------------------------------------------- | ----------------- |
| `/api/login/free` | 描述为校验登录态，可能返回 401                 | 被配置为公开路径，Controller 无条件返回成功                          | **确定冲突**。         |
| 401/403           | OpenAPI 和约定要求 HTTP 401/403        | Filter 和 AccessDeniedHandler 返回 HTTP 200＋失败 envelope | **确定冲突**          |
| 时间                | OpenAPI `date-time` 通常表示 ISO-8601 | Jackson 全局输出 `yyyy-MM-dd HH:mm:ss`                   | **确定冲突或至少缺少兼容标注** |
| 商品状态              | 应定义稳定枚举                           | schema 允许任意字符串，前端提交中文，后端使用 `on_sale`                 | **确定冲突**          |
| 收款幂等              | Spec 要求重复外部参考号拒绝                  | `transactionRef` 非必填，也没有唯一约束                         | **契约缺失导致实现风险**    |

### 6.2 Controller 与前端 API

大多数路径已经统一通过领域 module API 调用，当前没有发现旧版那种页面直接创建 Axios 实例的大范围问题。用户、商品、交易 API 的主要 path 与 Controller 基本一致。前端基础设施也正确处理了 Result envelope、Blob 错误和文件名。

仍存在以下实质差异：

* 前端 Authorization 直接发送存储值，没有统一补 `Bearer `；后端为兼容同时接受裸 Token。它能工作，但违反约定并扩大历史兼容面。
* 商品状态语义不一致；
* 前端分页类型不能完整表达后端 PageInfo；
* 部分页面用中文错误文本决定业务提示。

### 6.3 响应结构

主 JSON API 基本统一使用：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {}
}
```

没有确认存在第二套 `success/message/result` envelope。主要问题不是 envelope 名称，而是：

* OpenAPI 对 `data` 的具体 schema 过于宽泛；
* Security Filter 绕过全局异常处理；
* 同一失败原因的 HTTP 状态不一致。

### 6.4 分页

当前存在：

* `current/pageSize`；
* `page/size`；
* 前端 `PageResult`；
* 后端 PageHelper `PageInfo`；
* 超大页有的裁剪、有的未限制、有的按约定应返回 400。

统一约定允许历史参数继续存在，但要求 OpenAPI 精确记录并明确迁移窗口；当前没有形成完整兼容治理。

### 6.5 错误码

**正确部分**

* `BusinessException` 可映射到 400、403、404、409、422 等状态；
* 前端 `httpClient` 优先读取稳定 `code`；
* 会话失效有单飞通知入口。

**问题**

* Filter/AccessDeniedHandler 不设置 HTTP 状态；
* 部分 Controller 直接返回 `Result.FAIL`，不经过异常映射；
* 前端仍有中文文本分支；
* 一些业务冲突仍使用通用 `FAIL/OPERATION_FAILED`，无法让客户端区分库存不足、重复支付、资源被引用等原因。

### 6.6 文件上传下载

**较可信部分**

* 下载不套 Result envelope；
* 前端可从 `Content-Disposition` 提取文件名；
* Blob 中为 JSON 错误时能还原为 `ApiError`；
* Token 通过 Header 发送，不再放入下载 URL。

**缺口**

* OpenAPI 对导入文件大小、MIME、扩展名、部分失败语义仍不够具体；
* 导入 Service 有 1000 行限制，但契约应同步说明；
* 需要真实 multipart 契约测试，而不是仅核对路径字符串。

### 7.2 JWT 会话 Redis 是否可信

**结论：读取校验路径基本可信；会话创建和撤销路径不可信，因此整体不能视为生产级闭环。**

可信部分：

* JWT 签名必须有效；
* Redis 必须存在完全相同 Token；
* Redis 失败时 `get()` 返回 null，认证拒绝，不会错误放行；
* 每次请求重新查询用户和角色；
* 禁用、锁定用户即使 Redis 残留，也会因 DB 状态复查被拒绝。

不可信部分：

* 登录 Redis set 失败仍返回 JWT；
* 登出 Redis delete 失败仍返回成功；
* 改密 Redis delete 失败仍提交密码并返回成功；
* 代码中没有可靠的会话版本机制。

### 7.3 字典缓存是否可信

**结论：不可信。**

详情缓存基本正确，但按类型列表缓存存在确定的失效遗漏；字典删除行为还会主动清理历史备注，问题已经超出缓存层。

### 7.4 负责人缓存是否可信

**结论：不可信。**

主要原因是无 TTL、List 非幂等回填、失效失败不可见。

### 7.5 Redis 是否被误当业务事实来源

**未发现 Redis 被用于决定金额、库存或交易状态。**

金额、状态和库存事实最终仍从数据库读取，这是正确方向。当前 Redis 风险主要集中在：

* 会话撤销；
* 负责人和字典脏缓存；
* key 治理混乱；
* 无收益的死缓存代码。

### 7.6 其他正向结论

* 模式删除使用 SCAN，而不是生产环境 `KEYS`。
* 线索 Excel 导入不再依赖长期全局 `cacheMap`，而是每次从数据库构建导入上下文。

## 8. 数据库与 SQL 审计

### 8.1 DDL / Model / Mapper / 测试 Schema 不一致

| 对象                       | 生产 DDL            | 测试 DDL          | 风险               |
| ------------------------ | ----------------- | --------------- | ---------------- |
| `t_clue.phone`           | 无唯一约束             | `UNIQUE(phone)` | 测试不会出现生产并发重复     |
| `t_customer.clue_id`     | 普通索引，无 FK         | FK RESTRICT     | 生产可删除已转线索，测试可能拒绝 |
| `t_tran.customer_id`     | 普通索引，无 FK         | FK RESTRICT     | 生产可产生悬空客户交易      |
| `t_tran_history.tran_id` | 无可靠删除约束           | FK RESTRICT     | 删除行为相反           |
| `t_tran_approve.tran_id` | `UNIQUE(tran_id)` | 没有唯一约束          | 测试可能允许生产会失败的重复审批 |
| `t_payment.tran_id`      | 无 FK              | FK RESTRICT     | 生产删除可留下资金孤儿      |
| 商品、促销、分类引用               | 生产约束较少            | 测试增加多组 FK       | 测试无法代表生产删除语义     |

### 8.2 关键约束缺失

生产至少缺少或未证明存在：

* 规范化线索手机号唯一；
* 客户与来源线索的一对一/合并语义约束；
* 交易号唯一；
* 支付渠道＋外部参考号唯一；
* 退款幂等号；
* 库存流水业务对象＋动作唯一键；
* 订单/库存占用唯一关系；
* 交易—客户、交易商品—商品、支付—交易、发票—交易的 FK；
* 字典 `type_code` 唯一。生产字典类型只有普通索引，而测试增加唯一。

### 8.3 动态 SQL 风险

**未确认存在不受控 SQL 注入。**

已审阅的核心 Mapper：

* 使用 `#{}` 参数；
* 状态范围使用 `<foreach>` 参数绑定；
* 数据范围片段是固定 XML 片段；
* 没有发现客户端字符串直接进入 `${}`。

需要继续用静态规则禁止未来新增 `${}`，但不应把旧文档中的历史实现误报为当前漏洞。

### 8.4 批量 SQL

线索批量删除在 Service 层处理空集合并去重；当前未确认会生成无条件 DELETE。字典批量删除也有空集合检查。风险主要不是空集合 SQL，而是**批量物理删除历史**。

### 8.5 稳定排序

交易列表只有 `ORDER BY create_time DESC`。当多条记录时间相同，数据库可以任意排序，跨页时可能出现重复或遗漏。应使用：

```sql
ORDER BY create_time DESC, id DESC
```

类似要求应覆盖线索、客户、活动、支付和审计列表。

### 8.6 索引风险

高概率需要补充或验证的复合索引：

* `t_tran(create_by, stage, create_time, id)`；
* 带组织模型后的 `t_tran(org_id, team_id, stage, create_time, id)`；
* `t_clue(owner_id, create_time, id)`；
* `t_customer(clue_id)` 的唯一或业务约束；
* `t_payment(tran_id, payment_status)`；
* `t_payment(transaction_ref)` 唯一；
* `t_tran_invoice(tran_id, status)`；
* 库存占用业务键；
* `t_operation_log(user_id, create_time)` 和 `(action_code, create_time)`。

是否选择上述具体顺序需结合 MySQL `EXPLAIN ANALYZE`，因此索引数量本身属于高概率性能项，不作为确定功能错误。

### 8.7 统计 SQL 风险

* `SUM(money)` 不过滤交易状态；
* 交易数使用去重客户数；
* 无退款净额；
* 无时间范围；
* 无数据范围；
* 多表事实未统一。

统计口径风险已经直接影响正确性，不只是性能问题。

### 8.8 删除与历史保护

生产数据库缺少 FK，Service 又存在大量先删子表再删主表的逻辑。其总体模式是：

```text
为了让 DELETE 成功
→ 先删除备注、审批、支付等历史
→ 再删除主对象
```

这与真实 CRM “历史事实不可因为主数据整理而消失”的要求相反。

## 9. 前端工程审计

### 9.1 模块边界

**当前较好。**

* 用户、商品、交易等 API 已迁移到 `modules/<domain>/api`；
* 页面通过模块 API 调用后端；
* 统一 `httpClient` 负责 Token、envelope、错误转换和文件下载；
* 未发现大面积页面自行创建 Axios client。

保留的旧 `doGet/doPost` 属于兼容残留，应防止新页面继续使用。

### 9.2 类型问题

主要问题：

* `PageResult` 没有完整映射 PageInfo；
* 多个状态仍声明为普通 `string`，未收窄为稳定 union；
* OpenAPI 本身 schema 过宽，前端很难生成可靠类型；
* Long/Integer ID 虽有 `EntityId` 兼容，但后端商品 ID 与部分交易 DTO 类型仍需系统性核对。

### 9.3 API 封装问题

正向部分：

* 正常 JSON 请求自动解包 `data`；
* 错误 envelope 转为 `ApiError`；
* 会话失效由稳定 code 驱动；
* Blob 错误能够还原。

问题：

* Authorization 没有统一 `Bearer`；
* 历史 API helper 仍暴露；
* 部分页面 catch 后丢失稳定 code；
* 商品页面在前端模拟服务器筛选。

### 9.4 权限展示与后端授权边界

当前路由和按钮权限可用于体验，但真正授权仍在后端 `@PreAuthorize` 和数据范围中，这是正确方向。

核心缺陷不是前端按钮，而是后端交易数据范围本身过宽。即使前端隐藏审批按钮，也无法阻止经理直接调用其他团队交易审批接口。

### 9.5 重复请求、loading 和错误处理

商品页具备：

* `loading`；
* `submitting`；
* 删除确认；
* 空 ID 检查；
* `finally` 恢复 loading。

但仍存在：

* 筛选时一次请求 1000 条，在前端过滤和再分页；
* 无明确“最后请求获胜”序号；
* 快速筛选时旧响应覆盖新响应的风险需运行测试确认；
* catch 常统一显示“加载失败”，丢失稳定业务原因。

### 9.6 中文 msg 分支

商品删除通过：

```ts
message.includes('foreign key')
|| message.includes('约束')
|| message.includes('引用')
```

判断资源是否被引用。这是确定的契约违规。

### 9.7 不可信字段提交

前端商品表单提交 `stock` 和中文 `status`，均不应由普通商品维护接口决定。交易表单提交 `customerId` 本身合理，但后端必须按当前用户范围重新验证，不能将它视为可信关联。

### 9.8 文件下载

该部分是当前前端相对可信的模块：

* 正确设置 `responseType: blob`；
* 检查 JSON Content-Type；
* 从 Blob 还原 API 错误；
* 支持 RFC 5987 文件名；
* 不依赖中文消息决定是否失效会话。

## 10. 代码风格与补丁代码审计

这里只列会造成长期维护或业务风险的编码模式。

### 10.1 用“自动补一个交易”填补缺失业务对象

`CustomerManager` 在线索转客户时直接构造交易，是典型补丁式闭环：

```text
没有独立商机/报价创建流程
→ 转客户时顺便创建 TTran
→ 看起来流程有下一步
→ 实际污染交易和库存事实
```

这不是普通代码重复，而是领域边界错误。

### 10.2 用一个 `TTran.stage` 代替多个领域状态

当前阶段同时承担：

* 报价；
* 结算；
* 审批；
* 发票准备；
* 收款；
* 完成；
* 取消。

结果是一个模块动作不得不直接推进另一个模块状态，例如创建 PENDING 发票直接把交易推进 PAYMENT。这种状态压缩会随着功能增加越来越难维护。

### 10.3 用删除历史解决引用冲突

典型位置：

* 删除线索前删除线索备注；
* 删除字典值前删除业务备注；
* 交易重提删除原审批；
* 删除交易清理审批、支付等子表。

这类代码是在绕过历史保护规则，而不是正常清理临时数据。

### 10.4 同一枚举兼容多套字符串

促销有效状态同时接受：

* `进行中`
* `ACTIVE`
* `active`

商品前端同时兼容：

* `上架`
* `ON_SHELF`
* `ENABLED`
* `on_sale`
* `ON_SALE`

这种兼容逻辑会掩盖数据库脏值。应在迁移后拒绝非法值，而不是永久扩大兼容数组。

### 10.5 Redis key 治理未真正统一

虽然 `RedisKeys` 注释声明为唯一入口，实际仍存在：

* `Constants.REDIS_JWT_KEY`；
* `Constants.CACHE_KEY_TRAN_*`；
* 手写 `"cdrm:tran:payments:"`；
* `RedisKeys`。

这会直接导致生产者、消费者和失效点使用不同 key。

### 10.6 测试在固化错误业务语义

现有交易单测明确断言：

* 创建 QUOTATION 会扣库存；
* 创建发票会进入 PAYMENT；
* 收齐款会完成交易；
* 重提删除旧审批；
* 退款恢复库存。

安全测试还断言未认证请求 HTTP 200。它们不是“缺少测试”，而是在保护与当前 Spec 冲突的行为。

### 11.1 已确认性能问题

| ID      | 问题                              | 为什么慢                  | 数据量上来后的表现                    | 优化方向                     | 是否影响正确性   |

## 13. 修复优先级地图

1. **先修 P0 生产阻塞**

    * 封堵交易 `customerId` 越权；
    * 落实团队/门店数据范围；
    * 统计使用同一数据范围；
