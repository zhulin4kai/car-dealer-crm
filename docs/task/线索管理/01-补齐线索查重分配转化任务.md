# 补齐线索查重分配转化任务

## 任务目标

按线索管理 Spec 和流转方案，补齐线索查重、分配转派、关闭原因、导入摘要、转客户和转商机边界，确保线索不会直接产生订单、收款或发票。

## 当前代码落点

- `ClueController.addClue` 负责新增线索入口。
- `ClueController.batchDelClue` 负责批量删除入口。
- `ClueServiceImpl.importExcel` 负责线索导入。
- `ClueServiceImpl.saveClue`、`delClueById`、`batchDelClueByIds` 是现有主要写操作。

- 前端线索 API 和类型在 `dealer-web/src/modules/clue/`，页面在 `dealer-web/src/pages/dashboard/clue/`。

## 执行步骤

1. 找出线索状态字段、来源字段、负责人字段和最近跟进字段。
2. 定义后端线索状态稳定 code，补齐新线索、待跟进、跟进中、已预约、已转客户、已转商机、无效、重复、战败。
3. 在 Service 层实现创建前查重，至少覆盖手机号、备用联系方式、姓名加联系方式、已有客户和已有活跃线索。
4. 补齐分配、认领、转派、回收方法，记录原负责人、新负责人、原因和时间。
5. 补齐关闭和恢复方法，关闭必须有无效、重复或战败原因，恢复必须有恢复原因。
6. 调整导入逻辑，返回成功、失败、重复数量和逐行错误摘要。
7. 调整转客户逻辑，保留线索来源、跟进历史和责任链，不删除线索历史。
8. 转商机在商机模块完成前返回明确业务错误或生成待办，不得直接创建交易。
9. 调整前端列表、详情、导入结果、关闭原因和转派交互。
10. 补充后端和前端测试。

## 代码逻辑要求

- Controller 只做参数绑定、权限和调用 Service，不能直接调用 Mapper。
- 查询必须带数据范围，禁止查询全部线索后在前端过滤。
- 批量导入必须限制单次数量，空文件、格式错误、重复数据和部分失败都要有稳定结果。
- 线索关闭后禁止继续编辑核心信息；恢复后才能继续推进。
- 删除线索前检查是否已转客户、已转商机或有关联跟进记录。
- 导出必须独立权限、数量限制和操作审计。

## 完成条件

- 新增线索有来源、负责人和初始状态。
- 重复联系方式能被识别并返回可理解结果。
- 转派线索保留责任变化记录。
- 转客户后线索历史仍可追溯。
- 线索转商机不会直接产生交易、收款或发票。
- 普通销售不能访问或导出超出范围的线索。

## 交付说明

完成后说明：

- 新增或调整的线索状态 code。
- 查重规则覆盖哪些字段。
- 导入结果如何表达重复和失败。
- 转客户、转商机边界如何处理。
- 哪些测试已运行，哪些风险仍待商机或跟进任务模块承接。

## 业务场景

- 线索进入、查重、分配、跟进、转客户或转商机。
- 执行时先确认该任务在业务闭环中的上游对象、下游对象和责任边界。

## 状态事件要求

- 线索状态只能表达线索自身生命周期，转化事件必须保留历史关联。
- 状态推进必须由真实业务事件触发，并保留必要原因、操作者和时间。

## 与其他任务的边界

- 跨模块共享不变量以 `docs/task/核心业务闭环/` 为准。
- 模块内部页面、接口、模型、测试和局部校验由本任务负责。
- 涉及共享文件时遵守 `docs/task/核心业务闭环/00-任务拆分总览.md` 的文件所有权。

## 不得破坏的业务事实

- 不得让线索转化直接生成交易、收款、发票或交付。
- 不得为了让测试通过而降低业务断言或删除历史事实。

## 场景验收

- 完成后能验证线索历史保留、客户或商机关联正确、无下游履约对象被误创建。
- 验收必须能映射到 `docs/task/文档链路治理/验收矩阵.md` 中至少一个端到端场景。
