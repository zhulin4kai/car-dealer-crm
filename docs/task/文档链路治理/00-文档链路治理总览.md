# 文档链路治理总览

## 任务目标

把业务闭环、模块规格、落地计划和执行任务统一成可追踪链路，避免文档按模块孤立编写，导致状态、责任、金额、库存、票据、交付和统计口径割裂。

## 文档链路

文档链路固定为：

业务闭环 Spec -> 模块 Spec -> 跨模块 Plan -> 模块 Plan -> 可执行 Task -> 验收矩阵。

每个模块文档必须能回答：

- 上游业务对象是谁。
- 下游业务对象是谁。
- 本模块负责什么业务事实。
- 本模块不能替代什么业务事实。
- 本模块拥有哪些状态。
- 本模块消费和发出哪些业务事件。
- 本模块产生哪些历史、审计和统计口径。

## 执行顺序

1. 新增业务闭环 Spec。
2. 更新项目业务方向规范。
3. 补齐所有模块 Spec 的业务对象关系和状态事件边界。
4. 更新核心业务闭环 Plan。
5. 补齐所有模块 Plan 的业务协同、状态事件、数据历史方案。
6. 更新核心业务闭环 Task 的职责边界。
7. 补齐所有模块 Task 的业务场景、状态事件、任务边界和场景验收。
8. 新增端到端验收矩阵。

## 文件所有权

- `docs/spec/业务闭环/` 负责全局业务对象关系、事件和异常历史规则。
- `docs/spec/项目业务方向规范.md` 负责项目愿景、业务地图和闭环引用，不重复展开状态细节。
- 各模块 `docs/spec/*/` 负责模块边界和模块状态事件。
- `docs/plan/核心业务闭环/` 负责跨模块不变量、依赖顺序和场景验收矩阵。
- 各模块 `docs/plan/*/` 负责模块落地方案。
- `docs/task/核心业务闭环/` 负责共享文件和跨模块不变量执行。
- 各模块 `docs/task/*/` 负责模块内部实现任务。
- `docs/task/文档链路治理/` 负责文档体系自身的治理任务和验收矩阵。

## 冲突处理

- Spec 与 Plan 冲突时，以 Spec 为准，修 Plan。
- Plan 与 Task 冲突时，以 Plan 为准，修 Task。
- 模块 Task 与核心业务闭环 Task 抢同一文件时，以核心业务闭环任务总览的文件所有权为准。
- 当前代码与 Spec 冲突时，以 Spec 为改造方向，不从代码反推业务规则。

## 完成条件

- 所有模块 Spec 都有业务对象关系和状态事件边界。
- 所有模块 Plan 都有业务协同关系、状态事件方案和数据历史方案。
- 所有模块 Task 都有业务场景、状态事件要求、任务边界、不得破坏事实和场景验收。
- 所有端到端业务场景都能从 Spec 找到 Plan，再落到 Task。
