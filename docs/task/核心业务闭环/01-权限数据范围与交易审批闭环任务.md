# 权限数据范围与交易审批闭环任务

## 任务目标

按用户权限和交易履约规则，修复销售创建交易后主管、财务无法处理的问题，同时禁止交易创建人审批自己的交易，补齐最后管理员角色保护和负责人候选过滤。

## 当前代码落点

- `CurrentUserProvider.getDataScopeUserId()` 当前只有管理员全局、非管理员本人两档结果。
- `DataScopeAspect.process()` 只把 `dataScopeUserId` 写入 `BaseQuery`。
- `TTranMapper.selectByQuery()` 和 `TTranMapper.selectScopedById()` 使用 `t.create_by = dataScopeUserId` 限制交易范围。
- `TranServiceImpl.approveTran()` 负责交易审批，但需要显式拒绝创建人审批本人交易。
- `UserServiceImpl.assignRoles()` 先删除用户全部角色再插入新角色，需要在删除前判断是否会移除最后一个管理员。
- `TUserMapper.selectByOwner()` 当前负责人候选需要过滤启用、未锁定和销售岗位。

## 执行步骤

1. 梳理当前角色编码，确认系统中用于管理员、销售顾问、销售经理、财务人员的稳定 role code。
2. 在后端建立数据范围判断模型，至少表达：
   - `SELF`：本人负责数据。
   - `TEAM_APPROVAL`：销售经理可处理团队或固定范围内待审批交易。
   - `FINANCE_STAGE`：财务可处理进入财务阶段的交易、发票、收款和退款。
   - `ALL`：管理员全局数据。
3. 调整 `CurrentUserProvider`：
   - 保留获取当前用户 ID 的职责。
   - 新增或返回可表达角色数据范围的对象，不再只用一个 nullable userId 表达全部规则。
   - 如果短期仍使用 `BaseQuery.dataScopeUserId`，必须为交易查询额外补充财务阶段和审批阶段过滤字段，避免把所有非管理员继续锁死在本人数据。
4. 调整 `DataScopeAspect`：
   - 对普通业务查询注入本人范围。
   - 对交易查询注入角色范围、允许阶段或允许审批状态。
   - 确保 Mapper SQL 中体现数据范围，不能查全量后在 Java 中过滤。
5. 调整 `TTranMapper.xml`：
   - `selectByQuery` 支持销售本人、销售经理审批范围、财务阶段范围和管理员全局。
   - `selectScopedById` 与列表规则一致，详情、审批、开票和收款不能出现列表不可见但详情可操作的漏洞。
6. 调整 `TranServiceImpl.approveTran()`：
   - 在加锁读取交易后比较 `tran.createBy` 与当前审批人。
   - 相同则抛出稳定业务异常，不进入 `updateStageAtomic`。
   - 拒绝和通过两个分支都必须受此规则限制。
7. 调整 `UserServiceImpl.assignRoles()`：
   - 读取目标用户当前角色。
   - 如果目标用户当前拥有管理员角色，而新角色集合不再包含管理员角色，则执行最后管理员保护。
   - 内置管理员不得被移除管理员角色。
   - 删除旧角色必须发生在所有校验通过之后。
8. 调整 `TUserMapper.selectByOwner()`：
   - 只返回启用、未锁定账号。
   - 只返回具备销售顾问或销售经理等可作为线索、客户、商机负责人角色的账号。
   - 返回字段保持前端负责人下拉需要的最小字段。
9. 检查前端用户管理：
   - 角色分配失败时展示后端稳定错误信息。
   - 负责人下拉不在前端二次拼接非法候选。
10. 补充测试：
   - 销售顾问创建待审批交易后，销售经理能查到并审批。
   - 财务能查到进入财务阶段的交易并进行开票、收款。
   - 交易创建人审批本人交易被拒绝。
   - 最后一个管理员不能通过角色分配移除管理员角色。
   - 负责人候选不包含禁用、锁定、财务、库存等不适合成为销售负责人的账号。

## 代码逻辑要求

- 角色判断集中在安全或权限服务中，不能在多个业务 Service 中散落字符串判断。
- 查询范围必须在 SQL 层完成。
- 权限失败与业务状态失败使用稳定错误码或稳定异常类型。
- 审批写入、阶段更新、库存释放和审计记录保持原有事务语义。
- 不得通过放宽交易详情查询来让主管和财务“看见全部”。

## 完成条件

- 销售创建的待审批交易，主管可见并可审批。
- 财务可处理进入财务阶段的交易。
- 创建人不能审批自己创建的交易。
- 最后一个管理员不能被移除管理员角色。
- 负责人候选只包含有效销售类账号。

## 业务场景

- 跨模块修复权限、商品促销契约、交易资金库存、历史保护、DDL 和统计口径。
- 执行时先确认该任务在业务闭环中的上游对象、下游对象和责任边界。

## 状态事件要求

- 核心任务负责共享不变量和跨模块状态事件，不替代模块内部状态实现。
- 状态推进必须由真实业务事件触发，并保留必要原因、操作者和时间。

## 与其他任务的边界

- 跨模块共享不变量以 `docs/task/核心业务闭环/` 为准。
- 模块内部页面、接口、模型、测试和局部校验由本任务负责。
- 涉及共享文件时遵守 `docs/task/核心业务闭环/00-任务拆分总览.md` 的文件所有权。

## 不得破坏的业务事实

- 不得和模块任务抢同一文件；共享文件以任务拆分总览 owner 为准。
- 不得为了让测试通过而降低业务断言或删除历史事实。
