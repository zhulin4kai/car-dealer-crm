- Task 25—29 已完成并通过试点；不得在迁移命令族时再次发明切面、策略、协调器或事件协议。

## 迁移范围

- `AuthorizationServiceImpl` 中用户角色、个人 GRANT/DENY、有效期、数据范围和批量授权写命令。
- `RoleAccessServiceImpl` 中角色目录、适用组织、权限矩阵、影响预览和角色停用写命令。
- 对应 Controller 用例入口、DTO 适配和测试；查询投影可以暂留原 Service，但不得继续混入写逻辑。

## 目标不变量

- 禁止自改、上下级边界、可委派上限、受保护角色双人治理、个人拒绝优先和数据范围来源保持不变。
- 角色矩阵变更必须锁定并验证全部受影响用户，使用版本 CAS，原子写完整历史和审计。
- 批量授权全成功或全失败，目标顺序稳定，任一历史或版本失败全部回滚。
- 成功后数据库授权版本立即阻断旧 Token，Redis 和负责人候选缓存通过提交后事件清理。

## 允许修改范围

- 角色/授权命令处理器、显式授权策略调用、协调器计划适配和事件适配。
- 原 `AuthorizationServiceImpl`、`RoleAccessServiceImpl` 及直接测试、Controller 注入。
- 为兼容查询所需的只读投影接口。

## 禁止修改范围

- 不改变权限计算公式、权限 code、角色种子、数据范围 code、API 或错误码。
- 不把影响用户查询、受保护角色规则或授权上限放入切面。
- 不保留新旧写入口双写，不让同一变更生成两份历史、审计或会话事件。
- 不修改其他业务模块的数据范围 Mapper。

## 执行步骤

1. 按 Task 25 矩阵逐个迁移角色目录、矩阵、用户角色和个人权限命令。
2. 命令先提交显式锁计划，在锁内调用授权委派策略并完成 Mapper CAS。
3. 构造类型化授权历史和影响用户快照，交由事务协调器同步保存。
4. 对每个受影响用户显式提交授权/认证版本及会话撤销计划，提交后统一清缓存。
5. 每迁移一个命令即删除旧写方法或改为不超过 5 个依赖的单向兼容委派；同一版本结束前删除全部兼容委派。
6. 用代码图谱确认所有生产 Controller 已指向新命令入口，旧写方法无生产调用。

## 特征与并发测试

- 本人、同级、上级、跨组织、受保护账号和越级委派拒绝保持原 code。
- 角色矩阵影响预览与实际受影响用户一致，范围外成员使修改失败。
- GRANT/DENY、取消拒绝、临时到期、续期和 `CUSTOM_ORGS` 来源保持一致。
- 两名管理者并发修改同一用户或角色时仅一方成功，另一方返回既有冲突。
- 历史、审计、授权版本或批量任一目标失败时全部回滚且无提交后事件。

## 量化验收

- 新角色/授权命令处理器每个不超过 250 行、直接依赖不超过 8 个、公开写方法不超过 60 行。
- `AuthorizationServiceImpl` 与 `RoleAccessServiceImpl` 合计行数相对 Task 25 基线至少下降 40%。
- 两个旧类对 `revokeAllForSecurityChange`、`invalidateAfterCommit` 和 `registerSynchronization` 的直接调用全部为 0。
- 每个角色或用户授权命令只产生一次协调器调用和一次根提交后事件。
