# 用户管理提交后事件任务

## 关联业务缺口

- UM-39（P2）：Redis 清理、负责人候选缓存失效和提交后注册分散，提交时序、重试和告警语义不一致。

- Task：`docs/task/用户权限/24-凭证Outbox与管理员降级恢复任务.md`

## 前置依赖

- Task 28 已完成，事务内权威事实和提交后副作用已经通过类型化计划分开。
- 现有凭证 Outbox 继续作为外部凭证投递权威机制；本任务不得建立第二套通知队列。

## 目标不变量

- 提交后事件只代表数据库权威事实已经提交，不代替业务事务、历史、审计、会话事实或凭证状态。
- 回滚事务不发布事件；成功事务按稳定事件 ID 发布一次。
- Redis 会话 Key 清理失败不能使旧 Token 恢复有效，因为数据库安全版本和撤销事实已经生效。
- 负责人候选缓存、派生列表缓存和 Outbox Worker 唤醒均可幂等重试。

## 允许修改范围

- 用户管理本地提交后事件、发布桥、处理器、重试/告警接口和测试。
- 收敛 `OwnerCandidateCacheInvalidator`、用户会话 Redis 清理和 Outbox Worker 唤醒入口。
- 必要的稳定指标与脱敏日志。

## 禁止修改范围

- 不发布原始凭证、nonce、完整联系方式、密码摘要、恢复密钥或完整授权明细。
- 不通过普通 Spring 内存事件替代 Task 24 的持久化凭证 Outbox。
- 不在处理器写授权历史、组织历史、生命周期事件或“成功”业务审计。
- 不让处理器失败回滚已经提交的数据库事务，也不静默吞掉重试耗尽。
- 不要求 Controller 等待 Redis 清理或 Worker 实际投递才返回业务成功。

## 执行步骤

1. 定义不可变事件，包含事件 ID、根命令 ID、命令 code、目标 ID、已提交版本和派生副作用枚举。
2. 协调器只在事务同步可用时注册统一发布桥；回滚和无事务调用都不得发布。
3. 事件处理器按副作用类型执行 Redis 会话清理、负责人候选缓存失效、派生缓存清理和 Outbox Worker 唤醒。
4. 每个处理器以事件 ID 和目标版本保证幂等，重复处理不得重复撤销数据库事实或生成第二个凭证。
5. 定义有限重试、退避和重试耗尽告警；日志只包含事件 ID、命令 code、目标 ID 和失败分类。
6. 删除试点写服务中的手工 `TransactionSynchronization` 和直接缓存清理。
7. 对进程在提交后、处理前中断的窗口明确恢复策略；必须恢复的外部投递仍依赖持久 Outbox。

## 测试

- 提交、回滚、嵌套事务和重复事件分别产生确定次数。
- Redis 第一次失败、第二次成功时数据库授权已经失效且处理器最终完成。
- 重复事件不重复创建凭证、不重复写业务审计、不改变权威历史。
- Outbox Worker 唤醒丢失时，定时扫描仍能处理 `PENDING/RETRY` 消息。
- 事件序列化或日志中不存在敏感字段。

## 量化验收

- 用户管理写服务对 `invalidateAfterCommit` 和 `registerSynchronization` 的直接调用在试点范围降为 0。
- 全项目只保留一个用户管理事务提交后发布桥；处理器按副作用拆分，单处理器不超过 150 行、构造依赖不超过 5 个。
- 每个事件处理器至少覆盖成功、重复、暂时失败和永久失败四类测试。
- 事件失败不会导致任何已提交安全版本回退，相关集成测试必须直接校验数据库与 Token 访问结果。
