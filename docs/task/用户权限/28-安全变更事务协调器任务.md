- UM-37（P2）：安全版本、会话事实、凭证撤销、权威历史和审计在多个写服务重复编排，存在漏调用和顺序漂移风险。

- Task 25—27 已完成，命令矩阵、特征测试和显式策略可用。
- 本任务建立事务内编排能力，但不迁移全部命令；Task 30—32 才按命令族切换。

## 目标不变量

- 公开写命令继续拥有明确 `@Transactional(rollbackFor = Exception.class)`。
- 锁序、状态校验和业务 CAS 在命令或显式策略中可见，协调器不按方法名推断。
- 协调器只消费类型化 `SecurityMutationPlan` 和 `MutationReceipt`，不重新查询业务对象决定规则。
- 安全版本、数据库会话撤销事实、凭证撤销、权威历史和操作审计全部在同一事务完成。
- 任一要求的影响行数、历史或审计失败时整个业务动作回滚。

## 显式计划字段

- 稳定命令 code、操作者、目标用户/员工/角色/组织标识。
- 命令已经取得的有序锁计划及锁内策略校验收据。
- 已完成业务 CAS 的对象、预期版本、实际影响行数和冲突 code。
- 是否提升认证/授权/会话 revision 及其预期影响行数。
- 需要同步撤销的数据库会话事实和活动凭证。
- 类型化授权历史、组织任职历史、生命周期事件和操作审计摘要。
- 事务提交后需要触发的派生副作用类型，不包含原始凭证或完整联系方式。

## 允许修改范围

- 新增协调器、类型化计划/收据、锁计划执行器和测试。
- 收敛 `AuthorizationAuditRecorder`、会话数据库撤销及安全版本更新的通用事务入口。
- 选择一个 Task 25 已保护的低风险写命令作为试点。

## 禁止修改范围

- 协调器不持有 `ApplicationContext`，不反射调用 Service，不接收自由 Map 作为业务计划。
- 不在协调器或切面隐藏最后管理员、汇报环、状态机和目标可管理性判断。
- 不把权威历史、生命周期事件或审计移动到提交后事件。
- 不在事务内调用 Webhook、Redis 网络清理或其他不可控外部调用。
- 不允许协调器忽略影响行数为 0 或把审计失败降级为日志。

## 执行步骤

1. 定义不可变 `SecurityMutationPlan`，通过构建器校验命令 code、目标、历史与副作用组合。
2. 定义 `MutationReceipt`，证明业务 CAS 已按预期完成；缺失或失败收据直接拒绝协调。
3. 定义显式 `SecurityLockPlan`，只负责按命令给出的有序枚举获取锁并校验返回值，不自行选择锁。
4. 协调器入口验证实际事务存在，且同一根命令最多应用一次最终安全变更计划。
5. 按固定阶段执行：验证收据 → 安全/授权版本 → 数据库会话与凭证事实 → 权威历史/生命周期事件 → 操作审计 → 注册提交后事件。
6. 复用可信操作者、请求 ID 和时间来源，覆盖调用方传入的非可信审计字段。
7. 为单目标、批量目标、无会话、无凭证和多历史场景定义确定语义。
8. 试点命令重构前后执行同一特征测试并比较全部数据库表和审计输出。

## 测试

- 无事务调用协调器立即失败且无任何写入。
- 收据缺失、CAS 影响行数不符、版本提升不完整、历史失败、审计失败均整体回滚。
- 事务回滚不发布提交后事件，事务提交只发布一次。
- 锁计划顺序错误、重复锁和未知锁被拒绝，命令声明的合法顺序保持可见。
- 批量目标按稳定 ID 排序处理，任一目标失败时全批回滚。
- 原始凭证、nonce、完整联系方式和恢复密钥不能进入计划、历史、审计或事件。

## 量化验收

- 协调器直接构造依赖不超过 8 个，公开方法不超过 4 个，单文件不超过 300 行。
- `SecurityMutationPlan` 不超过 20 个强类型字段；需要扩展时优先组合值对象，不增加自由字符串开关。
- 试点写服务对 `revokeAllForSecurityChange`、`invalidateAfterCommit` 和手工 `registerSynchronization` 的直接调用均降为 0。
- 同一试点命令的版本提升、会话事实、历史和审计调用次数均为恰好一次。
