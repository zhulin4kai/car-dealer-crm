# 用户数据范围与负责人资格任务

## 关联业务缺口

- UM-11：数据范围主要只有管理员全局和普通用户本人。
- UM-12：负责人候选按全局角色筛选，不能反映组织、岗位和管理范围。

## 当前错误行为

- `CurrentUserProvider` 和 `DataScopeAspect` 主要提供单一用户 ID 范围，无法表达团队和组织树。
- `/api/owner` 对所有登录用户返回全局启用销售角色账号，且缺少组织范围授权。

## 目标不变量

- 数据范围按具体权限动作计算，稳定使用 `SELF`、`DIRECT_REPORTS`、`REPORTING_TREE`、`PRIMARY_ORG`、`ORG_TREE`、`CUSTOM_ORGS`、`GLOBAL`。
- 功能权限和数据范围必须同时满足；个人权限增加不自动获得更大数据范围。
- 负责人候选必须同时满足账号、任职、岗位资格和当前操作者组织范围。

## 前置依赖

- 完成 Task 09、Task 11、Task 12 和 Task 13。

## 允许修改范围

- `CurrentUserProvider`、`DataScopeAspect`、数据范围上下文与解析器及直接测试。
- 用户列表、管理者候选、负责人候选相关 Mapper、Service、API、缓存和测试。
- 数据范围权限常量、OpenAPI、`modules/user/model/owner.types.ts` 和 `modules/user/api/user-api.ts`。
- `t_role_permission_organization`、`t_user_permission_organization` 的 Schema、Model、Mapper、历史与迁移；`CUSTOM_ORGS` 组织候选、保存和读取接口及前端选择器。

## 禁止修改范围

- 不在本任务中批量改造其他业务模块 Mapper 和页面。
- 不通过查询全部后 Java 或前端过滤。
- 不因为用户拥有某个经理或财务角色直接赋予全局范围。

## 兼容契约

- 保留现有单用户范围入口供旧业务 Mapper 兼容，新用户管理接口使用结构化数据范围上下文。
- 数据范围上下文包含是否全局、可见用户、可见组织和对应范围类型，不依赖中文角色名。
- 负责人列表缓存按操作者、组织范围和资格维度隔离，并具有 TTL 与可靠失效。

## 执行步骤

1. 新增按权限 code 解析的数据范围上下文，组合角色范围、个人范围和当前组织关系。
2. 实现组织树、直属下属和有效汇报树查询，排除过期代理关系。
3. 用户列表和候选 Mapper 接受结构化范围并在 SQL 中限制。
4. 重构负责人候选资格，要求账号启用、未锁定、在职、岗位有效且在可管理范围。
5. 明确组织、任职、岗位、授权变化触发负责人候选缓存失效；TTL、并发回填和缓存实现由 Task 06 唯一负责。
6. 增加全局范围保护，普通管理者不能通过角色组合或个人增加获得全局。
7. 为 `CUSTOM_ORGS` 原子保存明确组织集合，校验操作者覆盖范围、重复项、组织启停、授权有效期和历史审计；组织停用后不得继续参与新授权，已有事实保留解释并从有效范围退出。
8. 同步 OpenAPI、前端类型和相关测试。

## 测试

- 本人、直属下属、汇报树、主要组织、组织下级、指定组织和全局范围计算。
- 同一用户不同权限动作可以得到不同范围。
- 个人增加权限没有明确范围时不能扩大访问。
- 过期代理管理关系不进入范围。
- 用户列表和负责人候选在 SQL 层限制，跨组织 ID 请求被拒绝。
- 负责人候选事实查询按范围隔离，缓存行为在 Task 06 验证。
- 角色和个人 `CUSTOM_ORGS` 集合持久化、越界拒绝、到期、组织停用和历史解释正确。
