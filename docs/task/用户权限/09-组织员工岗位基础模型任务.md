## 关联业务缺口

- UM-01：账号、员工、岗位和权限角色含义混合。
- UM-02：缺少公司、门店、部门、团队和任职历史模型。

## 当前错误行为

- `t_user` 同时承担登录账号和员工资料，没有组织、岗位、任职、直属管理者及历史事实。
- 现有账号无法表达待激活、离职、返聘、兼岗和代理任职。

## 目标不变量

- 账号、员工、岗位、组织和权限角色分别表达，用户 ID 和登录行为由最终模型直接承载。
- 一个员工同一时间只有一个有效主要任职，兼岗和代理任职具有明确有效期。
- 组织和任职历史不可通过更新当前记录被覆盖。

## 前置依赖

- 无前置依赖。

## 允许修改范围

- `dealer-server/src/main/resources/CarDealerCRM.sql`
- `dealer-server/src/main/resources/schema-test.sql`
- `dealer-server/src/main/resources/data.sql`
- 组织、岗位、员工、任职和汇报关系的 Model、Mapper、Mapper XML、枚举及测试。
- `TUser` 与本任务最终字段及其 Mapper 映射。

## 禁止修改范围

- 不修改其他业务模块的状态机、页面和 Mapper。
- 不改变用户 ID、角色权限关系及当前有效登录语义。
- 不伪造现有用户的真实直属管理者；无法推断的信息进入待补录状态。

## 数据契约

- 新增组织单元、岗位、员工、任职和汇报关系表，使用稳定 code、外键、唯一约束和版本字段。
- 组织类型使用 `COMPANY`、`STORE`、`DEPARTMENT`、`TEAM`。
- 任职类型使用 `PRIMARY`、`SECONDARY`、`ACTING`；任职状态使用稳定英文 code。
- 最终表、字段、约束、索引和种子直接写入正式数据库基线，不建立增量升级链。
- 无法推断真实组织的用户进入待补录状态，或关联明确标记的待分配占位组织；占位组织不得进入管理范围、负责人资格和业务数据范围计算。
- 账号新增和资料更新入口必须在 Task 15、Task 16 完成账号—员工事务性创建及资料写入后再开放；仅写 `t_user` 的结果不构成完整员工档案。

## 执行步骤

1. 设计并同步生产 Schema、H2 Schema和初始化数据，直接形成最终数据库基线。
2. 新增组织、岗位、员工、任职、汇报关系的 Model、Mapper 和 Mapper XML。
3. 建立默认公司和明确标记的待分配占位组织；不伪造真实门店、团队和直属管理者，补录前不生成可参与权限计算的真实主要任职。
4. 保留受保护系统恢复账号不绑定普通员工，禁止通过员工流程修改。
5. 通过唯一约束和事务保证账号员工一对一、主要任职唯一和当前直属关系唯一。
6. 增加稳定排序、孤儿关系、重复 code、非法有效期和影响行数检查。
7. 补充基线核验测试，检查行数、空值、重复、孤儿和历史记录。
8. 从空数据库执行正式基线，验证生产 Schema、H2 Schema 和初始化数据表达同一最终模型。

## 测试

- Schema 约束：组织 code、员工编号、账号员工关系和主要任职唯一。
- Mapper：组织层级、岗位、员工和有效任职查询映射正确且排序稳定。
- 基线：初始化用户均具有完整员工资料，用户 ID、密码和角色关系正确。
- 事务：任职历史写入失败时当前任职不发生部分更新。
- 方言：H2 测试通过，并核对 MariaDB/MySQL 使用的 Check、索引和时间类型。
