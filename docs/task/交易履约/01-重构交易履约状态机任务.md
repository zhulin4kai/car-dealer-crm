# 重构交易履约状态机任务

## 任务目标

按交易履约 Spec 和状态治理方案，重构交易履约状态机，确保订单成立、收款、发票、库存和交付状态互相观察但不混淆。

## 当前代码落点

- `TranServiceImpl.createTransaction` 创建交易。
- `TranServiceImpl.settleTransaction` 处理结算。
- `TranServiceImpl.approveTran` 处理审批。
- `TranServiceImpl.deleteLockedTransaction`、`resubmitTransaction` 处理删除和重提。
- 前端交易状态映射在 `tran-stage.ts`。

## 执行步骤

1. 梳理现有 `TranStage` 枚举、数据库状态值、前端状态映射和测试数据。
2. 定义目标履约状态和允许动作矩阵。
3. 将交易状态迁移收口到明确方法，如 `placeOrder`、`markDepositPending`、`markVehicleLocked`、`startDelivery`、`completeTransaction`、`cancelTransaction`、`closeTransaction`。
4. 状态更新 SQL 带当前状态、交易 ID 和数据权限条件。
5. 交易完成校验订单未取消、交付完成、应收满足条件、必要发票或票据流程完成、资料移交完成。
6. 取消和关闭记录原因，并为库存释放、退款处理和商机结果提供联动。
7. 写入 `TTranHistory` 或等价历史记录。
8. 调整前端交易列表、详情和状态操作。
9. 补充状态迁移、并发冲突、事务回滚、前端映射测试。

## 代码逻辑要求

- 成功迁移必须检查 Mapper 影响行数为 `1`。
- 非法迁移返回稳定业务错误码。
- 交易历史记录操作者、前后状态、原因和时间。
- 收款、发票、交付任一完成不能单独把交易置为完成。
- 已完成交易不得普通取消。

## 完成条件

- 订金完成不会自动完成交易。
- 发票完成但车辆未交付时交易仍待交付或交付中。
- 交付完成且应收满足完成条件后交易可完成。
- 取消交易后库存释放和退款待处理状态可见。
- 已取消交易不计入完成成交数。
- 前后端状态 code 一致。

## 交付说明

完成后说明：

- 目标履约状态和允许动作矩阵。
- 哪些旧状态如何迁移或兼容。
- 交易完成条件如何判断。
- 与商机、收款、发票、交付的边界。

## 业务场景

- 订单成立后聚合观察库存、收款、发票、交付和异常阻塞点。
- 执行时先确认该任务在业务闭环中的上游对象、下游对象和责任边界。

## 状态事件要求

- 交易履约状态只能聚合完成判定，不能吞并资金、票据、库存和交付独立状态。
- 状态推进必须由真实业务事件触发，并保留必要原因、操作者和时间。

## 与其他任务的边界

- 跨模块共享不变量以 `docs/task/核心业务闭环/` 为准。
- 模块内部页面、接口、模型、测试和局部校验由本任务负责。
- 涉及共享文件时遵守 `docs/task/核心业务闭环/00-任务拆分总览.md` 的文件所有权。

## 不得破坏的业务事实

- 不得让单一收款、发票或交付动作直接完成交易。
- 不得为了让测试通过而降低业务断言或删除历史事实。

## 场景验收

- 完成后能验证交易完成可从订单、资金、票据、库存和交付明细反算。
- 验收必须能映射到 `docs/task/文档链路治理/验收矩阵.md` 中至少一个端到端场景。
