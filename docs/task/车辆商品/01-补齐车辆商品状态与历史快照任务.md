# 补齐车辆商品状态与历史快照任务

## 任务目标

按车辆商品 Spec 和目录治理方案，补齐商品状态、可报价控制、删除限制、历史快照和前端商品状态展示。

## 当前代码落点

- `ProductController.addProduct` 是当前商品创建入口。
- `ProductServiceImpl.addProduct`、`restock` 是当前商品和库存关联主要逻辑。
- `ProductCategoryController.addCategory` 和 `ProductCategoryServiceImpl.addCategory` 是分类入口。
- 前端商品、分类、库存、促销类型集中在 `dealer-web/src/modules/product/model/product.types.ts`。

## 执行步骤

1. 定义商品状态 code：草稿、上架、可售、暂停售卖、下架、停售。
2. 调整商品创建、编辑、上架、下架、停售和删除限制。
3. 报价候选、订单候选和试驾候选只允许使用符合状态的商品。
4. 商品被报价、订单、试驾或库存引用后，禁止修改会破坏历史事实的字段。
5. 为订单或报价引入成交时商品描述快照，包含品牌、车系、车型、配置、年款和指导价摘要。
6. 分类删除前检查商品引用。
7. 调整前端商品列表、表单、状态操作和分类删除提示。
8. 补充商品状态、历史快照、引用限制和前端测试。

## 代码逻辑要求

- 商品状态使用稳定 code，不保存中文文案。
- 商品删除 Mapper 必须带主键和引用限制，禁止无条件删除。
- 商品状态变化写操作审计。
- 前端不能通过隐藏停售商品绕过后端校验。
- 商品价格是报价基础，不等于最终成交价。

## 完成条件

- 草稿商品不会出现在销售报价候选中。
- 下架商品不再参与新报价。
- 历史订单仍能显示成交时车辆信息。
- 商品有关联订单时普通人员不能直接删除。
- 商品状态变化可审计。

## 交付说明

完成后说明：

- 历史快照保存在哪里。

## 业务场景

- 维护车辆商品目录、分类、价格、状态、可报价控制和成交快照。
- 执行时先确认该任务在业务闭环中的上游对象、下游对象和责任边界。

## 状态事件要求

- 商品状态表达目录可售性，不代表具体库存和订单成交状态。
- 状态推进必须由真实业务事件触发，并保留必要原因、操作者和时间。

## 与其他任务的边界

- 跨模块共享不变量以 `docs/task/核心业务闭环/` 为准。
- 模块内部页面、接口、模型、测试和局部校验由本任务负责。
- 涉及共享文件时遵守 `docs/task/核心业务闭环/00-任务拆分总览.md` 的文件所有权。

## 不得破坏的业务事实

- 不得让商品编辑覆盖库存数量或历史订单快照。
- 不得为了让测试通过而降低业务断言或删除历史事实。

## 场景验收

- 完成后能验证商品状态、报价候选、历史快照和引用保护。
- 验收必须能映射到 `docs/task/文档链路治理/验收矩阵.md` 中至少一个端到端场景。
